# ORC-030 stabilization, worker S2: five fixes, their options and choices

**What this is.** The record of five backlog items from `docs/design/ORC-030-stabilization.md`: B-05, B-04, B-32, B-33 and B-17. For each: the defect, its root and the class of the root, the options, the choice and why, the test that failed before the fix, and the lesson.

**Where it fits.** ORC-030 step 2 fixes each bug at its root with a test that fails first. Step 1 (QA) and the other workers' items run beside this one. The lead merges this branch and updates the backlog and the README.

**What I need from you.** Nothing to continue. Two product choices are at the end, each with a recommendation.

## B-05: Checks steps waited on the wrong probe

**Defect.** A Checks step waited until the Codex sandbox on this computer passed its probe, even when the project's environment (Docker) would run the checks. A user without Codex had every Checks step held.

**Root (build).** Unit E1 moved the checks into the environment, but the probe and the hold stayed on the host sandbox. Two places decided where checks run: the run's route (the facade) and the probe (always the host).

**Options.**

| | Option | For | Against |
| --- | --- | --- | --- |
| a (chosen) | The probe goes where a run goes: the facade routes runs and probes through one function, and the scheduler gives the probe the environment a run would get. The observed record says where the checks run (`runsIn`). | One decision for runs and probes. The domain's hold does not change. | The scheduler reads the dev container at the trusted base for each probe (at most every six hours, or on a change). |
| b | Probe both places every time; hold only when neither is ready. | Simple to state. | It probes Codex for users who have none, and the hold no longer says where checks will run. |
| c | Put an environment observation in the state and decide in the domain. | The hold is pure. | The domain cannot see the dev container, so it would hold a second copy of the decision. |

**What (a) adds.** When the last probe found the environment ready, this computer's sandbox was not probed. A run can still come to it: Docker stopped, the image could not be pulled, or the dev container changed. Such a run carries `hostUnverified`, and the Codex sandbox probes itself before the first command. If the sandbox is not ready, the run fails with both reasons, and the step is blocked with them. A change to the environment setting asks for a new probe, so the hold follows the change at once.

**Tests that failed first.**
- server/environment/runner.test.ts: the facade's probe with an environment and no Codex.
- server/checksflow.test.ts: the scheduler path, where setting an environment lifts the hold.
- src/domain/environment.test.ts: the probe request on `setEnvironment`, and the Activity words.
- server/checks.codex.test.ts: a hand-over to a sandbox that is not ready runs no command.

**Lesson (proposed check).** A probe must test the same route as the work it gates. Where a router exists, the probe calls it; a test gives the router an input for each route and asserts the probe's answer.

## B-04: nothing swept the environment's leftovers

**Defect.** A service that stopped mid-step left the environment's containers, its networks and its work folders. Housekeeping knew only the recorder's container names.

**Root (design, and a check that missed it).** E1 and E2 added names, networks and folders, and the sweep's name pattern was not extended. No test tied a container's name to the sweep.

**Options for "this is ours".**
- (chosen) The label `orchestrator.environment`, which every container and network of the environment carries and only the service sets. The name gives the pid of the service; the label is the proof.
- Name patterns only: the same failure as before when a new kind is added.

**Options for "no live service owns it".**
- (chosen) A container or network goes when its service's pid has gone, or when it is older than any step. Three hours is longer than any step: checks have a 120-minute limit, and a capture's prepare and capture take under two hours. This service's own never go.
- Age only: a crash's leftovers would wait three hours.

**The work folders** (a step's copy in `<project>/runs/`, the probe's in `.probe/`, a prepare being kept in `prepared/.tmp-*`). A container that still runs could swap a folder of the copy for a link (review finding 4 of E1). So a folder goes only when it is older than three hours and Docker lists no container of the environment after the sweep's own removals. While a run is live, its folders wait for a later sweep. Without Docker on the computer, no container can mount them. When Docker does not answer, they stay. A link is never followed or removed.

**Tie of names to the sweep.** `ENV_KINDS` and `RECORDER_KINDS` list every kind the service names. A test makes a name of each kind with the service's own functions and expects the sweep to find it. A new kind is covered at once. The stand-in run test checks that a live run's folder is one the sweep looks for.

**Tests that failed first.** server/housekeeping.test.ts, "the project environment's leftovers (B-04)": the sweep by label, the order, the folders, links, the tie, and Docker's network time (it has fractions of a second). A real Docker test (server/environment/environment.docker.test.ts) makes a labelled container and network with a dead pid, an owner's container and an old work folder: the first three go, and the owner's stays.

**Lesson (proposed check).** Every resource kind a service names comes from one exported list, and the clean-up's test iterates that list.

## B-32: the recorder ran as a fixed user

**Defect.** The recorder's containers ran as user 10001 with bind mounts. On a Linux host a bind mount keeps its folder's owner (this computer's user, mode 0700), so the container likely could not write its output, and the service could not remove what it wrote. Colima maps every user, which hid it on the Mac. Commit 2868c70 fixed the same defect in the environment.

**Root (a check that missed it).** Every container proof ran on Colima.

**Choice.** One rule for every container with bind mounts: `envUser` (environment/docker.ts), this computer's user, 10001 only when the service runs as root. The recorder's home tmpfs takes the same uid and gid. The image's user 10001 stays for the root case.

**The image: no new tag.** Nothing in the image needs user 10001: its files are readable by every user, and HOME is a tmpfs that Docker gives to the run's user. Measured on this Mac with `orchestrator-recorder:2` and the new arguments:
- the container runs as `uid=501 gid=20`, writes its output folder and its home, and the service removes what it wrote. Group 20 is "dialout" inside the image; the container has no device of the host, so the group gives nothing (the probe checks `/dev`);
- the real tests pass: the recorder's probe (server/studio/container.test.ts, 20 of 20), VHS recordings with Chromium, the hostile tape included (server/studio/terminal.test.ts, 27 of 27), and the captures of evidence on both paths (server/studio/evidence.container.test.ts, 9 of 9).

Only a comment in docker/recorder/Dockerfile changed. A build of the changed file has the same layers, user, entrypoint, command, folder and variables as `:2`; only its id differs, by timestamps. So the tag stays `:2`, and the Dockerfile now says to bump the tag when a change changes the image, not for a comment.

**Test that failed first.** The recorder's argument list must name this computer's user (server/studio/container.test.ts).

**Lesson (proposed spec line).** A container that writes to a bind mount runs as the owner of the mounted folder. Real container tests must run on a Linux host too (B-11).

## B-33: the Docker stand-in's containers outlived their tests

**Defect.** The stand-in's container process ran on after its test process was killed. Three ran for 50 minutes.

**Root (build).** The stand-in modelled one fact (a container outlives its docker command) and missed the other (nothing outlives the test).

**Choice.** The docker command passes its parent's pid (the test process) to the container, which ends, as if killed, once that process has gone. An attached docker command ends too. A real container's lifetime does not depend on the docker command, so the model stays true for the tests that kill the command.

**Test that failed first.** server/testing/fake-docker.test.ts kills a stand-in test process and expects its container to end, for an attached run and a detached one.

**Lesson.** A test double that starts a detached process must tie it to the test process.

## B-17: a note test raced a delay

**Defect.** "A note before the turn exists is held" raced a 300 ms stub delay against 10 ms polling of a log file, and failed under load. With the delay at 30 ms, it failed every time.

**Root (a check that waited on wall-clock time).**

**Choice.** The stub answers `thread/start` only when the test makes a gate file. The test sends the note, checks that it is held, then opens the gate. The same gate replaces the stub's 2-second "slow-thread" mode in two other tests. `CODEX_STUB_THREAD_DELAY_MS` and the "slow-thread" mode are gone. The tests passed five runs in a row with ten busy loops on the CPU.

**Lesson (proposed principle line).** A test controls the order of events itself; it never bets on a delay.
