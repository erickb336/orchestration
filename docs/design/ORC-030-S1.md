# ORC-030 stabilization, worker S1: the budgets and the PE

**What this is.** The design choices for four rows of the ORC-030 backlog (`docs/design/ORC-030-stabilization.md`): B-02 with decision D-3, B-03, B-06 and B-18. Each section gives the defect, its root, the options, the choice and the test that failed first.

**Where it fits.** ORC-030 step 2 fixes the backlog at the root. These four rows are about money and the PE: the building budget's stop, the PE's estimates, and the PE's review in the studio.

## B-02 and D-3: a paused Codex run stopped the factory

**The defect.** Every real Codex run that was paused recorded no usage (10 of 10 in `docs/real-runs/`, for example run-1038 and run-1046). The budget rule "unknown is never zero" counts a run with no recorded cost at its run limit. Codex has no run limit, so while a building budget was set, one ordinary pause held every new run. A model missing from the price table did the same.

**What the Codex adapter knows.** Codex sends `thread/tokenUsage/updated` after each model request completes, with the thread's totals. It sends nothing for a request that is cut off: an interrupt, a failure or a crash. So at the end of a run the adapter knows exactly:
- the totals of the requests that completed;
- whether it asked Codex for the turn at all (before that, no model request was made);
- whether the turn completed (if not, the last request has no report).

The adapter already passed its totals with a stop. A run paused in its first request had none, so it reported nothing, and "nothing" looked the same as a run the service lost.

**The root.** Design. The domain could not tell three different facts apart: "no model request", "one request with no report", and "no record at all". It treated all three as a cost with no bound.

**Options.**

| Option | What it does | Why not, or why |
| --- | --- | --- |
| a. Record the partial usage the adapter saw | The adapter reports its totals with the stop. | Already done. It does not help when no request completed, which is the observed case. |
| b. No model call is $0; a cut-off request counts at an estimate | The adapter reports zeros, and marks a cut-off request (`openRequest`). The budgets count that request at an estimate, labelled as one. | **Chosen.** It removes the root: each case has its own record, and only a cost nothing bounds still holds the stop. |
| c. The owner acknowledges the "no recorded cost" item (D-3) | A chip stays on the budget; the item comes back for a new unpriced model. | It hides the item but keeps the stop, and a new paused run would bring it back each time. |
| d. Give Codex runs a spend limit that the service enforces | The service stops a Codex run past the run limit, so an unknown run counts at the limit. | A product change (Codex runs would stop at $2), and it does not help a model with no price. |
| e. Ask Codex for the thread's usage (`account/usage/read` with a thread id) | Codex's own estimate of the thread. | Unverified: it needs a real run, and it may exist only for some accounts. |

**The choice (b), as built.**
- The Codex adapter reports usage at every end it reports: its totals, or zeros when no request completed. When the run ends before its turn completed, the usage has `openRequest: true`. A run that never asked for its turn reports zeros: it made no model request, a known $0.
- No tokens cost $0 at any price.
- Each cost with no full record counts at an estimate, never $0:
  - a cut-off request: the dearest finished run on the same model so far (a whole run has at least one whole request), or the run limit before there is one;
  - a model with no price: its tokens at the dearest price its provider has in the price list;
  - a Claude run with no usage: its run limit, its spend cap, as before.
- A cost that nothing bounds (a Codex run the service lost, or from before this fix) still holds the stop, and the stop names the run.
- The PE's budget check uses the same counted spend, so a pause no longer sends every PE call with a building cost to the owner.

**D-3.** With (b), nothing waits for the owner when every cost is counted. So the separate "no recorded cost" item in Needs you is removed, and nothing needs an acknowledgement. The budget's words (the floor, Settings and the Lock in summary) say what is estimated and why. When a cost cannot be counted, the stop is the one item, and its detail names the runs.

**What stays imperfect.** The estimate for a cut-off request is high on purpose: a whole run, not a part of one. A model with no price can cost more than the dearest known price. Both are labelled as estimates.

**Tests that failed first.** `server/runtimes/codex.test.ts` (8 tests: the stop's usage, the open request, the crash, no request before the turn) and `src/domain/spend.test.ts` ("costs the providers do not report", 8 tests, among them the real run's pause and the PE's budget check).

## B-03: the PE's estimate was never computed

**The defect.** Nothing wrote `factoryStarts[].estimate`. So the floor said "PE estimate for the rest: no estimate", its maintenance line said "The PE estimates it before the factory starts" (false), and on Autopilot every PE call that added a monthly cost went to the owner.

**The root.** Build. Pass 6 designed the estimate as a new field that a PE run at the pre-flight would fill. The build left the run out, and ORC-029 closed with it under "Not yet".

**What already exists.** The PE reviews each part of the design in the studio, and its verdict may carry a budget estimate: `buildUsd` and `maintenanceUsdPerMonth`, each a range, with a basis (`PeVerdict.budget`). The Lock in summary already shows these per part and sums them for the changes.

**Options.**

| Option | What it does | Why not, or why |
| --- | --- | --- |
| a. A PE run at the pre-flight writes the start's estimate | As pass 6 designed. | A new agent run, with its cost and its failure modes. The figure goes stale at the next Lock in, and it repeats what the PE already said per part. |
| b. Derive the estimates from the PE's verdicts on the parts | No new data, no new run. | **Chosen.** It stays current with each Lock in and each new verdict. |
| c. The owner types the estimate | A field in Settings. | The owner is not the PE, and the figure would not follow the design. |

**The choice (b), as built.**
- The parts: the approved items in force, but not a word list (the PE does not review one) and not a reproduction of the code as it is today (it exists already).
- The PE's estimate of a part: the budget on its newest verdict on that version (and variant). This is one function (`itemEstimate`), which the Lock in summary now uses too.
- **The rest of the build:** the building estimates summed over the parts that no landed work has built in this version. Work that runs or waits counts in full; landed work counts in the building spend. "Built" means landed, not "built and verified": an interface, an algorithm or a topology is never verified today, so it would stay in "the rest" for ever.
- **Maintenance:** the monthly estimates summed over all the parts (they will all run), plus the PE calls that stand.
- A part with no figure from the PE makes no total: "none for 2 of 3 parts", never $0. With no part approved, there is nothing to estimate yet.
- `FactoryStart.estimate` is removed: nothing wrote it, and the Lock in summary the start records already holds the per-part estimates.

**Tests that failed first.** `src/domain/spend.test.ts` ("the PE's estimates of the approved parts", 4 tests), `src/domain/studio/itemStatus.test.ts` ("the PE's estimate for the rest of the build", 2 tests) and `src/ui/home.test.tsx` (the floor's two budget tests).

## B-06: no way to ask the PE again

**The defect.** When the PE's runs on a version ended twice without a verdict, its review ended ("no-review"), and the owner had no action to ask the PE again. The same was true after "no enabled provider could run the next step" ("no-provider"), even once a provider was enabled again.

**Does the artifact stay stuck?** No. A review that ended goes to the owner, who can mark the version and approve it without the PE (there is no objection to overrule). But it then has no PE review and no estimate, so B-03's sums say "none for 1 of N parts", and the only other way to a review is a new version in a new round.

**The view's "No verdict" state.** It could not be reached: while the review waits and no PE run is under way, the service always asks again (`peRunDue`). The real end state is "PE review ended: the PE's runs on it ended 2 times without a verdict". The unreachable branch is removed.

**The root.** Design: this end state got words, not an owner action ("Not done here" in the pass 3 design).

**Options.**

| Option | What it does | Why not, or why |
| --- | --- | --- |
| a. One owner command, `askPeAgain` | The version waits for the PE again; the service asks for the run on its next cycle, through the existing path (`askForPeReviews`). | **Chosen.** One rule decides when the PE runs, and the run gets the usual retry. |
| b. The command starts the PE run itself | `requestStudioRun` from the command. | A second path to the same run, and a refusal (no provider) would be a command error, not the recorded end the service already writes. |
| c. The service retries for ever | No end state. | A broken PE would run, and spend, without a limit. |

**As built.**
- `askPeAgain { artifactId, version }`: a client command, so the owner's (the lead sends no commands). Only for the newest version, whose review ended with no verdict because the PE could not answer (no-review or no-provider). It is refused for any other version or end, and when the review still could not go on (its round closed).
- It records `askedAgain: { at, runsBefore }` on the version and clears a recorded end. The PE's runs before the ask no longer count toward "no-review", so the PE gets two runs again.
- The studio's PE panel says "You can ask the PE again." and shows the button "Ask the PE again".

**Tests that failed first.** `src/domain/studio/runs.test.ts` (2 tests: the ask and the second "no-review"; the refusals) and `src/ui/studio/studio.test.tsx` (2 tests: the words and the button).

## B-18: pruning the decisions record dropped PE calls

**The defect.** Past 2,000 decisions, the record drops decided decisions of settled tasks, oldest first. A PE call that stands is one of them, but the budgets still count it: its monthly cost is in the maintenance estimate, and an unrun fix commits building cost. Dropping it made the estimate fall.

**The root.** Design: the cap's rule ("a repair or the gate may still read it") did not know the budgets read the record too.

**Options.** (a) Never drop a PE call that stands; the cap yields, as it does for open decisions. (b) Fold dropped calls into a running total on the project. **Chosen: (a).** It needs no new state, and the predicate is the one the budgets use (`isStandingPeCall`), so the two cannot drift apart. PE calls are few beside review findings, so the cap still holds the record near its limit.

**Test that failed first.** `src/domain/orc013.review.test.ts`: "the cap never drops a PE call that stands" (the call was dropped, and the estimate fell from $30 to $0 a month).
