# ORC-024: Principles in every flow

## Task identity

- ID and title: ORC-024. Every stage's agent gets a few short working principles that fit its job, adapted from pstack. One of them, "attack the premise", switches on by itself when a repair keeps failing the same check.
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: **In progress, P1.** In the owner's words:
  - "these principle skills are very useful concepts";
  - "I am more interested in these principles we can apply to this project";
  - "Let's keep this shared set for V1".
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

**The problem.** Each agent today gets a generic role description, the task's spec and its inputs. The judgment that makes work good is left to each model's defaults, for example:

- compare options before designing something new;
- fix the root cause;
- the smallest change;
- prove it works;
- stop patching when fixes keep failing.

pstack (Lauren Tan, MIT) writes this judgment down as short principles, each with "apply when" and "don't apply when".

**The outcome:**

- **15 shared principles.** They live as short files in `principles/`, adapted from pstack with credit.
- **Each flow step names the ones that fit it.** The service adds them to the agent's instructions, under a size cap.
- **"Attack the premise" switches on by itself** for a repair round that follows a round that failed the same way.
- **Each run records which principles it was given.** The task page and Settings show them.
- **The same text goes to Claude and to Codex.**
- **The agents that build Orchestrator follow the same files,** through AGENTS.md.

## Scope

### The files

- **`principles/<id>.md`, one per principle.** The frontmatter carries:
  - `id`, which is the file name;
  - `name`;
  - `applyWhen`: one line;
  - `source`: `pstack principle-<name>, MIT, Copyright (c) 2026 Lauren Tan, github.com/cursor/plugins at 12d587d, adapted`.
- **The body is at most 200 words.** It keeps the rule, when it does and does not apply, and when to stop. Tool-specific instructions, sub-agents and links to other skills are removed or rewritten (another principle is named in plain words). The voice is plain and literal (PRODUCT.md).
- **`principles/LICENSE-pstack`** holds the MIT license text.
- **`principles/README.md`** covers what principles are, how to change one (edit the file, run `npm test`), and the credit.
- **The source texts** are pstack at commit `12d587dfb20741cafc376c42c696c5f6e2a64487`, `pstack/skills/principle-*/SKILL.md`.

### "Attack the premise" switches on by itself

- **When.** A repair step gets it when it is about to run a round after the first: a loop iteration `-i<k>` with `k ≥ 2`, a check-round fix `-r<k>-fix` with `k ≥ 2`, or Design S3's next iteration. It also needs the gate to have failed the same way again:
  - a check that failed in the round before the previous repair still fails in the round just before this one (same check name); or
  - a finding comes back: same file and the same normalised title, open in this round's inputs and also in the previous round's.
- **What it records.** The run records it with a reason, for example "added: check `test` failed again after S3" or "added: the finding "Invite links are not scoped to the trip" came back after S3".
- **When not.** A first repair, or a later round whose failures are all new, does not get it.

### What the agent receives

- **A section after the role brief and the spec.**
  ```
  ## Principles for this step
  These describe how the owner wants this kind of work done. Apply each one where its "apply when" fits your task. They never change the specification.

  ### Exhaust the design space
  Apply when: <applyWhen>
  <body>
  ```
- **A cap.** The section is at most 1,000 words. If a step's set would pass it, the principles that do not fit are listed by name and "apply when" only. A test proves that no built-in step passes the cap with the 15 as written.
- **The lead's runs** get the same kind of section with the lead's set.

### Records and UI

- **The run's record.** Its snapshot gains `principles: { id: string; hash: string; added?: string }[]`, written at dispatch. The hash is the SHA-256 of the file's body. `added` is the automatic reason. Older runs have none.
- **The task page.** Each step shows "Principles: Exhaust the design space · Experience first" (muted). A run that had an automatic one shows "+ Attack the premise (added: …)".
- **Settings → Flows** shows each step's principles in its read-only step list.
- **Settings gains a read-only "Principles" card.** It lists the 15, each with "apply when", the credit to pstack, and how to change one.
- **The README.** One sentence in "How it works" says that each stage also gets a few working principles, adapted from pstack (MIT).
- **AGENTS.md.** One line under Implementation: agents working on this repository follow the principles in `principles/` that fit their work, the same text Orchestrator gives its agents.

### What does not change

- How stages run, flows' shapes, artifacts, delivery and checks are unchanged.
- **Tasks created before ORC-024** keep their copied steps without principles. Their runs get none, and nothing claims otherwise.
- **The flow hash** covers the new field, so new tasks record new hashes.
- **There is no state migration.** The new fields are optional.

**Excluded:**

- A project's own principles (the owner chose one shared set for v1).
- Turning principles off in the UI.
- Measuring their effect.
- Principles for checks steps.
- Native sub-agents in workers.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Files in the repository, named per flow step, added to the envelope; one automatic trigger from recorded loop data | Consistent judgment where it matters; Claude and Codex get the same | Small–medium | Longer instructions; the effect is unmeasured until real runs | High (remove the field or the files) |
| B | Rely on each provider's native skills (Claude skills, Codex skills) | Less code | Small | Unequal across providers; no record of what an agent had; no structural trigger | High |
| C | Write the judgment into the role briefs | Simplest | Small | Every step of a role gets everything; no triggers; hard to change one rule | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: the owner, on the set and on one shared set for v1. The lead chose the mechanism.
- The owner's direction, 2026-10-01:
  - "these principle skills are very useful concepts" (citing exhaust the design space and attack the premise);
  - "Let's first look at the starting set of principles and when to apply";
  - "I think Migrate callers, then delete legacy APIs could work in any repair cycle no?" (added: to implement, fix, repair and code review, internal code only);
  - "Let's keep this shared set for V1".
- **Uncertainty.** How much principles change agents' work is unmeasured until real runs. The cap and the 200-word bodies keep the cost of being wrong small.

## Acceptance and validation

- **The files.**
  - 15 files with valid frontmatter, each body 200 words or less, and the id equal to the file name;
  - `LICENSE-pstack` present;
  - every `source` names pstack and the commit.
- **The mapping.**
  - Every built-in, internal and check-round step carries exactly the principles in the table above (a test pins the table).
  - Every named id exists.
  - The flow schema accepts `principles` and rejects unknown ids.
- **The envelope.**
  - The section appears with the exact header and wording, in table order.
  - The cap holds for every built-in step.
  - A step with none has no section.
  - The lead's runs carry the lead's set.
  - Claude and Codex envelopes are identical.
- **The automatic trigger:**
  - It is added for a same-check failure in round 2.
  - It is added for a returning finding.
  - It is added for Design S3's next iteration when the same UX finding returns.
  - It is not added for a first repair.
  - It is not added when every failure is new.
  - The recorded reason names the check or the finding.
  - A mutation check is done on the condition.
- **The records.**
  - The snapshot lists the principles with their hashes and any `added` reason.
  - The task page and Settings show them.
  - Older runs show none.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build`;
  - `node scripts/real-run-test.mjs --fake`;
  - an independent review;
  - a browser pass by the lead (task page, Settings; light and dark; 375 px).
