## Problem and outcome

**The problem.** About twenty milestones each added their own panel, chip or setting, and nobody designed the whole. The inventory (`evidence/ui-audit-2026-10-01/inventory.md`, 86 screenshots) found:

- **Counts:** about 300 controls on 13 screens.
- **Settings:** one 7,000 px page with 117 controls.
- **The task page:** up to 60 controls, and up to 6,000 px tall.
- **"Needs you":** shown in 10 places, worded four ways.
- **Task states:** about 25 different labels.
- **"Simulated":** said in five different styles.
- **Developer internals:** run ids, revision numbers and graph notation sit in the main view.

**The outcome.** A product shaped around how the owner works:

- autopilot by default;
- talking to one lead;
- reviewing results, not code.

Its rules:

1. **One place for each thing.**
2. **What you do daily comes first;** the rest is a click away, under Details or Advanced.
3. **One word for each idea.**
4. **Plain words, not internals.**
5. **The demo says "simulated" once per thing.**

### Dark only (r2)

The owner, 2026-10-01: "can we have dark mode like shown in the audit be the default and only option".

- **One dark palette,** taken from the audit page: near-black, cool-cast surfaces, light text, and the same four state colours.
- **No light theme and no system switch.** The first paint is dark (`color-scheme` and `theme-color` meta).
- **The demo bar is inverted** (light), so it reads as "not the product".
- **The README images** are retaken dark in pass 8, along with the hero frame.

### A component kit (r3)

The owner, 2026-10-01: "we can also have a component library so UI things are consistent throughout the app".

- **Where:** `src/ui/kit/`, with one small component per role. That covers:
  - Button (primary, secondary, quiet, danger);
  - Chip and StatePill (tones: work, you, done, fail, neutral; one "simulated" chip);
  - Card (title, count, actions), Banner (you, info, fail) and Row (title, meta, actions);
  - Field with Input, Textarea and Select (label, hint, error);
  - Disclosure (Details) and Confirm (in-page, replacing `confirm()`, P8);
  - Tabs and SegmentedControl, SideNav (Settings sections), StepList, EmptyState and Toast.
- **One type and spacing scale** in the tokens (C5). The kit uses only tokens, and screens use only the kit for these roles.
- **A test fails on inline font sizes and colours in screen files,** so drift is caught by a check, not by review.
- **A gallery route, `#/kit`,** shows every component in every state on the dark theme. It is not in the navigation, and the README's Development section names it.
- **It is built before the screen passes,** which rebuild their screens from it.

- **The README's images** (hero, tour, Overview, board) are retaken dark, and the README text is updated to the new words and screens. This is the last pass.

## Options and tradeoffs

| Option | Approach | Benefit | Cost and risk |
| --- | --- | --- | --- |
| A | Passes, each its own pull request: words and fixes first, then screen by screen, then code | Each pass is reviewable and testable; the words settle before the screens | Several pull requests; screen passes wait for pass 1 |
| B | One large rewrite | One change | Unreviewable; high regression risk |
| C | Code cleanup only | Small | Leaves the UX the owner asked to fix |

## Decision

- Selected option: A.
- Decided by: the owner chose the audit-first approach and marked the items; the lead chose the passes.
- Rationale: it follows the owner's UI-first preference. The target screens were shown first; the backend changes only where a screen needs it.
