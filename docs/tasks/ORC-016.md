# ORC-016: Pipeline patterns instead of an editable pipeline

## Task identity

- ID and title: ORC-016, pipeline patterns: a curated catalog of pipelines defined as JSON files and chosen per task, instead of a pipeline edited in the UI
- Author and timestamps: Lead (Claude), 2026-09-30
- Status, priority, and priority rationale: Completed, P2. The user asked for it "as a follow up once these last tasks are completed". It removes a large, fragile editing surface, and it is the base for comparing patterns later (ORC-018).
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-30
- Technical design: `docs/design/ORC-016-design.md`

## Problem and outcome

The user's request, verbatim:

> "lets remove the editable pipeline (as a follow up once these last tasks are completed) I don't want the pipeline to be configurable maybe we can create different configurations with different patterns to select from but it seems flaky to use UI for editing the pipeline"

Later directions from the user, in the same conversation:

- "Yeah the model and provider should be configurable."
- "pipeline editing should be done through code maybe as templated json config files or something like that"
- "I want to eventually experiment with different patterns"
- "We should not be afraid of using existing open source tools here."

Observed, from a read of `main` at `4096d49` (state format 14):

- **The editor can change everything.** `src/ui/PipelineEditor.tsx` (539 lines) edits a task's pipeline and the project's templates:
  - it adds, removes and reorders steps;
  - it sets each step's purpose, role, dependencies, inputs, outputs and run-if conditions;
  - it sets the review gate, parallel agents (2–5, copies or best of N, alternating providers), repeats (`iterate`), and waiting for child tasks;
  - on Checks steps, it sets what a failure does and which check commands run (`checks.only`).
- **Saving a running pipeline is intricate.** `setPipeline` keeps unchanged steps, revalidates changed steps and everything downstream, and stops their runs. It keeps pins by step ID, refuses reused IDs of removed steps, refuses changes to a step already split into parallel copies, and syncs copies with their leader. Each rule has its own tests.
- **Templates are editable too.** Settings → Workflow templates offers Edit, Duplicate, Reset, Delete, New template and Restore. Custom templates and edited built-ins live in `project.templates`.
- **Some features are reachable only by editing.**
  - Best of N and parallel copies.
  - Gates on single steps.
  - Per-step `checks.only`.
  - Loops (`iterate`), conditions (`runIf`) and waiting for child tasks, except in the shapes the built-in templates already have.
- **Model choice per step is a project rule.** `AGENTS.md` says: "Provider/model choice must be configurable per workflow step, with project role defaults and task/step overrides." The step pins already live on the task page, outside the editor.
- Uncertainty: no bug report names a failure of the editor. The evidence is the user's judgement and the size of the surface above.

Outcome:

- **You choose, you do not build.** Every task runs one pattern from a curated catalog: Change, Feature, Bug fix, Investigation, Design, Goal, and a few labelled variants. Each pattern says when to use it and shows its steps before you choose it.
- **Patterns are code.** Each pattern is one JSON file:
  - built-in patterns are in the repository, under `patterns/`, and change through ordinary commits and reviews;
  - your own patterns go in `~/.orchestration/patterns/`, and Reload picks them up without a rebuild;
  - a variant can be two lines: `extends` another pattern and change one step.
- **Models stay configurable.** These do not change:
  - the provider and model pin on each step, on the task page;
  - task role overrides;
  - project role defaults.
- **Experiments are cheap and recorded.** A pattern can be marked experimental, with its hypothesis. Every task records which pattern it ran (id, content hash, source). From now on, every finished or cancelled task also records its outcome: time, runs, tokens and cost, repair rounds, findings, checks and coverage. A later comparison view (ORC-018) can then be built on that data.

## Scope

Included:

- **A catalog of patterns, in files.**
  - `patterns/*.json` (built-in), validated against `patterns/pattern.schema.json` (JSON Schema 2020-12).
  - `~/.orchestration/patterns/*.json` or `*.jsonc` (yours). A file with the same id as a built-in replaces it, and is marked "yours". Your files may contain comments and trailing commas.
  - `extends` plus `stepOverrides`: a variant changes fields of existing steps, and `null` removes an optional field. No parameters, no expressions, no code.
  - Optional `experimental: true`, with a required `hypothesis`.
- **The proposed catalog** (design §3.6):
  - Standard: Change (the default), Change reviewed by the other provider, Feature, Bug fix, Investigation, Design, Goal.
  - Pauses for you: Feature with a pause after design, and Goal with a review of the plan before child tasks start.
  - Experiments: Change with the best of two implementations, and Change without the lead's final verification.
  - Not offered: "Quick change (no separate review)". It would skip the independent review that `AGENTS.md` and `TEAM.md` require. The lean experiment tests the cheaper Change while keeping that review.
- **Service-owned pipelines stay in code**: Revert, Delivery review and Delivery checks. Their steps are a contract with delivery code (a prepared revert, a review pinned to a commit, a check target), so no file can replace them.
- **Validation and loading.**
  - Every file is checked against the JSON Schema with `ajv`, then by the pipeline graph rules (`validatePipeline`), then by pattern rules, such as "best of N requires `experimental`".
  - An invalid file is skipped and listed with its exact error. The app still starts. When a file of yours that replaces a built-in has an error, the built-in stays in effect.
  - Patterns load at start and on Reload (Settings → Patterns). There is no file watch.
- **Where you choose a pattern.**
  - When you create a task.
  - In the lead's proposals, which name a `patternId` that is validated.
  - In breakdown items, for child tasks.
  - As a project default, used when a proposal or item names none.
  - The lead and breakdowns use standard patterns only. Experiments, patterns that pause for you, and patterns without an independent review are yours to choose.
- **Changing a task's pattern.** You can change it before the task starts, or while it is Paused. The pipeline starts over from the new pattern; work already done stays on the record, labelled, and is never reused. Changing it while running, pausing, done or cancelled is refused, with the reason.
- **Removed.**
  - The pipeline editor (`PipelineEditor.tsx`, the Edit pipeline mode on the task page, template editing in Settings).
  - The commands `setPipeline`, `saveTemplate`, `deleteTemplate` and `restoreBuiltInTemplates` from the command registry, and therefore from HTTP.
  - Custom templates. Your existing ones are saved as pattern files (see Migration).
  - `setPipeline` stays as an internal domain function, which tests use to build pipelines patterns do not offer. No command reaches it.
- **Kept on the task page.**
  - The step table, with a provider and model pin per step, Rerun and Retry.
  - Task role overrides.
  - Review every step.
  - Hold before start.
- **Migration (state format 14 → 15).**
  - Tasks, including tasks running on custom pipelines, keep their steps, state, pins and history untouched.
  - Custom templates and edited built-ins are retired from the state. At the next start they are written once as pattern files of yours, never overwriting a file.
  - Unedited built-in templates are dropped; the catalog provides them.
- **Provenance and outcomes.**
  - Every pipeline revision that applies a pattern records the pattern's id, its content hash, its `extends` chain, its source, and who chose it.
  - A `TaskOutcome` record is written once when a task is done or cancelled, from data already stored. Delivery results (landed, merged by the app or by a person, sent back, reverted) are already stored on the task, so they are derived later rather than copied.
  - Field names follow the OpenTelemetry GenAI conventions where they exist, so a later export is a mapping.
- **Docs.**
  - README: remove the pipeline-editor screenshot and its text, replace every "editable pipeline" wording, and add "Adding or changing a pipeline pattern" with an annotated example.
  - `PROJECT_SPEC.md` and the package description.
- **Scripts.** `scripts/real-run-test.mjs` writes its one-step pattern as a file of its own before starting the service. `server/testing/prSandbox.ts` names `patternId`.
- **Tests**, with mutation checks (design §17).

Excluded:

- **Dropping per-step provider and model choice.** That would need the user to change `AGENTS.md`. This spec does not do it, and the user confirmed the choice stays.
- A pattern comparison view (outcomes grouped by pattern and hash, with honest sample-size notes): a later ORC-018. The data recorded here is meant to be enough for it.
- Exporting traces to Arize Phoenix or Langfuse (a later ORC-018), and running SWE-bench Verified tasks through patterns (a later ORC-019). Nothing here sends telemetry.
- Automatic assignment, such as "try pattern B on the next N tasks of kind X". It is not trivial: it needs task kinds, and rules for the lead and for holds. The seam is the recorded `chosenBy`, which would gain `"rotation"`.
- Patterns read from a managed repository. Agents can edit those files and could weaken reviews or checks. A later option would read them only from the trusted base, as ORC-013 does for conventions, and add them to protected paths.
- Named parameters in patterns, a file watch, and a YAML format.
- A replacement for per-step `checks.only`. Patterns cannot name check commands, which belong to each project. A possible follow-up is a "final checks only" setting per command in Settings → Checks.
- Editing step structure on the task page in any form, including a per-step gate toggle.

## Options and tradeoffs

The main question is where pipelines are defined and who changes them.

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| **A (selected)** | **JSON pattern files.** Built-ins in the repository, yours in `~/.orchestration/patterns/`. Validated by JSON Schema and the graph rules, with small `extends` variants. A read-only catalog and picker in the UI. Per-step models stay on the task page. | No structure editing in the UI. Patterns are versioned and reviewed like code. A new variant is one file and a Reload. Every task records exactly what it ran, ready for comparison. | Large (about 6–8 days, five steps) | Three small dependencies. A loader and a migration to maintain. Your files can still describe a weak pipeline, which is why they are labelled and kept away from the lead unless standard. | High: patterns are additive. The editor remains in git history. |
| B | **Patterns in TypeScript only** (`templates.ts` as today), with no editor and no files | Smallest change: delete the editor and the template commands | Medium (3–4 days) | Every experiment needs a code change and a restart. There is no personal catalog. Patterns are harder to read than one JSON file. | High |
| C | **Keep the editor, behind an "Advanced" switch** | Nothing lost | Small | Keeps the surface the user called flaky, and the risks in `setPipeline` | High |
| D | **Fixed built-ins only**: no files of yours, no variants | Simplest catalog | Medium | Experimenting means forking the repository. Conflicts with "I want to eventually experiment with different patterns". | High |
| E | Defer | None | None | The editor stays | — |

How each part works:

| Question | Selected | Alternatives rejected |
| --- | --- | --- |
| File format | JSON with `$schema`, so editors complete and flag fields. Your files may also use `//` comments and trailing commas (`jsonc-parser`). Built-in files are strict JSON, because the app compiles them in. | YAML (`yaml`): a second syntax, indentation mistakes, and editor schema support needs an extension. JSON5: no better than JSONC here, and less common in editors. |
| Built-in loading | Compiled in through JSON imports, so the domain stays free of I/O and seeds and tests need no file access. Editing a built-in means a commit and a restart. | Reading `patterns/` from disk at runtime: domain code and tests would then need file access, or a second copy of the patterns. |
| Your patterns | `~/.orchestration/patterns/` (next to the database), read at start and on Reload. The same id replaces a built-in. | The managed repository (agents can edit it). A file watch (`chokidar`): half-saved files would flap in and out of the catalog. Reload is one click. |
| Reuse | `extends` one pattern, plus `stepOverrides` on existing steps; `null` removes an optional field | Parameters and templating: harder to read one file and know the pipeline. Adding and removing steps in a variant: write a full file instead. |
| Gates | Pattern variants for the common cases (after design, after the goal's plan), plus the existing per-task "Review every step" | A per-step gate checkbox on the task page: still editing the pipeline in the UI |
| `checks.only` | Not in patterns or the UI. Existing tasks keep it. | Allowing it in pattern files: check ids differ per project, so a pattern would be valid in one project and broken in another |
| Changing a task's pattern | Before start, or while Paused. The pipeline starts over; work done stays on the record and is never consumed. | Keeping done steps whose id and structure match: ids mean different steps in different patterns (S1 is design in Feature and implementation in Change), so matching saves little and risks stale results |
| Custom templates | Retired from the state, then written once as pattern files of yours at the next start | Dropping them (loses work). Keeping them selectable (keeps custom templates alive in the UI). |
| Who may use which pattern | The lead, breakdowns and the project default use standard patterns only | Letting the lead pick experiments: `AGENTS.md` allows competing implementations only when the user enables them |
| Outcome data | One `TaskOutcome` snapshot when a task settles, computed by a pure function and applied in one place in the store. Delivery results are derived later from fields already kept. | Recomputing everything later: finding decisions are pruned (at most 2,000), so their counts would be lost. A full event log or traces now: out of scope (ORC-018). |
| Content hash | SHA-256 (`@noble/hashes`) of the resolved steps, canonicalised with RFC 8785 (`canonicalize`), plus a per-file hash for each file in the `extends` chain | A hash of the file bytes only: whitespace and comments would split comparison groups |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead. These parts are the user's own decisions, recorded here:
  - **Model choice stays.** "Yeah the model and provider should be configurable." Per-step provider and model, task role overrides and project role defaults stay. Only the pipeline's structure becomes pattern-based.
  - **Patterns are files edited in code.** "pipeline editing should be done through code maybe as templated json config files or something like that".
  - **Experiments must be possible.** "I want to eventually experiment with different patterns". Hence the experimental flag, provenance and outcome records.
  - **Use open-source tools.** "We should not be afraid of using existing open source tools here." Hence `ajv`, `jsonc-parser`, `@noble/hashes` and `canonicalize`, all under permissive licences, with versions pinned.
- Rationale and evidence:
  - A removes the editor and the four commands that write pipeline structure, so the only way to change a pipeline's shape is a reviewed file.
  - Built-in patterns are a 1:1 transcription of today's built-in templates, checked by a test, so tasks behave exactly as before.
  - Service-created work (repairs, fixes, follow-ups, reverts, delivery reviews and checks) keeps its current shapes.
  - The catalog reaches the pure domain through the state, as the model catalog already does (`setCatalog`). Commands stay pure, and the state remains the single source of truth.
- Uncertainty and what would change the decision:
  - **Whether `tsx` and Vite import JSON** as `tsc` expects with `resolveJsonModule`. This is checked first in step 1. The fallback is import attributes (`with { type: "json" }`).
  - **Whether the user wants the lead to choose patterns that pause** (the gated variants). They are user-only for now; it is one rule to relax.
  - **`checks.only` removal.** If the user misses it, the per-command setting in Settings → Checks is the follow-up.
  - **The OpenTelemetry GenAI conventions are still marked "Development".** Attribute names are re-checked against the version pinned when ORC-018 exports traces.
- User override: none yet.

## Acceptance and validation

- **No structure editing.**
  - The task page has no Edit pipeline, and Settings has no template editing.
  - `POST /api/commands` with `setPipeline`, `saveTemplate`, `deleteTemplate` or `restoreBuiltInTemplates` is refused as an unknown command.
  - `createTask` ignores any `steps` a client sends.
- **Model choice unchanged.** A step's provider and model can still be pinned and reset on the task page, and task role overrides and project role defaults still apply, in the same resolution order.
- **The catalog.**
  - New task, the task page and Settings → Patterns show each pattern's name, description, when to use it, its flags (experimental with its hypothesis, pauses for you, yours), and a read-only list of its steps.
  - Settings → Patterns lists load errors with the file, line and column, and offers Reload and the project default.
- **Your patterns.** Dropping a two-line variant into `~/.orchestration/patterns/` and choosing Reload adds it without a restart.
  - An invalid file is listed and skipped.
  - When an invalid file of yours replaces a built-in, the built-in stays in effect.
  - A task created before the file changed keeps its steps and its recorded hash.
- **The lead's choices.**
  - A proposal with a valid standard `patternId` gets that pattern, and one without gets the project default.
  - An unknown, experimental, pausing, unreviewed or service pattern is rejected with the list of valid ids.
  - A legacy `templateId` is read as `patternId`.
  - Breakdown items follow the same rules and never get a pattern that breaks down again.
- **Changing a pattern.**
  - Before start, the pattern is replaced. A pin is kept on a step with the same id and role; any other pin is dropped and listed.
  - While Paused, every step starts over and the task stays paused.
  - While running or pausing, the change is refused with the reason.
  - A result from a run that started before the change is discarded.
  - Artifacts from before the change are labelled "earlier pattern" and cannot be edited.
- **Migration.**
  - A format-14 database with a custom template, an edited built-in, and a task running on a custom pipeline opens at format 15.
  - The running task finishes with its steps, pins and history unchanged.
  - Both templates appear as files of yours at the next start, and an existing file is never overwritten.
- **Outcomes.**
  - A task that finishes or is cancelled after the upgrade has exactly one outcome record, with its pattern id and hash, runs by role and provider, tokens (cost where the provider reports it), repair rounds, findings by severity and action, decisions, checks and coverage.
  - Tasks settled before the upgrade get none.
- **Checks.** `npm run typecheck`, `npm test` and `npm run build` pass. The mutation checks in design §17 fail as listed. A browser pass on the fake runtime covers the picker, the change panel and Settings → Patterns, in light and dark, at desktop and phone width. `node scripts/real-run-test.mjs --fake` passes with its pattern file.

## Execution plan

- Branch `pipeline-patterns` from `main` after the tasks in flight when the user asked are merged. One pull request to `main`.
- Five sequential steps. Each is one implementation followed by an independent review on the other provider, and each leaves the suite green:
  1. **Catalog and creation.**
     - Pattern files, the schema, the pure resolver, the server loader, the catalog in the state, and migration 14 → 15 with the export of retired templates.
     - Every task-creation path moves to patterns, with provenance, and the lead's choices are validated.
     - The four commands are removed, with the minimal UI changes that follows from that.
     - Tests switch to the test helper and to `patternId`.
  2. **Changing a task's pattern.** `changePattern`, the stale-result guards, the artifact-edit guard, and a basic button.
  3. **Outcome records.**
  4. **UI.** The picker with its step preview, the change panel with its consequences, Settings → Patterns, and the labels for earlier patterns. `PipelineEditor.tsx` is deleted.
  5. **Docs, scripts and screenshots.**
- Recovery: each step is its own commit. Step 1 keeps behaviour identical: the built-in patterns equal today's built-in templates, which a test checks. A failed step is reverted alone.
- Hold state: none. The spec is published, not a gate.
