## Problem and outcome

ORC-001 steps are hardcoded per sample task. Steps have ordering but no defined inputs or outputs. Workers cannot know what context they receive. Repair always runs, lead planning/verification are not steps, and nothing can be added, removed, or reordered. Templates reference the sample app.

Outcome: each task has an editable pipeline. Every step declares the artifacts it produces and the upstream artifacts it consumes. Workers receive exactly the vision, spec, and declared inputs. Every run records the artifact versions it consumed, so reruns precisely invalidate downstream results. Projects hold generic, editable workflow templates that apply to any app or goal.

## Scope

Included:

- Typed artifacts (brief, design, plan, code change, review findings, verification, report, handoff), versioned per producing step and immutable once accepted.
- Step inputs referencing upstream outputs, explicit dependencies, and a run-if condition (for example, repair runs only when a review has open findings; otherwise the step is skipped).
- The lead can own steps (plan, verify and integrate) with a configurable provider/model like any role.
- Pipeline validation: unique IDs, dependencies only on earlier steps (no cycles), inputs only from upstream outputs, and conditions only on upstream findings.
- Pipeline edits create a pipeline revision with a reason. Changed or removed steps that are running are stopped. Completed steps that changed, and their dependents, are revalidated. Pinned model selections survive.
- Generic built-in templates: Feature, Change, Bug fix, Investigation, Design. Project templates are editable, duplicable, and removable. A task pipeline can be replaced from a template.
- Run snapshot records consumed artifact IDs and versions; task detail shows artifacts, producers, consumers, staleness, and a context-envelope preview per step.
- Simulated runtime produces simulated artifacts, including occasional review findings, so conditional repair is exercised.

Excluded: real artifact storage (worktrees, commits, files: Milestones 2–3), graph editor, user-created tasks (lead-created tasks arrive in Milestone 4), review → repair → re-review loops beyond one repair pass.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Typed artifact I/O: steps declare outputs and consume named upstream outputs; runs record consumed versions | Precise, auditable context; exact invalidation on rerun; works across providers | Medium–large | More configuration per step; mitigated by templates | High; data model extends ORC-001 |
| B | Shared task blackboard: every step appends notes and every worker reads all of it | Simplest mental model | Small | Context bloat and cost grow per step; no precise invalidation; harder to audit what influenced a result | Medium |
| C | Keep fixed templates; add only step add/remove/reorder | Least work | Small | Leaves worker context undefined, which blocks cross-provider handoff | High |

## Decision

- Agent recommendation: A
- Selected option: A
- Decided by: Lead
- Rationale and evidence: PROJECT_SPEC.md requires an assignment envelope with artifact references, handoffs instead of session transfer, and "upstream artifact changes invalidate downstream acceptance evidence." Only A makes those enforceable. The lead always has read access to all artifacts, which gives B's visibility without giving every worker all of it.
- Uncertainty and what would change the decision: if templates prove too heavy for small fixes, add a one-step "quick fix" template rather than weakening I/O.
- User override, if any: none

## Acceptance and validation

- The user can add, remove, reorder, and edit steps (role, purpose, dependencies, inputs, outputs, run-if) with inline validation errors, and save with a reason as a new pipeline revision.
- Invalid pipelines cannot be saved.
- Editing an active task's pipeline stops affected running steps before redispatch and revalidates changed completed steps and their dependents.
- A conditional repair step is skipped when its referenced reviews have no open findings. It runs when they do, and skipped steps satisfy dependencies.
- Each run records its consumed artifact versions. The UI shows when a completed step consumed an outdated version.
- Templates contain no app-specific content. Settings lists templates and can edit, duplicate, and delete them. A task pipeline can be loaded from a template.
- Tests cover validation, conditional skip/run, input recording, pipeline edits during runs, and template instantiation.
- Checks: `npm run typecheck`, `npm test`, `npm run build`, and a browser pass.

## Revision history

- r1, Lead, 2026-09-29: initial spec from user direction ("editable pipeline where each step creates inputs/outputs other agents can access"; "templates should be generic for a project/app goal").
- r2, Lead, 2026-09-29: decisions from independent review. A step's purpose is its worker instruction, so editing it counts as a structural change (runs stop, results revalidate) and each run records it. A run that omits a declared output is not accepted and blocks the step, with a Retry control. Step IDs are never reused within a task. Workers receive, and run-if conditions read, only the outputs of a step's current accepted run.
