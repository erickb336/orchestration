# ORC-008: Pull-request delivery, automatic review and merge, and a review-later queue

## Task identity

- ID and title: ORC-008, deliver finished work as GitHub pull requests. A pull request can be held for you or reviewed and merged automatically, and everything that has merged lands in a list you can review later.
- Author and timestamps: Lead (Claude), 2026-09-30
- Status, priority, and priority rationale: Proposed, P1. The user asked for this directly, in three messages:
  - "Can this system auto merge PRs as well"
  - "or have like a block and notify on PRs or enable auto-review and merge PRs"
  - "I want to be able to review PRs after they have been merged into main"

  Today the only delivery is a fast-forward of a local branch. Work never reaches GitHub without the user doing it by hand, which works against the user's preference for autopilot with optional human review.
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-30 (working copy). The relevant rules:
  - external publishing is a separate capability that must be switched on explicitly;
  - reviewers must not be the only approver of their own implementation;
  - the app never enters, stores or logs credentials;
  - desired state is kept apart from observed state.

## Problem and outcome

Observed. These come from read-only traces of the code and read-only GitHub queries. No model runs were made and nothing on GitHub was changed.

- **Nothing reaches GitHub.** No code pushes, opens a pull request or calls GitHub. "Delivery" means fast-forwarding a local branch.
- **GitHub's own auto-merge cannot be the safety gate.** On the user's repository it is switched off. Where it is on, `gh pr merge --auto` merges at once when only optional checks are failing.
- **The user's account can bypass the branch rules.** The ruleset on `main` lists the admin role as "always" allowed to bypass. A merge made under the user's account is therefore not reliably stopped by GitHub when the required check has not passed. The app has to check for itself and must never use the bypass.
- **A finished task can carry unreviewed code.** When the repair loop runs out, the last repair is never reviewed and the task still finishes. This was confirmed with a probe. Auto-merge must not trust "the task is done".
- **The default reviewer cannot see the change.** A Claude reviewer has only file-reading tools and gets a list of changed files, not the changed lines.
- **Follow-ups have defects that "send back" would hit.** A follow-up of a follow-up gets a duplicate ID, follow-ups copy already-expanded loop steps, and they always start held.
- **Local delivery has three defects on this feature's path.** Work integrated while delivery was off is never delivered. An unchanged "waiting" result notifies again every minute. After a blocked delivery nothing can reset the baseline.

The user's job is to let finished work flow to `main` without reading code, to be told only when something needs them, and to look over what merged whenever they like.

Outcome. Pull-request delivery is a third delivery mode, next to Off and Local branch. It is off until the user turns it on. Each finished task becomes one pull request, and the user chooses what happens next:

- **(a) Hold and notify.** The app opens the pull request, makes sure an independent agent has reviewed it, watches the checks, and tells the user once when it is ready, or when it needs them. The user merges on GitHub or with a Merge button in the app.
- **(b) Auto-review and merge.** The app merges by itself, and only when all of these are true for the exact commit being merged:
  - an independent agent review is clean, by default from the other provider than the one that wrote the code;
  - every check the repository requires has passed;
  - GitHub itself reports the pull request as mergeable;
  - the change does not touch files that control the checks.

  It respects branch protection and never bypasses it.
- **(c) Review later.** Every merged pull request, and every local delivery, lands in a Review list. Each item shows what changed, the agent review, the checks and the task it came from. The user can mark it reviewed, leave a note, or send it back as a fix or a revert through the normal pipeline. The list never blocks anything.

## Scope

Included:

- **Delivery mode.** One setting with three choices: Off, Local branch (today's fast-forward), GitHub pull requests. The two delivery modes are never on together. Turning pull requests on runs only a read-only check of the repository.
- **One pull request per task.** The pull request contains the task's final commit on a branch the app owns (`orchestration/<project>/pr/<task>-<n>`). The app pushes only to branches under that name, never forces a push, and never touches the user's branches or working copy.
- **Only the app's own commits are published.** Before any push, every commit must have been made by Orchestrator. If the work contains anyone else's commits, such as unpushed local work, nothing is pushed and the task shows why.
- **Hold and notify.**
  - The pull request opens and the user is told when it is ready: review clean and required checks passed.
  - A Merge click is tied to the commit the user saw. If the pull request changes afterwards, the click no longer counts.
  - A user's merge still has to pass GitHub's checks and rules.
- **Independent review.**
  - The task's own code review counts when it provably saw the final change, reported no open findings, and was run by a different provider than the writer.
  - Otherwise the app starts one dedicated review task for that pull request. It is an ordinary task: visible, pausable and editable, with the provider and model chosen per step. It is a review, not a second implementation.
  - The app never quietly substitutes a provider. If the other provider is not enabled, the pull request waits and says so, or the user chooses "any agent".
  - Reviewers now receive the actual changed lines.
- **Automatic merge.**
  - One pull request at a time is brought up to date with `main`, re-checked, and merged. What lands is exactly what the checks tested.
  - Other ready pull requests wait their turn and show their place.
  - There is a daily cap and a cap on open pull requests.
- **Protecting the checks.**
  - A change to CI workflow files is not pushed until the user allows it for that pull request.
  - A change to other protected files (build and test configuration, editable in Settings) is never merged automatically; the user merges it.
- **Bounded self-repair, automatic mode only.** When a required check fails, a review finds problems, or the pull request conflicts with `main`, the app creates one ordinary fix task whose result is added to the same pull request and reviewed again. At most two per pull request; after that it asks the user. In hold mode the same thing is a button.
- **Dependent tasks wait.** A task that depends on another starts only after the other's pull request has merged, so it is built on code that includes it.
- **Main is failing.** If the check on `main` fails after a merge the app made, automatic merging pauses and the user and the lead are told. It resumes when `main` is green again. After two such failures in a day it stays paused until the user resumes it.
- **Review list.**
  - A new Review page with a badge count that persists across visits.
  - "Reviewed" is set only by the user's explicit action, never by opening an item.
  - Notes can optionally be posted as a comment on the pull request. This is off by default and chosen per note.
  - Send back as a fix or as a revert creates a linked task.
  - Deliveries made before the feature was switched on are not added.
- **Truthful states.**
  - Settings and holds (desired) are shown apart from what GitHub reports (observed) and from requests in flight.
  - "Merged" appears only after GitHub reports the merge.
  - A merge already sent to GitHub is labelled as something that cannot be interrupted.
  - Simulated pull requests are labelled as simulated.
- **Pause.** A project pause stops every push, merge, comment and new review. The app keeps watching GitHub read-only, so a merge a person makes is still recorded. A single pull request can also be held on its own.
- **Interruption.** Every GitHub action is recorded before it is attempted. After a restart the app checks GitHub before doing anything again, so it never opens a second pull request or repeats a merge.
- **Credentials.**
  - The app uses the user's own `gh` and git sign-in. It never reads, stores or logs a token.
  - GitHub token variables are removed from worker processes.
- **GitHub status panel.** A read-only list in Settings of what the app found: the required checks, whether the user's account can bypass the rules, and anything that would stop automatic merging.
- **Notifications** for: ready for you, needs you, merged, closed on GitHub, check failed on `main`, GitHub sign-in needed. Each fires once per change, not once per poll.
- **The lead** sees pull requests that need attention, the unreviewed count and the user's notes, and may propose tasks. It cannot merge, push, comment or mark anything reviewed.
- **Fixes on this feature's path:** the three follow-up defects and the three local-delivery defects listed above.
- **Tests** that never touch GitHub: a local bare repository stands in for the remote, and the GitHub side is an injected fake.

Excluded:

- GitHub's native auto-merge and merge queues. The app does its own gating; a repository with a merge queue is reported as unsupported for automatic merging.
- Any use of the admin bypass, a forced push, or a direct call to GitHub's merge API.
- Automatic reverts. A revert always starts from the user's Send back.
- Squash and rebase merges. Merge commits only, so each task has one commit to show and to revert.
- Reviewing or listing pull requests that Orchestrator did not open. See "What needs you" below.
- Taking over a pull request after a person has pushed to its branch. That pull request stays held for the user.
- Committing under the user's GitHub identity.
- GitHub Enterprise hosts.
- The lead merging, sending work back, or posting comments on its own.
- Turning this on by any preset. Autopilot does not enable publishing or automatic merging.
- Merging or notifying while the service is not running. There are no webhooks and no background service; the UI says this plainly.
- ORC-009's area: lead steering, focus, deferral and priorities.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | **Safety-first.** A separate delivery record for every pull request. A dedicated review task for every pull request head, always. The strictest gate, about 20 commands and 24 "needs attention" codes. Merges without bringing the pull request up to date. | The most defensible gate, and it guards the checks themselves | Large (15–20 days) | Heavy to build, verify and tailor. Review cost is doubled even when the task's own review already covered the change. A combination that was never tested can merge. | High |
| B | **Autonomy-first.** An app-driven loop of review, repair and merge rounds, with automatic reverts and a circuit breaker. | Most failures heal without the user | Largest (about 4,000 lines) | Several risky defaults: merging with no checks, counting skipped checks as passed, automatic reverts switched on by a preset. The largest surface for races. | High |
| C | **Simplicity-first.** A pull request is another target of the existing integration step. The task's own review is the gate. One pull request at a time is updated, checked and merged. | The smallest design, and what was tested is what lands | Medium (10–12 days) | As designed it could publish the user's unpushed commits, let dependent tasks start without their prerequisite's code, and let an agent weaken the checks. No self-repair. | High |
| **D (selected)** | **C's structure with A's safety rules**, plus a small part of B. The task's own review counts when it provably covers the change; a dedicated review runs only when it does not. One bounded repair path. Pause on a failing `main`. | Small enough to build and tailor, with the strict gate and the protections | Large (12–15 days) | Merges one at a time, so throughput follows the speed of the checks. Automatic merging on the user's repository is unverified until a sandbox run. | High: off by default; every pull request can be held or closed; every merge can be sent back as a revert |
| E | **Status quo.** Local delivery only; the user opens pull requests by hand. | Nothing new to trust | None | Does not meet the request | — |

Key sub-decisions:

| Question | Selected | Alternatives rejected |
| --- | --- | --- |
| Who decides to merge | The app, after its own checks, and only when GitHub also reports the pull request as clean | GitHub's native auto-merge: off on the user's repository, and it merges while optional checks fail. Trusting GitHub alone: the user's account bypasses the rules |
| Which review counts | The task's own review when it provably covers the final change; otherwise one dedicated review task | Always a dedicated review: double cost. Only the task's review: falls back to the user whenever it does not cover |
| What is merged | The exact commit that was reviewed and checked, brought up to date with `main` first | Merging a pull request that is behind `main`: the combination is never tested |
| Failing checks, findings or conflicts | One ordinary fix task, pushed to the same pull request, at most two | Always ask the user: stalls autopilot. Unbounded repair rounds: cost and races |
| A failing `main` after a merge | Pause automatic merging; tell the user and the lead | Automatic revert: it can revert the wrong change when the check is flaky |
| Where the review-later item lives | On the task it came from, so no new collection is needed | A separate collection: more to build for the same list |
| Reverts | The service prepares the revert; a coder step completes it; it is reviewed and delivered like any task | GitHub's own revert: cannot resolve conflicts. A service-only revert: needs a new kind of step |

## Decision

- Agent recommendation: D
- Selected option: D
- Decided by: Lead
- Rationale and evidence:
  - **Two independent judgments disagreed on the winner and agreed on the result.** One scored the designs 7, 6 and 8 and chose C. The other scored them 8, 6 and 5 and chose A. Each then listed the other design's strengths as the ideas to add. Both lists describe the same hybrid, which is D.
  - **Every must-fix defect is addressed.** The two judgments listed 45 must-fix items, with much overlap. The technical design maps each one to a section and a test (§19).
  - **It matches the project's rule of one implementation and an independent review.** The pull-request review is a review. Nothing is implemented twice.
  - **The gate does not depend on GitHub alone.** This matters because the user's account can bypass the ruleset.
  - **Smallest structure that is still safe.** It reuses the integration queue, conflict handling, tasks, reviews, templates and follow-ups that already exist.
- Uncertainty and what would change the decision:
  - **The ruleset option `require_extra_approval_for_unattributed_changes` is on.** Orchestrator's commits are made under an identity that is not linked to a GitHub account, so GitHub may demand an approval from a second account. If the sandbox run confirms this, automatic merging cannot work on that repository until the user changes the option. The app detects the situation, holds with an explanation, and never bypasses it.
  - **What GitHub reports to a bypass account while a check is still running is unverified.** The app's own check of the required checks covers this either way.
  - **If merging one at a time is too slow,** "bring up to date before merging" can be switched off in Settings, which follows the repository's own policy.
  - **If dedicated reviews turn out to be frequent,** the templates should be changed so the last repair is always reviewed.
- User override, if any: none yet. The user can change the mode, hold any pull request, or turn the feature off at any time.

## Acceptance and validation

1. **Off by default.** A new or upgraded project has pull-request delivery off. Turning it on contacts GitHub only to read. A sample project and the simulated runtime never contact GitHub, and simulated pull requests are labelled.
2. **Hold and notify.**
   - A finished task produces exactly one pull request, on the app's own branch, containing exactly the task's final commit.
   - The user is notified once when it is ready, not once per poll.
   - Merge in the app merges only the commit the user saw, and only after GitHub's checks pass.
3. **Auto-review and merge.** With Codex writing and Claude reviewing, and then the reverse, a task merges with no person involved. The merge is recorded only after GitHub reports it.
4. **The gate refuses** in each of these cases, and shows the reason:
   - a required check is failing, skipped, missing, still running, or belongs to another commit;
   - GitHub's state is unknown;
   - the repository has no required check;
   - the review has open findings;
   - the reviewer is the same provider as the writer;
   - the final repair was never reviewed;
   - the change touches a protected file.
5. **Never bypasses.** No command the app runs contains the bypass, native auto-merge, force or delete-branch flags, and none calls GitHub's merge API directly. A test over the log of every GitHub command proves it.
6. **Never publishes the user's work.** A task built on unpushed user commits is not pushed.
7. **What was tested is what lands.** When `main` moves, the next pull request is brought up to date, checked again, and then merged. The review is not repeated for that update.
8. **Self-repair is bounded.** A failing check in automatic mode produces a fix task that updates the same pull request. A third failure asks the user.
9. **Interruption.**
   - A restart or a lost scheduler lease at each point (push, open, merge, comment) leaves exactly one branch, one pull request, one merge and one comment.
   - A project pause stops all writes while observation continues.
   - A merge already in flight is recorded with its real outcome.
10. **People on GitHub.**
    - A pull request merged by a person is recorded as merged by a person and appears in the Review list.
    - A closed pull request is never reopened or pushed to again.
    - A pull request a person pushed to stays held.
11. **Review list.**
    - Merged pull requests and local deliveries appear, unreviewed, with the summary, the agent review, the checks, the task link and the changes.
    - Mark reviewed, notes, and Send back as fix or revert all work.
    - A revert, once merged, restores the earlier files.
    - Opening an item never marks it reviewed.
    - The list never delays a task, a pull request or a merge.
12. **Dependent tasks** start only after the prerequisite's pull request has merged, and their workspace contains its code.
13. **Credentials.** No token appears in state, events, logs or error messages. Worker processes do not receive GitHub token variables.
14. **Existing behaviour.** Local delivery's safety tests still pass. A format 9 database migrates to format 10.
15. **Checks and evidence.**
    - `npm run typecheck`, `npm test` and `npm run build` pass.
    - A browser pass covers the Review page, the Settings delivery card and a task's delivery card, in light and dark themes and at 375 px.
    - Mutation checks: reverting each key guard makes a test fail.
    - A real run on a throwaway GitHub repository, only with the user's consent, records evidence for hold mode, automatic mode, the bypass question, the unattributed-changes rule, a revert, and a restart during a merge.

    Pull-request delivery is labelled "not verified against GitHub" until that real run has passed.

## Execution plan

- **Branch and integration.** Branch `pr-delivery`. The lead is the single integration owner. Merge into `main` through a pull request after CI and an independent review.
- **One implementation per step, then an independent review.** The three steps run in sequence and build on each other. There are no competing implementations.
  1. **Foundations and the Review list for local delivery.** The data model and migration, the follow-up and local-delivery fixes, the prepared revert, the changes viewer and the Review page. This step writes nothing to GitHub. It delivers (c) for the delivery mode that exists today.
  2. **Pull requests, hold and notify.** The GitHub connection and its fakes, the read-only repository check, push and open, observation, the user's Merge, holds, close and deliver again, recovery after interruption, waiting dependents, and the Settings and task views. It delivers (a).
  3. **Independent review and automatic merge.** Review coverage, the dedicated review task, the automatic gate, bringing a pull request up to date, bounded repair, the pause when `main` fails, the lead's view, and the sandbox evidence script. It delivers (b).
- **Fixed interfaces**, published before step 1 starts. The technical design is authoritative (§3, §5 and §7): the new types, the command names and arguments, and the `GitHubHost` interface that tests replace with a fake.
- **Files.** The technical design lists the files each step touches (§18). New logic goes into new files where possible: `src/domain/delivery.ts`, `server/github.ts`, `server/prdelivery.ts` and three new UI files. Existing files get small hooks.
- **ORC-009 sequencing.** ORC-009 is built next on the same branch. ORC-008 takes state format 10, and ORC-009 renumbers its migration to 11, as its spec already provides. ORC-008 adds nothing to the autonomy settings and nothing to the lead's reply contract. ORC-009 leaves integration and delivery state alone.
- **Workspace.** This repository. SimpleApps and other managed repositories are not modified. The uncommitted edits to AGENTS.md, README.md, PROJECT_SPEC.md and TEAM.md are preserved.
- **Checks per step:** `npm run typecheck`, the step's own test files, then the full suite before hand-off.
- **Effort checkpoint.** Re-estimate after step 2. If the remainder exceeds about five days, bounded repair moves to a follow-up task. The gate, the dedicated review and the pause on a failing `main` stay.
- **Recovery.** A stalled or failed run is stopped and re-run as a new attempt from its committed branch state. A change of provider is a new run, not a resumed session.
- **Hold state.** None. This spec is published, not gated. The user may pause, edit or cancel it at any time.

What needs you (nothing here blocks the start of the work):

- **A throwaway GitHub repository and your consent** for the real evidence run at the end. Nothing real is pushed or merged before that.
- **Your ruleset may block automatic merging.** "Protect main" has `require_extra_approval_for_unattributed_changes` on. If the evidence run shows pull requests stuck waiting for an approval, the fix is a setting only you can change.
- **Your account can bypass the rules on `main`** (admin, "always"). The app never uses this. Narrowing it is recommended and optional.
- **"Allow auto-merge" is off on your repository. Leave it off.** The app does not use it.
- **A question.** Should the Review list also show pull requests merged into `main` that Orchestrator did not open? This revision covers only the app's own work.
