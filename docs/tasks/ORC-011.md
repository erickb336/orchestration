# ORC-011: Guided setup and one-command start

## Task identity

- ID and title: ORC-011, guided setup (`npm run setup`) and one-command start (`npm start`, or `orchestrator` from anywhere)
- Author and timestamps: Lead (Claude), 2026-09-30
- Status, priority, and priority rationale: Completed, P1. The user asked: "Can we create an easier process for starting the app and setting up."
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-30

## Problem and outcome

Observed:

- **Starting takes several steps.** Starting with real agents means remembering `ORCHESTRATION_RUNTIME=real`, exporting credentials in every new terminal (`ANTHROPIC_API_KEY`, or `ORCHESTRATION_CLAUDE_AUTH` plus `CLAUDE_CODE_OAUTH_TOKEN`), running `npm start` from the project folder, and opening the browser by hand.
- **Mistakes stay silent.** A forgotten variable leaves the app in demo mode or leaves Claude "not configured".
- **Codex-only use needs manual changes.** Running on Codex alone means editing five role defaults and the lead by hand.

Outcome:

- **Setup, once.** `npm run setup` asks a few questions and saves the answers.
- **Start, every time.** `npm start`, or `orchestrator` from any folder, then:
  - starts with those answers;
  - finds the Claude credential in your environment or your macOS Keychain;
  - says plainly what it is using;
  - opens the browser.

## Scope

Included:

- **`scripts/orchestrator.mjs`: one command with `setup`, `start` (the default), `status` and `help`.** It is registered as the package's `orchestrator` command, so `npm link` puts it on the PATH.
- **`npm run setup`, which asks and checks:**
  - It checks Node ≥ 22.13, git, and installed dependencies (offering to run `npm install`).
  - It asks for real agents or the demo.
  - **Codex:** it reports the sign-in state (`codex login status`) and offers to run `codex login`.
  - **Claude**, one of:
    - an API key;
    - your own subscription token (opt-in, personal use, with Anthropic's rule quoted);
    - cloud credentials already in your environment;
    - Codex only.
  - **Credentials in the Keychain (macOS):** it offers to store the API key or token in the macOS Keychain. You type the value into macOS's own hidden prompt (`security add-generic-password … -w`), so the script never sees it or writes it anywhere.
  - It offers the `orchestrator` command through `npm link`.
  - It saves non-secret answers to `~/.orchestration/launcher.json`.
- **`npm start` and `orchestrator start`, in this order:**
  1. Read `launcher.json`. With no file, it starts the demo and suggests setup, as `npm start` does today.
  2. Resolve the Claude credential. An environment variable wins; otherwise the Keychain is read at start and passed only to the service process.
  3. Build.
  4. Start the service.
  5. Wait until the service answers.
  6. Open the browser (`--no-open` skips this).
  7. In Codex-only mode, apply Codex as the lead and every role default once.
  8. Print a short line on what is being used.

  An explicitly set environment variable always overrides a saved answer.
- **`orchestrator status`:** saved answers, credentials found (never their values) and the Codex sign-in, without starting anything.
- **README:** Install and Running real agents are rewritten around setup and start.
- **Tests** for the pure parts: settings validation, credential resolution order, the environment given to the service, and the Codex-only commands.

Excluded:

- Storing any secret in a file.
- Windows credential stores. Outside macOS, credentials stay environment variables.
- A background service or login item. The app still runs only while its terminal is open, as documented.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Interactive setup that saves non-secret answers; Keychain for secrets on macOS; one start command | One-time setup; `npm start` just works; no secrets in files or shell history | Medium | macOS-specific convenience; the Keychain read needs the user's approval on first use | High: delete `launcher.json` |
| B | A `.env` file that setup writes, including secrets | Simplest | Small | Secrets in a plain file, which the project rules forbid | High |
| C | Documentation only | None | Tiny | Starting stays error-prone | N/A |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead.
- Rationale and evidence: A makes starting a single command without ever writing a credential to disk. The Keychain keeps the value out of files and shell history, and the service still receives it only as an environment variable, as today.
- Uncertainty and what would change the decision:
  - Whether reading the Keychain prompts on each start (macOS may ask once, with "Always allow").
  - How `codex login` behaves when run from setup. It is a browser flow, run with the terminal attached.

## Acceptance and validation

- After `npm run setup` choosing real agents and Codex only:
  - `npm start` starts real mode and opens the browser.
  - The lead and every role default are Codex, applied once.
- After choosing the subscription with the token in the Keychain, the service environment has `ORCHESTRATION_CLAUDE_AUTH=subscription` and the token. `launcher.json` contains no secret.
- An explicit `ORCHESTRATION_RUNTIME` or credential variable overrides the saved answers.
- `orchestrator status` prints no secret values.
- With no `launcher.json`, `npm start` behaves as before (demo) and suggests `npm run setup`.
- Checks: `npm run typecheck`, `npm test` and `npm run build` pass. Setup and start are also exercised non-interactively in a scratch home directory.
