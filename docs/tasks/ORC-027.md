## Problem and outcome

**Where it fits.** On 2026-10-01 the owner ran `scripts/real-run-test.mjs` with real Claude and Codex, and it passed. That was the exit run of ORC-004 (runtime adapters), and the README now says what it verified. Three gaps remain:

- **CI never runs the scenario.** `--fake` mode exists, but only people run it, so a change can break the scenario unnoticed.
- **The evidence is not committed.** It lives in the ignored `evidence/` folder on one computer. Nobody reading the repository can see that a real run happened, or what it did.
- **Notes to a running agent (ORC-022, the main feature) have never run with real models.** Both adapters still mark steering "unverified".

**The outcome:**

- CI runs the scenario against the simulated runtime on every pull request.
- One command runs it against real Claude and Codex.
- Each real run leaves a small record in `docs/real-runs/` that can be committed, with no paths or secrets.
- The scenario now also sends a note to each running agent and requires the runtime's acknowledgment.

## Scope

**Included:**

- **The scenario** (`scripts/real-run-test.mjs`):
  - After the project resumes, a note is sent to each running first step (one Codex, one Claude). A check requires each note to be acknowledged live by its runtime.
  - Whether the report then answers the note is recorded, but it is not a check: following a note is the model's choice.
  - PASSED requires every expected check, by count.
- **Commands:**
  - `npm run test:integration` runs the scenario on the simulated runtime, at no cost.
  - `npm run test:real` runs it with real agents and the caller's own credentials.
- **CI** runs `npm run test:integration` after the unit tests.
- **Committed records:**
  - A real run writes `docs/real-runs/<time>.json`: the checks, the steps, the models, the outcomes and the costs.
  - Absolute paths become `<work>` or `~`, and the service log is left out.
  - A unit test fails if any record contains a home path or a key-like string.
  - The owner's run of 2026-10-01 is added as the first record.
- **Docs:** the README (Development and Status), `docs/real-agents.md`, and ORC-022's evidence if the notes check passes.

**Excluded:**

- Running real models in CI. That would need the owner's credentials stored as GitHub secrets, and it costs usage on every pull request.
- Pull-request delivery and lead conversations with real models; each needs its own scenario.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| **A (selected)** | The existing script stays the scenario. CI runs its simulated mode; `test:real` runs it for real and writes a committed record | One scenario, two modes; real evidence visible in the repository | Small | CI takes about 70 s longer | High |
| B | Record the real providers' message streams and replay them in CI | CI exercises real-shaped provider output | Large | Pause, resume and notes depend on live timing, which a replay cannot reproduce; fixtures go stale with each SDK version | Medium |
| C | Real runs in CI, with GitHub secrets | Real evidence on every pull request | Small | The owner's credentials in GitHub; usage cost and flaky model timing on every pull request | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: the lead, from the owner's request.
- Rationale and evidence:
  - The simulated scenario already passes (72 s on 2026-10-01).
  - The real one passed for the owner the same day.
  - Committing a scrubbed record makes the evidence durable without the 80-line service log or local paths.
- Uncertainty and what would change the decision:
  - A note may arrive after a short run has already ended. The note then reads "not delivered", and the check fails truthfully.
  - If that happens often, the scenario should send the note earlier or give the step more work.
