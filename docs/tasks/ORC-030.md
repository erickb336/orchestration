## Problem and outcome

**Where it fits.** ORC-029 and ORC-031 (subagents in read-only research steps) come first. ORC-029 adds the Vision studio, PE review, budgets, the pre-flight and the factory floor over six passes, each with its own screens. This is the same pattern that, before ORC-025, left the UI with a panel per feature. The demo and the README images must show the product as it really is. So the order is:

1. Test the product.
2. Audit the whole UI and fix it.
3. Only then make the demo.

**Outcome:**

- **A QA pass.** The main journeys are run end to end, simulated and with real agents within an agreed budget, and every defect found is fixed:
  - a new project;
  - Vision rounds with PE review;
  - the blueprint;
  - the pre-flight;
  - Start the factory;
  - tasks through review and delivery;
  - change orders;
  - budgets;
  - pause and resume;
  - notes.
- **A stabilization pass, with root-cause analysis** (r3; the owner, 2026-10-02: "we will need a milestone to focus on bug fixes and rca").
  - The backlog starts from every known limit and deferred finding the reviews have recorded in the specs and design docs.
  - Each bug is fixed at its root, and classified by where the mismatch started: intent, design, build, or a check that missed it.
  - The lesson goes into principles, checks or specs, as in ORC-033's bug flow, applied to Orchestrator itself.
- **A UI audit page** the owner marks, as in ORC-025: an inventory, screenshots, findings and target screens. Then the cleanup passes, keeping one word per idea and the component kit.
- **A new demo:**
  - the story: the idea → studio rounds with PE review → the blueprint → pre-flight → Start the factory → the factory floor;
  - the tour;
  - the README's hero, tour video and screenshots, retaken with `npm run capture`.
- **A shorter README** (r2; the owner, 2026-10-02: "When we re-do the demo and update readme can we trim down the readme - it has too many details").
  - Today it is 2,469 words, about half of them in Status (1,157 words: two milestone tables and the real-model results) and 588 in How it works.
  - The target is about 600–800 words, read in a few minutes:
    - the pitch and the hero image;
    - Try the demo;
    - How it works in a few lines (Vision → PE review → the blueprint → Start the factory → the factory), with one screenshot;
    - Why I built it, with how it was made, in one short paragraph;
    - Use it on your own repository;
    - Safety in three lines;
    - Development commands;
    - Status in three lines;
    - the licence.
  - The detail moves into the docs, each linked once from the README:
    - the milestone tables go to `docs/milestones.md`;
    - the real-model results go to `docs/real-runs/README.md`, which already exists;
    - the flows table goes to `flows/README.md`;
    - stepping in (messages, notes, Pause and edits) goes to a short user guide.
