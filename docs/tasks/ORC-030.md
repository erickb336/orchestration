## Problem and outcome

**Where it fits.** ORC-029 and ORC-031 (subagents in read-only research steps) come first. ORC-029 adds the Vision studio, PE review, budgets, the pre-flight and the factory floor over six passes, each with its own screens. This is the same pattern that, before ORC-025, left the UI with a panel per feature. The demo and the README images must show the product as it really is. So the order is:

1. Test the product.
2. Audit the whole UI and fix it.
3. Only then make the demo.

**Outcome:**

- **A QA pass.** The main journeys are run end to end, simulated and with real agents within an agreed budget, and every defect found is fixed:
  - a new project;
  - Vision rounds with PE review;
  - the blueprint;
  - the pre-flight;
  - Start the factory;
  - tasks through review and delivery;
  - change orders;
  - budgets;
  - pause and resume;
  - notes.
- **A stabilization pass, with root-cause analysis** (r3; the owner, 2026-10-02: "we will need a milestone to focus on bug fixes and rca").
  - The backlog starts from every known limit and deferred finding the reviews have recorded in the specs and design docs.
  - Each bug is fixed at its root, and classified by where the mismatch started: intent, design, build, or a check that missed it.
  - The lesson goes into principles, checks or specs, as in ORC-033's bug flow, applied to Orchestrator itself.
- **A UI audit page** the owner marks, as in ORC-025: an inventory, screenshots, findings and target screens. Then the cleanup passes, keeping one word per idea and the component kit.
- **A new demo:**
  - the story: the idea → studio rounds with PE review → the blueprint → pre-flight → Start the factory → the factory floor;
  - the tour;
  - the README's hero, tour video and screenshots, retaken with `npm run capture`.
- **A shorter README** (r2; the owner, 2026-10-02: "When we re-do the demo and update readme can we trim down the readme - it has too many details").
  - Today it is 2,469 words, about half of them in Status (1,157 words: two milestone tables and the real-model results) and 588 in How it works.
  - The target is about 600–800 words, read in a few minutes:
    - the pitch and the hero image;
    - Try the demo;
    - How it works in a few lines (Vision → PE review → the blueprint → Start the factory → the factory), with one screenshot;
    - Why I built it, with how it was made, in one short paragraph;
    - Use it on your own repository;
    - Safety in three lines;
    - Development commands;
    - Status in three lines;
    - the licence.
  - The detail moves into the docs, each linked once from the README:
    - the milestone tables go to `docs/milestones.md`;
    - the real-model results go to `docs/real-runs/README.md`, which already exists;
    - the flows table goes to `flows/README.md`;
    - stepping in (messages, notes, Pause and edits) goes to a short user guide.

## Scope, options and plan

Written 2026-10-03, when ORC-029 and ORC-031 were built (the owner, that night: "lets get ORC-029, ORC-031, and ORC-030 use your best judgement and run in autopilot"). Following the owner's preference, the experience comes first: the audit page and target screens come before any cleanup code, and the owner marks the audit. So the work splits at the owner's marks:

**Before the owner's marks (on autopilot):**
1. **QA.** Every main journey, simulated, in a real browser at 1280 and 375 wide, by a script per journey (several exist: the pre-flight, the factory floor, Design and reality): a new project, a Vision round with PE review, the draft and Lock in, the pre-flight and Start the factory, a task through review and delivery, a change order with Undo, the budget stop, pause and resume, notes. Each defect becomes a backlog row. Real runs only where a journey has none yet, within the owner's remaining trial budget.
2. **Stabilization with root-cause analysis.** The backlog starts from every known limit and deferred finding the specs and design docs record (for example: the PE's estimate for the rest of the build is never computed; a sweep of what a crashed service leaves in the environment; the old Node-only evidence path; the load-sensitive tests; the "code mode" commands Codex does not report). Each fix is at the root, with a test that failed first, and each row is classified by where the mismatch started: intent, design, build, or a check that missed it. The lesson goes into a principle, a check or a spec.
3. **The UI audit page,** as in ORC-025: an inventory of every screen, screenshots at both widths, findings (one word per idea, the kit, reading order, density), and target screens, published as a private page with marks.
4. **The README trim** to about 600–800 words, with the detail moved into linked docs (`docs/milestones.md`, `docs/real-runs/README.md`, `flows/README.md`, a short user guide). The hero, the tour video and the screenshots wait for the cleanup.

**After the owner's marks:**
5. **The cleanup passes** the marks call for.
6. **The new demo:** the story (the idea → studio rounds with PE review → the blueprint → the pre-flight → Start the factory → the factory floor), the tour, and the README's images and video retaken with `npm run capture`.

**Options for Resume (the owner chose A):** A, the fresh attempt starts from the paused attempt's diff; B, start over from the base (today); C, resume the provider's own session, which needs paid real runs on both providers to prove. A keeps the work at low risk; the fresh agent reads the diff as its starting point and the record says so.

**Options for keeping the Mac awake (the owner chose A):** the service holds macOS's idle-sleep assertion (`caffeinate -i`, bound to the service's own process) while any run is active, and lets go when none is. The display may still sleep. Other systems: no assertion, and the label stays.
