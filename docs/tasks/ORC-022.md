# ORC-022: Send a note to a running stage

## Task identity

- ID and title: ORC-022. The lead sends a note to an agent while its stage is running, without pausing or restarting it.
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: **Done, P1.**
  - The owner asked for it: "That's something good to build as task 22", then "Let's build out ORC-022 now".
  - It is the main way to change course without losing work in progress.
- Specification revision: 4 (detailed design; r1–r3 were the high-level spec)
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

**Today, changing what a running stage does means stopping it.** You edit the spec, which stops the run and starts it again, or you pause the stage and rerun it. Small course corrections cost a whole rerun and lose the work in progress. Examples: "skip the README", "use the existing helper", "don't touch the migrations".

**The idea comes from running this project.** The lead sent notes to running background agents mid-task, and they adjusted without restarting.

**Outcome.** You talk only to the lead. When something you say should change work that is already running, the lead sends a short note to the running stage or stages it affects. For example, you say "have the coder skip the README, I'll write it".

- **Delivery.** The agent receives it at its next step and carries on. Its work so far is kept.
- **A record.** The note is recorded on the run and in the stage's handoff, with the message of yours that led to it, so reviewers and you see the guidance the agent had.
- **Your view.** The lead's reply lists every note it sent, like its steering changes.
- **Truthful states:**
  - **"Delivered"** only once the runtime accepts the note.
  - **"Not delivered"**, with the reason, if the run had already finished. The lead then reruns the stage with the note, or reports that it did not.

## Scope

### What a note is

- **What it says.** A short instruction (1–500 characters of plain text) for the agent running one stage of one task: a coder or a designer, for example "skip the README; the owner will write it".
- **What it is for.** It is guidance within the current spec. It never changes the spec, the pipeline, a pin or a setting.
- **Who sends it:**
  - **The lead,** when your message asks for it. This is the main path.
  - **You,** directly from the task page. This is secondary.
- **Where it goes.** It is addressed to a task and a step (`WT-007`, `S2`). The service decides which run receives it.

### The note's life (desired state apart from observed state)

| Status | Meaning | Who sets it |
| --- | --- | --- |
| `queued` | Accepted. It waits for a run of that step: either the step has not started, or its run is stopping. | Service, at send |
| `sending` | Handed to the runtime for the step's live run. Not yet acknowledged. | Service, when it calls the adapter |
| `delivered` | The runtime acknowledged it (see "Delivery per runtime"). `via: "live"` for a running agent; `via: "start"` when it was written into the instructions of the step's next run. | Adapter event, or dispatch |
| `not-delivered` | It did not reach an agent. It has a reason, such as "S2 had finished", "the run stopped first", "the runtime refused it: …" or "the service restarted before the runtime answered". | Adapter event, or service reconciliation |

- **Which run it goes to:**
  - **The step has a live run** (running, not stopping): the note goes to that run.
  - **The step has not started, is waiting for a slot, or is paused:** the note is queued and written into the instructions of the step's next run. A note never starts, resumes or releases anything: pausing still wins.
  - **The step is done, skipped or failed, or its task is done or cancelled:** the note is not delivered, with the reason.
- **A note is bound to the run it was sent to.**
  - A result for a note on another run is ignored (stale-result protection).
  - A note that reached a run is never re-sent to a later run of the same step on its own; the lead or you send it again if it still applies.
- **Restarts.** A note left in `sending` when the service restarts is marked `not-delivered` ("the service restarted before the runtime answered"). It is never shown as delivered without an acknowledgment.

### Who may send a note to what

- **The lead:**
  - Only in a reply to your messages (`run.messageIds` not empty). Planning runs never can.
  - Only to coder and designer steps.
  - Never to a review step (code, security or UX review), a checks step, or a lead step. Reviews stay independent; the reviewer sees the notes the coder had anyway (below).
  - Never to delivery tasks (the review, fix and check tasks a pull request creates), the same as steering.
  - **Child tasks of a Goal are allowed.** A note is about the running stage, not the task's priority.
- **The steering mode applies** (`project.steeringMode`):
  - `apply`: the lead's notes are sent.
  - `apply-own`: notes to tasks whose root the lead proposed are sent. Others become suggestions.
  - `suggest`: every note is a suggestion.
  - **A held change set** (you sent a newer message, or edited the vision, while the lead worked): its notes are suggestions too.
  - **Suggestions** show a **Send** button in the lead's reply, which applies them through the existing `applySteering`.
- **You** may send a note to any running agent step of any open task: coder, designer, reviewers or lead steps (not checks). It is your call. The note is labelled "from you".
- **Agents never send notes,** to each other or anywhere.
- **Limits:**
  - at most 3 notes in one lead reply;
  - at most 10 notes for one run;
  - text 1–500 characters, one paragraph (newlines folded into spaces), no control characters.
  - Over a limit: the entry is rejected with a reason, and the others still apply.

### The lead's output and the change list

- **The format.** A message run's `steer` block gains `"notes"`:
  ```json
  "notes": [ { "task": "WT-007", "step": "S2", "text": "Skip the README; the owner will write it.", "ifFinished": "report" } ]
  ```
  - `ifFinished` is `"report"` (the default) or `"rerun"`.
  - **`"rerun"`:** when the step had already finished, the service reruns it with the note written into the new run's instructions. It does so only when:
    - the task is open and not paused by you;
    - no step that depends on it has started yet;
    - the mode allows.

    Otherwise the rerun becomes a suggestion, with a **Rerun with this note** button that does the same as the task page's Rerun plus the note.
- **Each note becomes a row** in the reply's change set: `kind: "note"`, with `taskId`, `stepId`, the text in `after`, the note's id, and the usual `status`.
  - `applied` means sent. The row then shows the note's live status: queued, sending, delivered or not delivered, and its reason.
  - **Notes have no Undo.** A sent note cannot be unsent. **Undo all** skips them, and the row says so.
- **The lead's next run sees what happened.** Its envelope lists the notes of the last 24 hours: who sent each one (the lead, or you), the task and step, the text, the status and the reason. Your direct notes are therefore visible to it. Its steering rules gain the note rules above, and the open-work board lists each open task's running and pending steps (id, role, provider), so it can address them.

### What the agent receives

- **Mid-run** (Codex and Claude): exactly this text, as a user message on the running turn.
  ```
  Note from the lead, relaying the user (mid-run, <time>): <text>
  This is guidance within your current assignment; it does not change the specification. Apply it from now on, keep the work you have done unless the note says otherwise, and finish with the output block as instructed. If you had already finished, apply the note and give the output block again.
  ```
  A note from you starts "Note from the user (mid-run, <time>)".
- **At start** (a queued note): the same text, in a `## Notes for this run` section of the envelope.
- **Downstream steps see the notes the producing run had.** For example, a reviewer reading `S1.change` sees `## Notes the S1 agent received` with each note, its source and its time. A review then does not flag "the README was not updated" after you said to skip it.
- **The task page** lists a run's notes under the run.

### Delivery per runtime (the adapter contract)

`RuntimeAdapter` gains one method and one event (fixed interface, committed by the lead before the workers start):

```ts
/** Deliver a note to the live run. Must not throw; the outcome arrives as a "note" event for this noteId. */
note(attemptId: string, note: { id: string; text: string }): void;
// AdapterEvent:
| { type: "note"; attemptId: string; noteId: string; outcome: "delivered" | "not-delivered"; reason?: string }
```

- **Codex** (app-server 0.159.2):
  - It calls `turn/steer` with `{ threadId, expectedTurnId: <the run's turn id>, input: [{ type: "text", text }] }`.
  - A response is `delivered`.
  - An error is `not-delivered`, with the error's message. Examples: no active turn, a turn-id mismatch, or a non-steerable turn ("review" or "compact").
  - No turn id yet, or the run already ended, is also `not-delivered`.
- **Claude** (Agent SDK 0.3.285):
  - **The query moves to streaming input.** The envelope is the first message of an input stream that stays open while the run lasts. Notes are pushed onto it as user messages with `client_composed: true` (so `@` mentions and slash commands in the text are never expanded), a `uuid`, and `priority: "next"`.
  - **`delivered`** only when an assistant message names the note's uuid in `user_message_uuid` or `user_message_uuids`. That is the SDK's acknowledgment that the agent saw it.
  - **A turn that ends before the agent saw the note.** The note then starts a new turn on the same session: the run continues, and the run's result is the last turn's final output. The adapter completes the run only on a result with no unacknowledged notes outstanding.
  - **Ending.** The input stream closes when the run completes, stops or fails. A note to a run that has ended is `not-delivered` ("the run had finished").
  - **Unchanged:** interrupt, timeouts, the budget and turn limits, and the terminal events.
  - **To verify before relying on it:** the coder reads the SDK's code to confirm that `priority: "next"` folds a message in at the next step and that this acknowledgment arrives. If either does not hold, the adapter reports `not-delivered` with the reason, never `delivered`.
- **Fake runtime:**
  - It acknowledges a note after a short simulated delay.
  - It reports `not-delivered` if the run ended first.
  - Its acknowledgments carry `simulated: true` in the domain, and the UI labels them simulated.
- **Check runs** (the service's checks) have no agent. The service never routes a note to them.

### Commands and UI

- **Commands:**
  - `sendNote { taskId, stepId, text }`: your direct note.
  - Applying a suggested note row goes through the existing `applySteering`.
  - `rerunWithNote { taskId, stepId, noteId }`: the suggested rerun. It uses the existing rerun rules, and the note is written into the new run's instructions.
- **The task page:**
  - **A running agent step** has a small **Send a note** control (secondary styling). It opens a one-paragraph text box with Send and Cancel, and shows the limit.
  - **Under each run:** its notes, each with its source ("from the lead, for your message …" or "from you"), its time, its status chip (Queued, Sending, Delivered, Delivered at start, Not delivered: reason) and a "simulated" label in the demo.
- **The lead's reply** (Conversation and SteeringChanges): note rows read "Note to WT-007 S2 (Coder · Claude): "…"", with the status chip. Suggested rows have Send. A rerun suggestion has Rerun with this note. There is no Undo.
- **Activity feed:** one event per note sent, delivered, or not delivered.
- **Demo:** one note from the lead appears in the story, to WT-002's coder, from the steering exchange that is already there. No run is in flight when the demo opens, so it is queued and shows "Delivered at start" once the first dispatch confirms the run started. Live delivery shows when you send a note from a running stage, or tell the demo lead "tell the coder on WT-002 to …". The tour does not change.

### State

- **Format 16 → 17:**
  - `state.notes: Note[]` is added (empty for older databases);
  - `SteeringChange.kind` gains `"note"`.
  - Nothing else moves. A migration test loads a format-16 database.
- **The `Note` record:**
  - `id` (`note-<n>`), `taskId`, `stepId`, `attemptId` (the run it went to, once known) and `text`;
  - `from`: `{ by: "lead"; leadRunId; changeSetId; changeId; messageIds }` or `{ by: "user" }`;
  - `at`, `status`, `via` ("live" or "start"), `reason`, `sentAt`, `settledAt`, and `simulated?: true`.
  - Pruning: at most 2,000 notes. Settled notes of done tasks are pruned first.

**Excluded:**

- Notes that change the spec or the pipeline (a spec edit does that).
- Notes between agents.
- Notes to check runs.
- Discord (ORC-023).
- Free-form multi-turn chat with a worker.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | The lead delivers notes into running agents; queued notes go into the next run's instructions; `ifFinished: "rerun"` reruns a finished step when nothing downstream started | You talk only to the lead; course corrections keep work in progress | Medium–large: the Claude adapter moves to streaming input, the lead's output gains a change kind, and there is a state migration | The Claude adapter change touches every Claude run; how agents weigh a mid-run note is unverified until a real run | High (notes are additive; a flag could switch them off) |
| B | Always stop and rerun with the note | Simple | Small | Loses work in progress, which is the problem being solved | High |
| C | Only the next stage gets the note | Trivial | Small | Too late for the stage that needs it | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead, on the owner's request. The owner's direction:
  - "I want the lead to be able to send notes to the subagents. I only want to communicate with the lead."
  - Then: "We can have control for me to message them directly as well but main feature is lead messages".
  - Then: "Let's build out ORC-022 now".
- **Rationale:**
  - Both pinned runtimes support mid-run input: the Codex app-server's `turn/steer`, and the Claude Agent SDK's streaming input with acknowledgments.
  - A reuses steering's validation, modes, held sets and change list, so notes behave like every other change the lead makes.
- **The lead's choices in r4:**
  - **The lead may not send notes to reviewers.** This keeps reviews independent; the reviewer sees the coder's notes anyway.
  - **Reruns.** A note to a finished step reruns it only when nothing downstream started; otherwise it is a suggestion.
  - **Claude acknowledgment.** "Delivered" for Claude needs the SDK's acknowledgment, not just a write to the process.
- **Uncertainty:**
  - How agents weigh a mid-run note is unverified until a real run, and it may change the note's wording.
  - The Claude fold-in behaviour is to be confirmed in the SDK's code by the coder (above).

## Acceptance and validation

- **Live delivery.** The lead's reply to "tell the coder to skip the README" on a task whose S2 (coder) is running:
  - It creates a note row.
  - The adapter receives the note for exactly that run, and the row and the task page show Sending, then Delivered.
  - The run continues, with its work kept, and completes normally.
  - Tested on the fake runtime end to end, and per adapter with a scripted app-server and a scripted SDK.
- **Queued.** A note to a step that has not started, or to a paused task, waits. It appears in the next run's envelope and becomes "Delivered at start". It never starts or resumes anything.
- **Too late:**
  - A note to a finished step is "Not delivered: S2 had finished".
  - With `ifFinished: "rerun"` and nothing downstream started, the step reruns with the note in its envelope.
  - Otherwise the row offers "Rerun with this note".
- **Who:**
  - Planning runs' notes are refused.
  - The lead's notes to review, checks or lead steps, or to delivery tasks, are rejected with a reason.
  - The modes (`apply`, `apply-own`, `suggest`) and held sets turn notes into suggestions as specified, and Send applies them.
  - Your direct note works on any running agent step except checks.
- **Truthful status:**
  - "Delivered" appears only after an acknowledgment.
  - A refused `turn/steer`, a Claude run that ends before the acknowledgment, and a restart while `sending` all end `not-delivered`, with the reason.
  - A result for another run's note changes nothing.
- **Downstream.** A reviewer's envelope lists the notes the producing run received.
- **Migration.** A format-16 database loads, with `notes: []`.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build`;
  - `node scripts/real-run-test.mjs --fake`;
  - an independent review;
  - a browser pass by the lead (the lead drawer, the task page, light and dark, 375 px);
  - a real-run check when the owner runs one. Until then the README says real-model delivery is unverified.
