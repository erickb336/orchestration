# ORC-022: Send a note to a running stage

## Task identity

- ID and title: ORC-022. The lead sends a note to an agent while its stage is running, without pausing or restarting it.
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: **Planned: the next milestone, to build after ORC-021.** This is a high-level spec; the detailed design comes when it starts. The owner asked for it ("That's something good to build as task 22"; "just do the high-level spec for now and note it as a milestone").
- Specification revision: 3 (high level)
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

**Today, changing what a running stage does means stopping it.** You edit the spec, which stops the run and starts it again, or you pause the stage and rerun it. Small course corrections cost a whole rerun and lose the work in progress. Examples: "skip the README", "use the existing helper", "don't touch the migrations".

**The idea comes from running this project.** The lead sent notes to running background agents mid-task, and they adjusted without restarting.

**Outcome.** You talk only to the lead. When something you say should change work that is already running, the lead sends a short note to the running stage or stages it affects. For example, you say "have the coder skip the README, I'll write it".

- **Delivery.** The agent receives it at its next step and carries on. Its work so far is kept.
- **A record.** The note is recorded on the run and in the stage's handoff, with the message of yours that led to it, so reviewers and you see the guidance the agent had.
- **Your view.** The lead's reply lists every note it sent, like its steering changes.
- **Truthful states:**
  - **"Delivered"** only once the runtime accepts the note.
  - **"Not delivered"**, with the reason, if the run had already finished. The lead then reruns the stage with the note, or reports that it did not.

## Approach

- **Codex:** the app-server's `turn/steer`, with an `expectedTurnId` guard, so a note can never land in the wrong turn.
- **Claude:** the Agent SDK's streaming input (`Query.streamInput()`), with notes marked `client_composed` so their text is never treated as a command.
- **Fake runtime:** simulates delivery, labelled simulated.
- **The lead sends notes as part of steering** (ORC-009). Its reply to your message may include notes, as a new kind of change alongside focus, priority, defer and drop. Each note names its task, its stage and the text.
- **Where notes may come from:**
  - Only a lead run that answers your message may send notes. A planning run cannot.
  - Agents never message each other.
  - **You can also send a note directly** from a running stage on the task page. This is secondary: the main way is to tell the lead. Your direct notes are labelled as yours, and the lead sees them in its next reply.
- **Scope of a note:**
  - Notes are guidance within the current spec. They never change the spec; a change of scope still goes through a spec edit, which the lead can propose.
  - Each note is short plain text, and a reply or a run may carry only a few.

## Options and tradeoffs

| Option | Approach | Benefit | Cost |
| --- | --- | --- | --- |
| A | The lead delivers notes into running agents; it reruns with the note when delivery is too late | You talk only to the lead; course corrections keep work in progress | The Claude adapter moves to streaming input; the lead's output gains a new kind of change |
| B | Always stop and rerun with the note | Simple | Loses work in progress |
| C | Only the next stage gets the note | Trivial | Too late for the stage that needs it |

## Decision

- Selected option: A.
- Decided by: Lead, on the owner's request. The owner's direction:
  - "I want the lead to be able to send notes to the subagents. I only want to communicate with the lead."
  - Then: "We can have control for me to message them directly as well but main feature is lead messages".
- Both pinned runtimes support mid-run input (Codex app-server 0.159.2, Claude Agent SDK 0.3.285).
- **Open question, to settle when it starts:** how agents weigh a mid-run note. This is unverified until a real run, and it may shape the note's framing.

## Acceptance (high level)

- **Delivery:** a note to a running stage is delivered and the stage continues. The note shows on the run and in the handoff.
- **A finished run:** a note to a finished stage is refused with a reason, and the lead reruns the stage with the note in its instructions, or says why not.
- **Who can send:**
  - **The lead,** in a reply to your message. This is the main path.
  - **You,** directly from a running stage. This is secondary.
  - Planning runs and agents never can.
- **Checks:**
  - both adapters' tests, and the fake runtime;
  - an independent review;
  - a browser pass;
  - a real-run check when the owner runs one.
