## Problem and outcome

Worktrees accumulate without cleanup. There is no first-run guidance, no notifications, and no import or export. A public repository also needs install instructions, a license, CI for pull requests, and a clear statement of why the tool exists.

Outcome: a stranger can install and start the tool, a new user is guided through setup, and meaningful events notify the user. Worktrees can be cleaned up. The existing Markdown boards can be imported (with missing legacy specs identified) and the board exported. Pull requests run CI.

## Scope

Included:

- **Workspace cleanup:** a service action that removes worktrees and private temp directories of runs that are no longer active. Branches are kept, because artifacts reference their commits.
- **Markdown export:** `GET /api/export.md` returns the board with each task's selected approach, state, and integration status, for repository visibility.
- **Markdown import:** the `importMarkdown` command reads a Markdown task table, creating tasks with IDs preserved.
  - Done rows become done tasks marked "legacy spec unavailable".
  - Other rows become held tasks that cannot run until a spec is written. Editing the spec clears the flag.
- **Onboarding checklist** on the Overview: repository, providers, vision, first message or task.
- **Browser notifications**, opt-in and per browser, for task done, failed or blocked, control failures, integration conflicts, and lead replies.
- **GitHub Actions CI:** typecheck, tests, and build.
- **Publication:** a license and a README covering why the tool exists, installation, customisation, and the workflow.

Excluded: hosted deployment, native notifications while the page is closed, and a multi-project UI.

## Acceptance and validation

- Cleanup removes only the worktrees of inactive runs, never an active run's, and branches remain.
- An imported table preserves IDs. Legacy done tasks show "legacy spec unavailable". Imported open tasks never dispatch until their spec is edited.
- The export contains every task, with its state and selected approach.
- The checklist reflects the actual setup state.
- Notifications fire once per event and only when enabled.
- CI runs on pushes and pull requests.
- Checks: typecheck, tests, build, and a browser pass.
