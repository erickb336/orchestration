# ORC-018: Compare patterns on their outcomes, and export traces

## Task identity

- ID and title: ORC-018, a comparison of pipeline patterns on recorded task outcomes, plus an opt-in OpenTelemetry trace export (for Phoenix, Langfuse or any OTLP receiver)
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: In progress, P1.
  - **The owner's stated purpose.** Orchestrator is "a starting playground for me to develop and test different patterns for and ways of using multiple agents in my workflows". ORC-016 records which pattern each task ran and its outcome, but nothing reads those records yet.
  - **The audience.** The README addresses future employers and developers, and its "Measuring, not guessing" section promises this view.
  - **The owner's direction.** The owner asked for existing open-source tools for measuring results.
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

Observed:

- **The data exists but nothing reads it.** Every finished or cancelled task carries a `TaskOutcome`: wall time, agent time, runs per role, runner and model, tokens and cost where reported, repair rounds, findings, decisions, checks, review coverage, and human edits. Each task also carries its `PatternRef` (id, content hash, source). No screen reads any of this; the Overview's "Latest outcomes" lists delivery states only.
- **No answers to the owner's questions.** For example:
  - Does "Change, reviewed by the other provider" catch more than "Change"?
  - Does the lean pattern save time without more findings at the end?
  - What does a bug fix cost?
- **Delivery results are not summarised.** They live on `task.integration` (merged, sent back, time to landed), and `deliveryOutcome(t)` was designed in ORC-016 §10.3 but never written.
- **No trace export.** Every run, its timing, model and usage exist as attempts, but cannot be looked at in a trace viewer, or kept outside the app.

Outcome:

- **A Compare page** groups finished tasks by pattern, and by version of that pattern. It shows each measure as a median and a spread, and every task as a dot. Sample sizes are stated plainly, and small groups are called too small to compare.
- **Exports.** The rows export as CSV and JSON for analysis elsewhere.
- **Opt-in trace export.** When you turn it on, each finished task is sent as one OpenTelemetry trace (a task span, a span per agent run and per check run, attributes following the GenAI conventions where they apply) to an OTLP endpoint you name. A local Phoenix or Langfuse is the expected receiver.
  - Nothing is sent by default.
  - No prompt, output, code or credential is ever sent.

## Scope

Included:

1. **`deliveryOutcome(t)`** (pure, `src/domain/outcomes.ts`), following ORC-016 design §10.3. It derives these from fields already kept:
   - the delivery status;
   - whether it landed, how (the app or a person), and whether it was sent back (fix or revert);
   - time to landed;
   - the flags.

   It is never stored.
2. **Comparison data** (pure, `src/domain/compare.ts`).
   - **Rows.** One row per settled task with an outcome: the pattern id, name and hash, the source, `chosenBy`, area, result and dates, plus the measures below.
   - **Groups.** Rows are grouped by pattern id, and within that by hash. Versions can be merged by choice, and a merged group says it mixes versions.
   - **Measures** (each with its own n, because not every row reports every measure):
     - time to done (`wallMs`) and agent time;
     - runs per task;
     - input and output tokens, and cost per task, counting only rows that reported them, with "n of m reported";
     - repair rounds;
     - findings raised by severity, and still open at the end;
     - checks: whether the final checks passed without a repair round, and failed check runs;
     - review coverage: complete, out of all reviews;
     - human involvement: artifact edits, decisions made by you, candidate choices;
     - delivery: landed, sent back, time to landed.
   - **Statistics.** Median, the 25th–75th percentile, minimum and maximum. No significance tests, no p-values, and no "winner".
   - **Sample size.** A group with fewer than 5 rows is marked "too few to compare". A difference is never called meaningful.
   - **Filters:**
     - area;
     - result (done only by default; cancelled can be included);
     - who chose the pattern (the lead, you, a breakdown);
     - a date range;
     - whether rows from tasks that changed pattern midway are included (excluded by default).
3. **The Compare page** (a new top-level tab, "Compare").
   - **The table:** one row per group, with the measures as columns. Each cell shows the median, with the spread in small type, and a dot strip of the tasks where it helps reading. A column header explains its measure in a tooltip.
   - **Choosing measures:** you pick which to show, and the choice is kept in the browser.
   - **Choosing two groups** shows them side by side, measure by measure. Each measure shows both medians and both spreads, and a plain note when either group is too small.
   - **Opening a group** lists its tasks, each linking to the task page.
   - **Exports:** "Download CSV" and "Download JSON" of the filtered rows, built in the browser.
   - **Labelling:** in the demo, the page says the outcomes are simulated, made by the demo to show the page, and say nothing about real patterns.
   - **Empty state:** it says what will appear here, and that outcomes are recorded from ORC-016 on.
4. **The demo shows a populated Compare page.**
   - The demo state gains earlier finished tasks, about 24 across "Change", "Change, reviewed by the other provider" and "Bug fix", with outcomes made by the real capture function from simulated attempts. They are labelled simulated.
   - **Collapsing old done tasks.** So the board stays readable, the board and the list collapse done tasks older than 7 days under "Done earlier (n)", shown with one click. This is useful in real projects too.
5. **Trace export** (`server/telemetry.ts`).
   - **Settings → Telemetry.** Turn it on and give an OTLP/HTTP traces endpoint. The default suggestion is `http://localhost:6006/v1/traces` (Phoenix). Langfuse's endpoint is shown as an example.
   - **Credentials.** Headers come only from the standard environment variable `OTEL_EXPORTER_OTLP_HEADERS` (for example Langfuse's Basic auth), set by you in your shell. The app never stores or shows them.
   - **Other hosts.** A non-loopback endpoint shows what will leave the computer (task titles, pattern names, model names, timings, token counts and cost) and needs a confirming checkbox.
   - **What is sent:** one trace per settled task, sent at settle. The spans follow ORC-016 design §10.4, re-checked against the pinned `@opentelemetry/semantic-conventions`:
     - a task span, with `orc.*` attributes and `orc.outcome.*`;
     - child spans per agent attempt, with `gen_ai.operation.name = "invoke_agent"`, `gen_ai.provider.name`, the request and response model, agent name and token usage, plus `orc.cost.usd`;
     - `orc.checks` spans per check run;
     - `error.type` on failed or lost runs.
   - **What is never sent:** spec text, prompts, outputs, artifacts, file paths, repository paths or credentials.
   - **Libraries:** the OpenTelemetry JS SDK (`@opentelemetry/sdk-trace-base`, `@opentelemetry/exporter-trace-otlp-proto`, `@opentelemetry/resources`, `@opentelemetry/semantic-conventions`; Apache-2.0, pinned).
   - **Status and sending.**
     - The status shows the last export, any errors, and how many traces are waiting.
     - Failed exports are retried with a backoff and a cap.
     - "Send finished tasks" exports the existing outcomes once, on request.
     - Each task is exported at most once per settle: the export state is recorded per task, and restarts do not send duplicates.
   - **The demo** can export too (labelled simulated in the resource attributes: `orc.simulated = true`).
6. **README:** the "Measuring, not guessing" section is updated to what exists, with a screenshot of the Compare page from the capture script, and a short "Look at traces in Phoenix or Langfuse" how-to.
7. **Tests:**
   - `deliveryOutcome`;
   - grouping, medians and quantiles at small n, "too few", merged versions, filters, and missing measures;
   - CSV quoting;
   - the trace builder, against the §10.4 table (attributes, parents, times, and the exclusions);
   - the exporter against an in-process OTLP/HTTP receiver: protobuf decoded, retry, at most once across a restart, nothing sent when off, headers taken from the environment only;
   - the non-loopback confirmation;
   - the demo state staying valid, with its outcomes;
   - the done-collapse.

Excluded:

- **Automatic pattern assignment** (rotation or A/B arms). It needs rules for lead-created tasks and holds, and is a follow-up (ORC-020).
- **Statistical significance.** With the sample sizes one person produces, intervals and claims would mislead.
- **Sending prompts or outputs to a trace viewer.** That may come later, opt-in, with redaction.
- **Running Phoenix or Langfuse for you.** You start the viewer; the README says how.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | In-app Compare page from `TaskOutcome`, plus opt-in OTLP export with the OpenTelemetry SDK | Answers in the app with no setup; deeper inspection in any OTLP viewer; open standards | Medium | Two surfaces to maintain; the GenAI conventions are still in development | High |
| B | Export only, and compare in Phoenix or Langfuse | Least UI | Small | Needs a running viewer to see anything; those viewers do not know patterns or outcomes, so the comparison is left to the user | High |
| C | In-app comparison only | No dependency | Small–medium | No traces for drilling into runs; nothing leaves the app for later analysis except CSV | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead.
- Rationale and evidence:
  - The owner wants to test patterns: the comparison must work with zero setup, which favours an in-app view.
  - The owner also asked for existing open-source tools: OTLP export lets Phoenix or Langfuse do what they are built for (span timelines, filtering, long-term storage) without the app rebuilding it.
  - The data model already exists (ORC-016), so the cost is mostly presentation and mapping.
- Uncertainty and what would change the decision:
  - Whether medians and dot strips are enough at small n. If not, the next step is a per-measure distribution view, not statistics.
  - Whether Phoenix accepts the spans as mapped. If its ingestion differs, the mapping adapts; the in-app view is unaffected.

## Acceptance and validation

- **Compare page, in the demo:**
  - three or more groups appear, with their n, medians and spreads;
  - a group under 5 says "too few to compare";
  - two groups compare side by side;
  - a group opens to its tasks;
  - CSV and JSON download the filtered rows;
  - the page says the outcomes are simulated.
- **Versions:** two versions of one pattern (different hashes) appear apart, and together only when merged, with a note.
- **Cost columns:** a measure missing from some rows shows "n of m reported" and never treats a missing value as zero.
- **Delivery:** `deliveryOutcome` covers landed by the app, landed by a person, sent back as a fix, sent back as a revert, closed, and not delivered.
- **Trace export:**
  - When off, nothing is sent.
  - When on, a settled task sends exactly one trace with the §10.4 attributes and none of the excluded content. The headers come from `OTEL_EXPORTER_OTLP_HEADERS` only.
  - A failing endpoint is retried with backoff, and a restart sends no duplicates.
  - A non-loopback endpoint needs the confirmation.
- **The board** collapses done tasks older than 7 days.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build`;
  - an independent review, and mutation checks of the key guards;
  - a browser pass in light and dark, at desktop and 375 px;
  - `npm run capture` producing `docs/screenshots/compare.png`.
- **Real Phoenix or Langfuse:** verified only if the owner runs one. Otherwise the evidence says it was not verified.
