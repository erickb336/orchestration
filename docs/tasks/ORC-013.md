# ORC-013: Quality gates

## Task identity

- ID and title: ORC-013, quality gates. The service runs the project's own checks (test, lint, typecheck, build) before work is delivered. Review findings are triaged one by one. A clean review must show it covered every changed file. CI failures are triaged before a fix task is paid for. The repository's agent-instruction files reach workers as labelled project conventions, the same way for Claude and Codex.
- Author and timestamps: Lead (Claude), 2026-09-30
- Status, priority, and priority rationale: Completed, P1. The user asked: "Build the most valuable learnings into the orchestrator". This follows research into two external tools, no-mistakes and firstmate. The researcher ranked service-run checks, per-finding triage, review coverage and CI triage as the most valuable ideas; the fifth part (instruction files) fixes an inconsistency the research exposed. All five serve the user's standing preference: autopilot by default, with optional review, and no need to read code.
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-30

## Problem and outcome

Observed. These come from a read-only trace of the code at `f51ee08` and of the Codex 0.159.2 binary's built-in defaults; no model runs were made.

- **Nothing guarantees that tests ran.**
  - The last step of every code template, "Verify and integrate", is a lead agent's judgement (`src/domain/templates.ts`). Its verification output gates nothing.
  - Claude workers have no shell unless the service is started with `allowShell`, and Codex workers run with the network off. A worker often cannot run the suite, and nothing records whether one did.
- **A review's findings are one number.**
  - A review reports a summary and `openFindings` (`server/envelope.ts`). The repair loop fixes "the findings", whatever they are.
  - That includes findings whose fix would widen the task or reverse a choice the user made.
  - Nothing records what was decided about a finding, so the next round can raise it again.
- **A clean review proves nothing about coverage.** `reviewCoverage` (`src/domain/delivery.ts`) checks that a review saw the final change and reported nothing. It does not check that the review looked at every changed file. The diff in the envelope is cut at 60 KB.
- **Every CI failure costs a fix task.**
  - `repairCause` treats every required check that is not `SUCCESS` as the code's fault. A run GitHub cancelled, a required check that was skipped, and a review bot's opinion each start a fix task.
  - `parseChecks` keeps the worst run of each check name, so a cancelled run stays red next to a later green re-run.
  - A repository with no CI can never be merged from the app, not even by the user's own Merge: gate item 6 blocks when no required check exists.
- **Workers see the repository's own agent instructions inconsistently.**
  - Claude workers load no project settings, so they read no `CLAUDE.md` or `AGENTS.md` (`server/runtimes/claude.ts`).
  - Codex workers very likely read `AGENTS.md` from the worktree. Codex 0.159.2 ships with `project_doc_max_bytes = 32768` and `project_root_markers = [".git"]`, and the adapter changes neither.
  - The worktree is written by agents, so a coder can rewrite what the next reviewer reads as instructions.
  - In this repository, `AGENTS.md` says "The primary agent is the lead", which a Codex coder reads as addressed to itself.

The user's job is to let the team deliver on autopilot and trust that what lands was built, tested and reviewed, without reading code.

Outcome:

- **Checks the service runs itself.**
  - You list the project's check commands once in Settings (or accept the ones the app suggests from the repository).
  - The service runs them in a disposable copy of each change, in the same sandbox Codex workers use: no network, and writes only inside that copy.
  - A failure becomes a finding the repair loop fixes. Before a task finishes, its final change must pass, or someone decides.
  - Off until you turn it on, because running checks runs the repository's code.
- **Findings with a severity and an action.**
  - Each finding says `error`, `warning` or `info`, and `auto-fix`, `ask-user` or `no-op`. A finding without an action is `ask-user`.
  - `ask-user` is for findings whose smallest honest fix would widen the task (new state, a schema change, a new subsystem) or question what was asked.
  - The repair loop fixes only `auto-fix` findings and the ones someone decided to fix. `ask-user` findings go to the lead, or to you, as a decision.
  - Decisions are recorded, shown on the task, and given to later repairs and reviews.
  - Reviews that report only a summary keep working as today.
- **Proof of coverage.** A review that reports nothing must list the changed files it judged. The list must equal the files the change touched. Otherwise the review runs again once with the missing files named, and it does not count as clean evidence for the pull-request gate or for skipping a repair.
- **CI triage for pull requests.**
  - A check GitHub cancelled is re-run once before any fix task.
  - A failing check from a review bot, and a required check that was skipped, need a person instead of a fix task.
  - An empty check list is never green, unless you declare that the repository has no CI; your own Merge then works.
- **One rule for agent-instruction files.**
  - No worker or lead run, on either provider, loads the repository's instruction files by itself.
  - The service reads `AGENTS.md` (and `CLAUDE.md`) from the trusted base and puts them in the assignment as "Project conventions". They guide how code is written and tested, and they never change the worker's role.

## Scope

Included:

- **Service-run checks.**
  - `Project.checks`: the command list, with a program allowlist, timeouts, the sandbox choice, protected check inputs and pass-through variable names. It is set only by the user.
  - Suggestions read from `package.json` scripts and lockfiles at the trusted base, applied only when the user accepts them.
  - A new step role, `checks`, run by the service, whose output is a `check-results` artifact.
  - The built-in templates Feature, Change, Bug fix and Revert get a Checks step inside the review–repair loop and a Final checks step before verification. The steps skip, labelled, while checks are off.
  - A runner (`server/checks.ts`) that uses the Codex app-server's `command/exec` sandbox. It captures output (redacted and capped), stores full logs outside the state, and builds the command environment from an allowlist.
  - Pause, stop, timeouts, lost runs and stale results follow the existing attempt rules.
  - Pull-request delivery: a "Service checks" item in the merge gate, and a dedicated check run when the final change has none.
- **Per-finding triage.**
  - Structured findings in the review output contract, strictly validated.
  - `FindingDecision` records, routed to the lead or the user by a project setting. The lead decides in its reply; the user decides in the UI.
  - Carry-forward of an earlier decision for the same finding, and decisions in later repair and review envelopes.
  - Backward compatibility for summary-only findings.
- **Review coverage.** `reviewedPaths` in the review output; the changed-path set recorded per run; one automatic re-review with the missing files named; the rule applied to runIf and to `reviewCoverage`.
- **CI triage (pull-request mode).**
  - Check runs are judged by their newest run.
  - A bounded re-run of provider-cancelled GitHub Actions jobs, as a recorded intent like every other GitHub write.
  - Review-bot and skipped checks become attention for a person.
  - A "this repository has no CI" declaration in Settings → Delivery.
- **Agent-instruction files.** `-c project_doc_max_bytes=0` for every Codex app-server the service starts, and a "Project conventions" section in worker and lead envelopes, read from the trusted base and capped.
- **UI:**
  - Settings → Checks.
  - Findings and check results on the task page.
  - Decisions in the Needs you list.
  - The new gate item and CI triage lines on the Review page.
  - The checks role in the pipeline editor.
- **Migration 13 → 14**, and tests with mutation checks.

Excluded:

- A repository configuration file (for example `.orchestrator.yml`). Commands come from project settings in r1; a repository file is an open question.
- Automatic merging in a repository without required checks. The no-CI declaration unlocks only the user's own Merge.
- Reading CI logs into agent envelopes. Repairs still get check names and links only.
- Changing how a worker itself runs commands (Claude shell access, the Codex sandbox).
- Windows. The sandbox relies on the Codex app-server's macOS and Linux sandboxes.

## Options and tradeoffs

The main question is where the check commands come from and how the service runs them.

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| **A (selected)** | Commands in **project settings**, set only by the user (with one-click suggestions). The service runs them in the **Codex app-server sandbox** (`command/exec`: no network, writes only in the run's copy). A Checks step in the loop, and a Final checks step. | Deterministic evidence that the final change builds and passes, with no agent judgement. Agents cannot change which commands run. Same sandbox as Codex writers. | Large (11–13 days, three steps) | Runs repository code, including code an agent wrote. The pinned sandbox cannot restrict reads, so a hostile test can read files and print them; redaction is best effort. Checks can still be weakened through files they read (`package.json` scripts, test config). | High: off by default; one switch |
| B | Commands in a **repository file** read from the base branch at a fetched commit (no-mistakes' model), run the same way | Versioned with the code; shared with anyone using the repository | Large, plus a parser and a trust model per delivery mode | The "trusted base" exists only in pull-request mode; local mode would trust the user's branch, which local delivery writes to. A landed change could edit the file. Needs YAML or JSON parsing and pinning. | High |
| C | **Agents run the checks**: give workers shell and network, and ask the verify step to report results | Least new code | Medium | Still an agent's word; widens every worker's reach; nothing binds the result to a commit | Medium |
| D | Defer | Nothing new to trust | None | Nothing guarantees tests ran; findings, coverage and CI stay as they are | — |

How each part works:

| Question | Selected | Alternatives rejected |
| --- | --- | --- |
| Where checks run in the pipeline | A Checks step first in the review–repair loop, so reviews and repairs see its results. A Final checks step after the loop. | A stage inside integration: a failure there would come after the task is Done, with no repair path. Checks after review only: the reviewer never sees a failing test. |
| What a failure becomes | One `auto-fix` error finding per failing command, fixed by the existing repair loop | A blocked step on every failure: stalls autopilot |
| Final change still failing after the loop | A decision. The lead may add a repair round (at most two); only the user may accept failing checks. | Letting the task finish: delivers failing code. Always the user: stalls autopilot. |
| How commands run | Codex app-server `command/exec` with `workspaceWrite`, network off, private temp and cache, an allowlisted environment; direct execution only if the user explicitly chooses "no sandbox" | A hand-written Seatbelt profile: platform-specific and unmaintained here. No sandbox by default: agent-written tests would run with full access. |
| Who decides `ask-user` findings | A project setting: the lead (the default for Autopilot projects) or the user. The lead's "fix" on a spec the user wrote becomes a suggestion to the user. | Always the user: stalls autopilot. Always the lead: widens scope the user set. |
| Coverage enforcement | One automatic re-review naming the missing files, then a blocked step | Accepting partial coverage: the gap the rule exists for. Blocking at once: costly on the first slip. |
| CI failures GitHub caused | Re-run the job once per check per head (budget 0–3, default 1), as a recorded intent | Always a fix task: pays an agent to read a run that tested nothing. Unlimited re-runs: cost and loops. |
| Instruction files | Never auto-loaded by workers on either provider. The service passes them from the trusted base, labelled as conventions. | Auto-load on both: the worktree copy is agent-written, and Claude project settings would also load hooks that run outside the workspace guard. |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead.
- Rationale and evidence:
  - A turns "verify" from a claim into a recorded run bound to a commit and a configuration revision.
  - It reuses the existing repair loop (runIf over an artifact's open count) instead of adding a second fix path.
  - Keeping the commands in the app's own state means no agent output, and no file an agent can edit, decides which commands run.
  - The Codex `command/exec` request exists in the pinned protocol (`CommandExecParams`: argv, cwd, env overrides, timeout, output cap, sandbox policy) and gives the same no-network, worktree-only sandbox Codex writers already run in. The project already starts and speaks to that app-server.
  - Triage, coverage and CI triage change what counts as evidence and who pays for a fix, without new kinds of task.
- Uncertainty and what would change the decision:
  - Whether `command/exec` works under a private, signed-out `CODEX_HOME`, ends a command's child processes on terminate, and honours `networkAccess: false`. A probe decides it on each machine. If it fails, checks need the user's explicit "Run without a sandbox".
  - Whether Codex 0.159.2 honours `project_doc_max_bytes=0` for the app-server (the key exists in the binary). A canary run decides it; until then Settings says "unverified".
  - Whether a real reviewer lists `reviewedPaths` reliably. If re-reviews become frequent, the rule may relax to "missing files only" (extra entries ignored).
  - GitHub's job re-run endpoint with the user's account, and whether a re-run replaces the cancelled run in the check rollup. The ORC-008 sandbox repository decides both.
  - A repository file instead of settings (option B) if the user wants checks shared with others.
- User override, if any: none yet.

## Acceptance and validation

- **Checks off (the default):**
  - Every built-in Checks step is skipped with "Checks are off for this project (Settings → Checks)".
  - Nothing is started: a spy on `child_process` sees no spawn.
- **Checks on:**
  - A Checks step runs the configured commands in a copy of exactly the change it received.
  - It records each command's status, exit code, duration and redacted output (at most 8 KB in the state; the full log, capped, in a file).
  - A failing command becomes one `auto-fix` error finding. The repair step receives it, and the next round's Checks step runs on the repaired change.
- **Final checks:**
  - When the final change is the one the loop last checked with the same configuration, the Final checks step reuses that result and says so.
  - When the final change still fails, the task does not finish. It needs a decision. The lead can add at most two repair rounds; only the user can accept failing checks, and that acceptance is flagged on the landed item.
- **Command environment:**
  - Built from an allowlist. Fake values of `GH_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `SSH_AUTH_SOCK` and `NODE_OPTIONS` never reach a command.
  - A fake token and a PEM private key printed by a command are masked in the state, the log file and every envelope.
- **Sandbox:** with the Codex sandbox, a probe command cannot write outside its copy, temp and cache directories, or open a network connection. Without it, the user chose "Run without a sandbox" explicitly, and every such run is labelled unsandboxed.
- **Network (review of steps 1–3, H1):** the network is given only to npm, pnpm and yarn dependency downloads with every hook that runs repository code switched off (`--ignore-scripts` or yarn's `--mode=skip-build`, `--ignore-pnpmfile` for pnpm, `YARN_IGNORE_PATH=1`; a yarn whose `.yarnrc.yml` sets `yarnPath` or `plugins`, or whose `.yarnrc` sets `yarn-path`, is kept offline). Every other prepare command, bun included, runs offline, and the record says so. A flag that switches a hook back on is refused by validation and dropped by the runner.
- **Exit status (review M5):** a command's status comes from the service's own wrapper process, never from a file the command can write; a wrapper ended by a signal is a failure.
- **Interruption:**
  - A pause or a pipeline edit during a check run ends the command's process group, records no result, and runs it again after resume.
  - A restart marks the run lost and requeues it.
  - A run from before a lost lease writes nothing.
- **Findings:**
  - Structured findings are validated. A missing or unknown action is `ask-user`, a missing severity is `warning`, and the open count is computed by the service, not taken from the worker.
  - The repair step waits while an `ask-user` finding it would read is undecided.
  - It fixes only `auto-fix` findings and those decided "fix". "Accept" and "follow-up" findings are listed to it as "do not implement".
  - Summary-only findings behave exactly as before.
- **Decisions:**
  - Routed as set. The lead's decisions are validated, attributed and changeable by the user until a repair uses them.
  - A lead "fix" on a user-written spec becomes a suggestion to the user.
  - The same finding in a later round inherits the decision, labelled.
- **Coverage:**
  - A clean review whose `reviewedPaths` differ from the changed files runs once more with the missing files listed, then blocks.
  - Such a review never counts as clean for the pull-request gate or for skipping a repair.
- **CI (pull-request mode):**
  - A required GitHub Actions check cancelled on the head is re-run once, and no fix task starts.
  - A failing review-bot check and a skipped required check each need a person, and no fix task starts. A cancelled check that cannot be re-run (no re-run left, no job id, another app, re-runs off) needs a person too.
  - A cancellation is the code's fault, and starts a fix task, when another job of the same workflow run failed, when the check was cancelled again after its re-run, or when the job ran to GitHub's 360-minute limit (a workflow's own shorter limit is not in the API).
  - A green re-run makes the name green: a newer run stands for an older one only when the older one was cancelled and both come from the same app, workflow and job name; every other non-success stays.
  - The driver's own read right after a re-run request does not count toward the wait for the new run.
  - `gh` is allow-listed by subcommand; a `gh api` write goes only to a pull request's comments, a job re-run or the scanned GraphQL query, however the method or body is spelled.
  - With the no-CI declaration, the user's Merge works with zero checks; automatic merging still needs a required check; checks that do appear are honoured.
- **Instruction files:**
  - Every Codex app-server the service starts has `-c project_doc_max_bytes=0`.
  - Envelopes carry "Project conventions" from the trusted base, never from the worktree, capped and labelled.
- **Migration 13 → 14:**
  - Defaults are added and unmodified built-in templates gain the Checks steps.
  - Edited templates are left alone, with an event.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build` pass, and a browser pass on the simulated runtime.
  - Mutation checks are listed in the design (§14).
- **Real evidence, with consent:**
  - The sandbox probe on this Mac.
  - A Codex canary run showing that `AGENTS.md` is no longer loaded.
  - A cancelled-job re-run in the ORC-008 sandbox repository.
  - Until each passes, the matching label says "not verified".

## Execution plan

- Branch `quality-gates` from `main` after ORC-012 merges (state format 12). One pull request to `main`.
- Three sequential steps. Each is one implementation followed by an independent review on the other provider, and each leaves the suite green:
  1. Findings, triage, coverage and instruction files, plus the whole data model and migration.
  2. Service-run checks.
  3. CI triage.
- Technical design: `docs/design/ORC-013-design.md`.
- Recovery: each step is its own commit. Checks stay off by default, so steps 1 and 3 change nothing a user runs until checks are turned on.
- Hold state: none. The spec is published, not a gate.
