## Problem and outcome

Today every task is written by the user, the "lead" is a rule-based scheduler, there is no lead conversation, and finished work stays on per-run branches.

PROJECT_SPEC.md's Milestone 4 exit is:

> Vision → spec → mixed-provider implementation → independent review → verified completion works without task-by-task prompting; either provider can lead.

Outcome:

- **Lead runs:** a real lead agent, on the configured provider and model (Claude or Codex), runs on demand and on a bounded cadence. It reads the vision, the board, recent outcomes and findings, and the conversation, then replies and proposes fully specified tasks. Those tasks flow through the existing pipelines.
- **Integration queue:** completed work is merged, one task at a time, into a per-project integration branch. Conflicts are surfaced and fed back to the lead.
- **Bounded autonomy:** it is off until the user enables it. Proposal counts, cadence, and operating hours are bounded. The user can pause everything.

## Scope

Included:

- **Domain:**
  - The conversation (user and lead messages).
  - Lead runs, as a separate kind of run: at most one at a time, stopped by a project pause, and confirmed stopped.
  - Autonomy settings:
    - enabled flag
    - planning interval
    - maximum proposals per cycle
    - maximum open lead proposals
    - hold lead proposals before start
    - operating hours
  - Lead-proposed tasks with complete specs: options, recommendation, selection, and a template-based pipeline.
  - Per-task integration status.
  - Lead model selection, where a switch stops an active lead run first.
- **Service:**
  - Lead envelope and a parser for its output (a reply, plus proposals validated against the spec requirements).
  - Scheduler triggers, coalesced into at most one pending lead run: a user message, a task completion, and the planning cadence.
  - A read-only worktree for the lead in real mode.
  - A serial integration queue, run in its own worktree with hooks disabled. Integration is frozen by a project pause.
  - The fake runtime simulates lead replies and one proposal per planning run.
- **UI:**
  - A lead conversation on the Overview.
  - Lead and autonomy settings.
  - Integration status, and the author of each task.
- **Tests** for the domain, the scheduler (lead runs with scripted adapters), and integration (merge and conflict, on a temporary repository).

Excluded:

- The lead editing existing tasks' specs or pinned choices. It proposes new tasks and replies. The user keeps control of existing work.
- Automatic merges into the user's own branches.
- A dedicated lead tool API (MCP board tools). The lead receives the board in its envelope and answers in a checked JSON format.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Lead runs through the same adapters, with an envelope containing the board and a checked JSON reply (reply plus proposals); the service validates and applies | Works identically for Claude and Codex; bounded; every lead action is validated and auditable | Medium | The lead cannot query the board interactively; the envelope must stay concise | High |
| B | Expose board tools to the lead over MCP and let it act directly | Richer interaction | Large | A new tool server per provider; harder to bound and audit; its behaviour differs by provider | Medium |
| C | Rule-based planner only (no LLM lead) | No cost | Small | Does not meet the milestone (no agent-created tasks, no conversation) | High |

## Decision

- Agent recommendation: A
- Selected option: A
- Decided by: Lead
- Rationale and evidence: PROJECT_SPEC.md says to "expose bounded task-management tools to the lead, validate its requests". A validated JSON proposal format is exactly that kind of bounded interface, and it is provider-independent, so either provider can lead.
- Uncertainty and what would change the decision: if a larger board overflows the envelope, add summarisation or move to option B.
- User override, if any: none

## Acceptance and validation

- A user message wakes a lead run, and the lead's reply appears in the conversation. Several messages sent during one run are answered together by the next run.
- With autonomy on, a planning run proposes at most N complete tasks. They appear on the board as authored by the lead and run through their pipelines without further prompting, unless "hold lead proposals" is on.
- With autonomy off, no planning run starts.
- Outside operating hours, and while the project is paused, no lead run starts. A project pause stops an active lead run, which shows as stopping until the stop is confirmed.
- Invalid proposals are rejected with a reason in the conversation and never become tasks. Examples: no options, an unknown template, or more proposals than allowed.
- A done task's latest code change is merged into `orchestration/<project>/integration`, one task at a time. A conflict marks the task "integration conflict", with the files involved, and is included in the next lead envelope. Nothing is merged into the user's own branches.
- Switching the lead's provider or model stops an active lead run first. The next run uses the new selection.
- Checks: `npm run typecheck`, `npm test`, `npm run build`, and a browser pass in fake mode (conversation, autonomy, proposals, integration status).
