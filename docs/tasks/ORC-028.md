- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: **In progress, P1.** The owner, 2026-10-01: "please continue with whatever improvements or fixes this caught and merge this as an integration test".
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

**Where it fits.** ORC-027 committed the real-run scenario as an integration test, and the lead ran it with real Claude and Codex (record `docs/real-runs/2026-10-02T02-22-16-079Z.json`). It passed every check, but its results showed a product gap that no check looked for. The early Codex note was the other catch, and ORC-027's review already fixed it.

**What the run showed** (task T-002, the Investigation flow, on Claude):

1. The note asked the agent to add greeting.js's line count. The agent did, and also dropped the list of files it read: the task's only acceptance criterion.
2. The review step caught it: finding F1, a warning marked auto-fix, "Report does not explicitly list the files read".
3. **Nothing fixed it.** Investigation is the only one of the six flows whose review has no repair step: Change, Bug fix and Feature repair until clean, and Design revises. The task went to **Done** with the warning open.
4. The lead's brief said "not ready", and reasoned that the findings were "auto-fix, so no owner decision is needed". Nothing was going to auto-fix them.

So a finding the system classed as auto-fix was silently dropped, and the board said Done. The owner reviews results, not runs, so they would never see it.

**The outcome:**

- No built-in flow can drop a review finding: every review feeds a step that repairs what it finds.
- Investigation repairs its report the way Design repairs its design.
- A note reminds the agent that the task's acceptance criteria still apply.
- The integration test fails if a finding that needed a fix is skipped, and it sends notes as early as a person might.

## Scope

**Included:**

- **The Investigation flow** (`flows/investigation.json`):
  - investigate → review → **revise the report while the review finds something (up to 3 rounds, like Design)** → the lead proposes the follow-up spec.
  - The lead's step reads the first report, the revised one and the findings, as Design's lead step does.
- **A structural rule** (a test over every built-in flow): each step that outputs review findings must be the condition of a later repair step. A new flow without one fails `npm test`.
- **The note wording** (`noteMessage`): it adds that everything the task asks for, including its acceptance criteria, still applies.
- **The demo:** WT-012 (the battery investigation) gets the new step. Its review leaves one finding that blocks nothing, so the revise step is skipped, and the lead's brief moves to S4.
- **The integration scenario:**
  - It expects four Investigation steps.
  - New check, per task: every repair step whose review found something that needed a fix ran, rather than being skipped.
  - Notes are sent as soon as the run is dispatched (polling every 100 ms). The record says whether Codex had started its thread yet, so the held-note path from ORC-027 is exercised when the timing allows.
  - The answer-to-the-note hint reads the newest report.
  - PASSED needs exactly 15 checks.
- **Docs:** the README's flows table, the milestone table, and `docs/real-runs/README.md`.

**Excluded:**

- Turning the lead's proposed follow-up into a task automatically. In Investigation the brief is the deliverable, and the lead's planning (Autopilot) already reads outcomes.
- Changing flows other than Investigation; the rule shows they already comply.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| **A (selected)** | Give Investigation a revise loop like Design's, and add a rule that every review feeds a repair | The report gets fixed before the lead writes the spec, and no future flow can drop findings | Small | One more agent run per round when the review finds something | High: a flow file and a test |
| B | Keep the flow; when a task ends with open blocking findings, put it under Needs you | The owner sees the problem | Medium | The owner fixes by hand what an agent could; it contradicts autopilot | High |
| C | Only reword the note | Smallest | Trivial | The run shows wording alone does not hold: the note already said it "does not change the specification" | High |

C is included as well, as a cheap second line, but not as the fix.

## Decision

- Agent recommendation: A, with C's wording.
- Selected option: A + C.
- Decided by: the lead, under the owner's instruction to continue with the fixes.
- Rationale and evidence:
  - Every other flow already pairs its reviews with a repair.
  - The finding was correct, and an agent could have fixed it in one round.
  - The rule turns this lesson into structure ("encode lessons in structure").
- Uncertainty and what would change the decision: whether a real model fixes a report in one round. The real run below shows it.
