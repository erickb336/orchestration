# ORC-010: Opt-in Claude subscription sign-in for personal use

## Task identity

- ID and title: ORC-010, opt-in use of the user's own Claude subscription token for Claude workers and the lead
- Author and timestamps: Lead (Claude), 2026-09-30
- Status, priority, and priority rationale: **Done, P2.** Merged on 2026-09-30 (erickb336/orchestrator#4); the owner's real-model run on 2026-10-01 used it (see ORC-004). The user asked for it directly ("Start that feature work now using CLAUDE_CODE_OAUTH_TOKEN"). The motivation is cost: an Anthropic API key is billed on top of the Claude subscription the user already pays for, whereas Codex already runs on the user's ChatGPT sign-in.
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-30

## Problem and outcome

**Observed:** Claude workers accept only `ANTHROPIC_API_KEY` or cloud-provider credentials (`server/runtimes/claude.ts`, `health()`). The user has Claude Code installed with a subscription, and has created a long-lived token with `claude setup-token`, which Claude Code documents as authenticating "with your Claude subscription".

**Policy, stated plainly:** Anthropic's Agent SDK documentation says:

> "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."

The documentation does not say whether a subscriber may use their own token in their own tool. The lead flagged this twice before building. The user chose to proceed. The feature therefore:

- is off unless explicitly switched on;
- is labelled for personal use;
- quotes the rule wherever it is switched on.

It never makes subscription sign-in the default or recommended path.

**Outcome:** a user who sets both `ORCHESTRATION_CLAUDE_AUTH=subscription` and `CLAUDE_CODE_OAUTH_TOKEN` gets Claude workers and a Claude lead that run on their own subscription. Settings says so truthfully, including the usage-limit and policy caveats.

## Scope

Included:

- **Health check:** the Claude adapter reports "ready" in subscription mode only when both variables are set. The detail text names the mode, the usage limits and the Anthropic rule, and never the token.
- **Worker and lead environment:**
  - In subscription mode: `CLAUDE_CODE_OAUTH_TOKEN` is passed, and `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and the cloud-provider flags are removed. The sign-in actually used is then unambiguous.
  - In the default mode: `CLAUDE_CODE_OAUTH_TOKEN` is removed, so a token the user has for other scripts is never used by accident.
- **Messages:** a plain explanation when the token is set without the switch, and when the switch is set without the token.
- **Documentation:** the README's credentials section.
- **Tests** for each of the above.

Excluded:

- Reading the token from Claude Code's keychain or its config files. The user sets the variable themselves; the app never reads, stores or prints it.
- Any interface control that turns the mode on. It stays an environment setting the user makes deliberately.
- Changes to Codex.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Explicit opt-in: both variables required; credentials made exclusive per mode | Uses the subscription the user already pays for; no accidental use | Small | Anthropic's rule may cover this use; usage limits are shared with the user's own Claude Code | High: unset the variable |
| B | Use `CLAUDE_CODE_OAUTH_TOKEN` whenever it is present | Simplest | Smallest | A token set for other scripts would be used silently; no deliberate choice | High |
| C | Do not build it; recommend Codex for writing and a capped API key for Claude reviews | No policy exposure | None | The user pays for API use on top of the subscription | N/A |

## Decision

- Agent recommendation: C. After the user's decision, A.
- Selected option: A.
- Decided by: User ("Start that feature work now using CLAUDE_CODE_OAUTH_TOKEN").
- Rationale and evidence: A gives the user what they asked for while keeping the choice deliberate, visible and reversible, and it keeps the credentials exclusive, so Settings tells the truth about what is used.
- Uncertainty and what would change the decision:
  - Whether Anthropic permits this use. A statement from Anthropic either way decides whether the option stays, and whether it belongs in the public repository.
  - Whether the Agent SDK honours `CLAUDE_CODE_OAUTH_TOKEN` in the way the service starts it. This is unverified until the user's real run.

## Acceptance and validation

- With both variables set, Settings shows Claude as ready with the subscription detail. Worker and lead processes receive the token and no API key or cloud flag.
- With only the token set, Claude is "not configured", and the message explains the switch.
- With only the switch set, Claude is "not configured", and the message explains `claude setup-token`.
- In the default mode, the token never reaches a worker.
- The token value never appears in a health detail, an event, an error or a log. The existing redaction covers variables named `*TOKEN*` and `sk-…` shapes; this is tested.
- Checks: `npm run typecheck`, `npm test` and `npm run build` pass.
- The real check is the user's own: run with their token, then confirm in Settings and in a first Claude run.

## Execution plan

Branch `claude-subscription`, then a pull request to `main`. Because of the policy question, the user decides whether to merge it into the public repository.

## Completion evidence

**Built** on `claude-subscription` (2026-09-30), in `server/runtimes/claude.ts`, `server/runtimes/claude.test.ts` and `README.md`.

**Checks:**

- `npm run typecheck` is clean, `npm test` passes (506 tests, 5 of them new), and `npm run build` passes.
- New tests:
  - Ready only with both the switch and the token, and the detail never contains the token or an API key.
  - Not configured with the switch alone (points to `claude setup-token`) or the token alone (explains the switch).
  - Exactly one sign-in is passed to a run: the token only in subscription mode, with the API key, auth token and cloud flags removed, and never the token in the default mode.
  - The token is masked in any text, by its variable name and by its `sk-ant-…` shape.
- Mutation checks: four guards were each reverted in turn, and each revert made a test fail. The guards are the token being removed in the default mode, the API key being removed in subscription mode, readiness without a token, and the token alone switching the mode.

**Not verified:**

- A real run with the user's token. Whether the Agent SDK accepts `CLAUDE_CODE_OAUTH_TOKEN` the way the service starts it is confirmed only by that run: Settings shows "ready" from the variables alone, and the token itself is checked on the first run.
- Whether Anthropic permits this use (see Problem and outcome).
