# ORC-017: A demo worth showing (sample story, visual polish, first-run tour, README hero and animated tour)

## Task identity

- ID and title: ORC-017. Make the demo marketable and visually appealing: a believable sample project, a visual polish pass in the existing black-and-white style, a first-run tour, and a README hero image plus an animated tour.
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: Completed, P1. The user asked: "Can you update the demo to be more marketable and visually appealing when you complete the final task". ORC-016 was that final task.
- Specification revision: 2
- Project vision revision: PROJECT_SPEC.md as of 2026-10-01

## Problem and outcome

Observed, in the demo and its README screenshots (`docs/screenshots/board.png`, `overview.png`, retaken 2026-09-30):

- **The sample reads like a test fixture.**
  - The project is "Example Notes (sample)".
  - Simulated breakdown children are titled "Simulated part A (run-1028)".
  - Artifact summaries end in "(sample)".
  - The lead's simulated replies start with "(Simulated)", and so does the focus they set.
  - None of this tells a story a visitor can follow.
- **The value is not visible at a glance.** The README's first claim is progress tracking across several tracks. The app has no view of progress by area: you read it card by card on the board.
- **Dense surfaces.**
  - Cards carry 8–10 chips of equal weight.
  - Explanations run several sentences above every table.
  - Some step purposes contain instructions meant for agents. For example, Change S4 "Verify and integrate" carries "Service check results are the record of what ran; do not say tests passed unless a check result shows it."
  - In Checks settings, each sandbox radio button sits on its own line above its label.
  - At 375 px, the pipeline table scrolls sideways inside its card.
- **No guided first look.** A first-time visitor lands on the Overview with no path through the board, a task, Review and Settings.
- **The README opens with text.** There is no hero image and no motion. Its screenshots are separate feature shots.

Outcome:

- **A believable sample project** whose state tells one story in a minute.
- **Calmer, clearer screens** that keep the black-and-white identity and use colour only for meaning.
- **A short tour on first visit.**
- **A README** that opens with a hero image and an animated tour. Every image can be regenerated by one script.

Everything simulated stays labelled as simulated.

## Scope

Included:

1. **Sample story** (fake runtime only).
   - **A new demo state**, separate from the test fixture `buildSeed()`, which hundreds of tests rely on and which stays unchanged. The fake service starts from it, and Reset sample data restores it.
   - **The sample product: "Weekend Trips (sample)"**, a small app for planning weekend hikes with friends. Its areas (tracks) are Offline maps, Trip sharing, Packing lists, Accessibility and Reliability.
   - **The vision** came out of a shaping conversation with the lead, so the vision history shows an accepted draft, and coverage is complete.
   - **The state shows each capability once, with realistic titles, specs and artifact summaries:**
     - Claude and Codex working in parallel on different tasks;
     - a goal broken into child tasks;
     - a pull request held for you, with its review and passing checks;
     - landed work in the review-later list;
     - a task paused, with the runtime's acknowledgment;
     - a failing check that became a finding and was repaired;
     - a decision that waits for you;
     - one steering exchange (focus moved to offline maps, one task deferred), with Undo;
     - one best-of experiment, labelled experimental.
   - **The fake runtime's generated text matches that story.** It is drawn from per-task scripts, falls back to neutral wording, and no longer produces "Simulated part A (run-N)".
   - **Labelling.**
     - The top banner stays on every page.
     - Lead replies and runs keep a visible "simulated" label as a chip. The "(Simulated)" prefix inside sentences goes where a chip or the banner already labels the content.
     - Nothing simulated is presented as real.
2. **Visual polish** (all modes, not only the demo), keeping black and white as the identity.
   - **Colour carries meaning only:** running, needs you, failed, done, paused or held. Each also has a text label, so colour is never the only signal.
   - **Typography and spacing** follow a clear type scale, consistent spacing and fewer borders.
   - **Card chips are prioritised.** The state, who is working on it and what needs you come first; the rest moves to the task page.
   - **Shorter explanatory text**, with the long form behind "How this works" disclosures where a page needs it.
   - **Light and dark, at desktop and 375 px.**
   - **Fixes included:**
     - The sandbox radios sit inline with their labels.
     - The pipeline gets a stacked phone layout.
     - Agent instructions move out of step `purpose` text in the built-in patterns. They are not lost: each moves to the role brief or the envelope, which the agent already receives.
3. **Progress by area on the Overview.**
   - One row per area: done out of total, what is running and on which provider, what is waiting for you, and a bar.
   - Choosing a row opens the board filtered to that area.
   - It is derived from existing task state; no new state is stored.
4. **First-run tour.**
   - About six stops, each one or two sentences: the simulated banner, progress by area, the board, a task's pipeline (provider and model per step, Pause), Review, and the lead.
   - It starts on the first visit to the demo, can be skipped, and is replayed from a "Tour" button.
   - Whether it was seen is kept in the browser (a per-viewer convenience). It is wrapped so blocked storage never breaks the page.
   - It is built on driver.js (MIT, pinned).
   - It is keyboard operable and respects reduced motion.
   - Real mode keeps its existing Get started steps and does not start the tour.
5. **README media.**
   - **A capture script,** `scripts/capture-demo.mjs`.
     - It starts a fake service in a throwaway data directory and drives Chrome with playwright-core (Apache-2.0, pinned dev dependency, using the installed Chrome).
     - It writes every README screenshot, a hero image and an animated tour (ffmpeg, which must be installed; the script says so if it is not).
     - It never touches the real `~/.orchestration`.
   - **The README** opens with the hero image and shows the animated tour (under 5 MB) near the top. All screenshots are retaken.
6. **Tests:**
   - the demo state is valid (it passes the state validators and migrations, and every pattern reference resolves);
   - the fake runtime's text never claims a real run;
   - the progress-by-area derivation;
   - tour storage failure;
   - the moved step-purpose text still reaches agents through the envelope.

Excluded:

- Hosting a public live demo.
- Changing what the real runtime does.
- Marketing copy that claims capabilities without evidence. In particular, real Claude and Codex runs remain unverified in this environment, and the README keeps saying so.
- A new font download at run time. If a typeface is added, it is bundled locally.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Separate demo state and story-aware fake text; polish the existing UI in place; tour on driver.js; scripted capture with playwright-core and ffmpeg | A coherent story, better UI everywhere, reproducible media | Medium–large | Two sample states to maintain (fixture and demo); two dev tools (one dependency, one system tool) | High |
| B | Rewrite `buildSeed()` itself as the story | One sample state | Medium | Breaks or rewrites many tests that pin sample ids and text; test churn hides real regressions | Medium |
| C | Marketing-only assets (a designed hero and a scripted video), app unchanged | Fast | Small | The demo people run would not match the README; violates "no claims without evidence" in spirit | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: Lead.
- Rationale and evidence:
  - The fixture's stability is what keeps the 878-test suite meaningful, so the story gets its own state.
  - Polishing the real UI makes the README truthful: the images are the app.
  - driver.js and playwright-core are mature open-source tools, which follows the user's direction to prefer them.
- Uncertainty and what would change the decision:
  - Whether the animated tour fits in 5 MB as a GIF. If not, it becomes an animated WebP, or an MP4 linked from the README.
  - Whether a bundled typeface is worth its weight. The design pass decides and records why.

## Acceptance and validation

- **The demo story.**
  - A fresh demo (or Reset sample data) shows "Weekend Trips (sample)" with five areas.
  - The board shows Claude and Codex runs in parallel, a pull request held for you, a paused task with its acknowledgment, a decision waiting for you, and a goal with child tasks.
  - No visible title or summary contains "Simulated part", "(sample)" or a run number used as a name.
  - The banner and the simulated chips are present.
- **Progress by area.** The Overview lists each area with its counts, and choosing one filters the board.
- **The tour.**
  - It starts once on a first visit to the demo and not again after Skip or Done.
  - The Tour button replays it.
  - With storage blocked, the page still renders, and the tour simply starts each visit.
  - It does not start in real mode.
- **Visual pass.**
  - Light and dark, at 1360 px and 375 px, on the Overview, the board, a task, Review, the pull-request card, Settings → Checks and Settings → Patterns.
  - No horizontal page scroll at 375 px.
  - Every state colour is paired with a text label.
- **Built-in patterns.** Their step purposes are plain descriptions. The moved instructions appear in the envelope (tested).
- **Media.**
  - `node scripts/capture-demo.mjs` regenerates every image in `docs/screenshots/` and the hero and tour media, from a throwaway data directory.
  - The README shows them, and the tour file is under 5 MB.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build`;
  - an independent review;
  - a browser pass by the lead covering the list above.

## Execution plan

Branch `demo-polish` from `main`, after ORC-016 merges. One integration owner: the lead.

**Design comes first.** The lead runs the impeccable design skill to set the direction:

- the type scale, tokens and state colours;
- the card hierarchy;
- the progress-by-area layout;
- the tour stops.

It is recorded in `docs/design/ORC-017-design.md`, with the story script: every sample task, its state and its text.

**Then two coders work in parallel, with disjoint files:**

- **The story** (B1): `src/domain/demo.ts` (new), the fake runtime's text, `server/app.ts` (choosing the demo state), and tests.
- **The UI** (B2): `src/ui/**`, the tour, progress by area, the built-in pattern purposes with the envelope change and its test, and tests.

**Then:**

- the capture script and README (B3), after B1 and B2 integrate;
- an independent review;
- fixes;
- the browser pass;
- a pull request, merged after CI passes. The user authorised merging feature pull requests once CI passes.

**Constraints:** no state-format change is expected. If one becomes necessary, it comes with a migration and a test.

**What integration found and fixed:**

- The tour could not start on a first visit, because `/` opened Tasks. The demo's bare address now opens the Overview.
- Skip, Esc and Done did not record the tour as seen, because driver.js calls `onDestroyed` only while it holds an element. The end is now handled in `onDestroyStarted`.
- The header counted service check runs as agents.
- An agent instruction remained in the internal revert pipeline's purpose.

**Review fixes, each with a test that fails when the fix is reverted:**

- Simulated checks now key a task tree by its root, so the demo's pull requests are held for you rather than failing (M4).
- Area labels name paused, deferred and waiting tasks, and say "in progress" (M1, M3).
- The board's area filter matches the counts (M2).
- Duplicate live lines are collapsed (L7).
- The simulated lead counts only its own lines as exchanges (L2).
- Also fixed: L4, L5, L6, L8 and L9.
- **Declined: L1, starting the demo on Autopilot.** A planning run at start would break the story's opening state: three agents at the limit, WT-003 next. The demo stays on "Manual", which is truthful.

**Media pass fixes:**

- The board uses the full width and names its empty columns in one line.
