# ORC-032: Import an existing project into Vision

## Task identity

- **ID and title:** ORC-032. Reverse-engineer an "as-is" vision from an existing repository, so an existing product can be revised and built on through the living design surface.
- **Author and timestamps:** Lead (Claude), 2026-10-02; r3 2026-10-03.

  - The owner's main real use (SimpleApps) is existing projects, so this comes early.
  - It is the last feature milestone for now.
- **Specification revision:** 3.
- **Project vision revision:** PRODUCT.md "The core problem" (2026-10-02); ORC-029 r12.
- **The design:** `docs/design/ORC-032-design.md` (the data, the rules, the readers, security and the units). The prototype: `docs/design/ORC-032-prototype.html` (sample data: tally, an invented CLI).

## Problem and outcome

**Where it fits.** ORC-029 makes Vision a living design surface for the whole product (r11). It starts from an idea, optionally with materials the owner brings. An existing repository has no vision at all, only code, tests, docs and config. Its design lives in the code, which is exactly where the owner does not want to look.

**The outcome.**

- **The import derives an as-is vision** of what the product is today, as parts organised by project domain (ORC-029 r9).
  - **Screen products:** the app runs in the project's environment, and the service records each key screen or command-line demo.
  - **Code products:** the public interface, usage examples from the README and tests, and the core algorithms in plain pseudo-code.
  - **Infrastructure systems:** the topology from config (compose files, IaC, CI and deploy scripts).
  - **Rules and edge cases come from the tests.** Each rule belongs to a part and names the existing tests that prove it.
- **Every rule carries its sources and a confidence:** confirmed (its tests pass), inferred (nothing proves it), or a conflict (a test fails, or two sources disagree).
- **The import is a review round:** round 0, "As it is today". The owner answers only the conflicts and the important guesses. That is the alignment loop of PRODUCT.md's core problem.
- **The owner's baseline Lock in makes it the baseline,** in force and built. After that, a change is an ordinary design round, and the first one starts the factory through the pre-flight.
- **The vision stays local.** No file in the repository changes.

## Scope

**In scope.** The import from the new-project screen, its budget, its reading (the tests, the rules, the parts, the words, the capture), the review, the baseline Lock in, and Design and reality after it. The demo: the import works on a bundled sample repository (tally) with the simulated runtime.

**Out of scope.** Importing into a project that has Vision rounds already. A second import of the same project (start a new project). Writing anything into the repository.

**What exists.** ORC-029 pass 4's lead-driven round 0, "as it is today": the designer reproduces parts as "as is" artifacts, each with the repository files it came from. The import replaces it (C12). The project environment (E1, E2) runs the tests and records the app; ORC-031's helpers serve the rules reader.

**The steps:**
1. **Start.** On the new-project screen, "Import an existing repository": the path and the commit it reads, the kind of product and the devices (each prefilled with its reason), how it runs (C1), who reads it (Claude by default), the helpers switch, and the import budget beside the estimate.
2. **Reading (research steps, read-only).** The checks run the tests once, in the project's environment with no network. The rules reader turns the tests and the code into rules, each in an EARS pattern with its tests and sources. The parts designer reproduces each part with its rules. The words designer collects the product's terms. The capture records each screen and command-line demo. The spend shows against the import budget; at the budget, the import's runs wait for the owner.
3. **Review (round 0, As it is today).** Each rule carries its confidence. The owner answers the conflicts and the important guesses (at most 10); confirmed rules and the parts are listed, and each has "Correct". An answer keeps the code, asks for a change, or fixes a misreading (a designer's next version of the part, before the Lock in).
4. **Baseline.** The owner accepts the vision draft and locks the baseline in: every part goes into force as built. Changes the owner asked for wait as change requests.
5. **After.** Design and reality shows each part: "built and verified" where its rules' tests pass and its recording has no failure, else "built, not verified" with the first gap, or "fails a check". The factory has nothing to build until the owner changes the design; the first change goes through the pre-flight.

## Acceptance and validation

**Unit 1, the domain** (each with a test that failed first; `src/domain/studio/import.test.ts`, `server/import.store.test.ts`):
- The confidence table, row by row, and the refusal of an unknown test id.
- Question choice: conflicts first, at most 10, a stable order.
- Each answer's effect, including an answer after the Lock in.
- `lockInBaseline`: only the owner's; only in Vision; only while there is no revision; compare-and-set on the draft and the digest. Revision 1 carries the baseline. The store refuses any other command that adds a revision.
- The statuses: built and verified, built and not verified (each gap), fails a check, in force. After a newer version is in force, the factory's rules apply.
- Rule results: a test proves a line by its id, and the baseline run counts at the Lock in's time.
- The Lock in summary has no new work for baseline items, and the rest of the build leaves them out.
- Spend: the split at the baseline Lock in; the import's stop; unknown costs.
- A format-19 database without the new fields loads unchanged.

**Unit 2, the server:** the whole import on the tally fixture with the fake runtime; the reader's output checked at the boundary; read-only access and helpers; the budget and pause; no Docker; the pass-4 round removed. A test proves that no tracked file or branch of the repository changes.

**Unit 3, the UI:** each screen's states as in the prototype, with C1, C5, C7, C8 and C9; the QA journey `import.mjs` at 1280 and 375, with no horizontal scroll and no console error.

**Checks:** `npm run typecheck`, `npm test`, `npm run build`, `npm run test:integration`, `npm run qa`.

## Execution plan

Three units (the design, section 8):
1. **Unit 1, the domain.** Phase A: the types, the commands and their guards, the state builders. Phase B: the derivations.
2. **Units 2 (the server) and 3 (the UI)** start from phase A, in parallel.
3. **The lead integrates** the units on `orc-032`, then the independent review, QA and one simulated import of tally.

## Workflow steps and model selections

Each unit is one implementer session in its own worktree, then an independent code review and QA. Real paid runs only within the owner's trial budget, if the owner allows them.
