# ORC-032: Import an existing project into Vision

## Task identity

- **ID and title:** ORC-032. Reverse-engineer an "as-is" vision from an existing repository, so an existing product can be revised and built on through the living design surface.
- **Author and timestamps:** Lead (Claude), 2026-10-02.
- **Status, priority, and priority rationale:** **Planned, not started; P1.** The owner, 2026-10-02: "We also need to think about how this could reverse engineer a vision when starting from an existing project - like import esque and after imported we can update the vision to make a change etc."
  - The owner's main real use (SimpleApps) is existing projects, so this comes early.
  - Recommended order: after ORC-029 and ORC-031, before ORC-030.
- **Specification revision:** 1.
- **Project vision revision:** PRODUCT.md "The core problem" (2026-10-02); ORC-029 r12.

## Problem and outcome

**Where it fits.** ORC-029 makes Vision a living design surface for the whole product (r11). It starts from an idea, optionally with materials the owner brings. An existing repository has no vision at all, only code, tests, docs and config. Its design lives in the code, which is exactly where the owner does not want to look.

**The outcome.**

- **The import derives an as-is vision** of what the product is today, organised by project domain (ORC-029 r9).
  - **Screen products:** the app is started in the sandbox (a container; ORC-029 pass 3), and each key screen is captured and becomes a design item. Flows come from routes and navigation, and the product's things and their relations come from schemas and types.
  - **Code products:** the public interface (exports, signatures, docs), usage examples from the README and tests, and the core algorithms summarised in plain pseudo-code.
  - **Infrastructure systems:** the topology from config (compose files, IaC, CI and deploy scripts).
  - **Rules and edge cases come from the tests.** Tests are where a project has already written down its decided cases, so each becomes a row in a table of cases and outcomes.
- **Every derived item carries its provenance and confidence,** for example "from tests, confirmed", "from code, guessed", or "conflicting: tests and docs disagree".
- **The import is a review round.** The owner confirms or corrects the guesses and conflicts first. That is the alignment loop of PRODUCT.md's core problem.
- **The owner's Lock in makes it the baseline.** After that, a change is an ordinary draft and Lock in, and the factory builds it.
- **The derivation is wide, read-only research,** so it may use subagents (ORC-031), and runs only in steps explicitly marked as research.
- **The vision stays local** (the owner, 2026-10-02: "it might best to keep vision things local"). Nothing is written into the repository.

## Scope, options and plan

Written when the milestone starts.

**The open design question** is how much to infer versus ask. The lead's default: infer what the code and tests show with high confidence, and ask only where confidence is low or sources conflict.
