## Problem and outcome

**Where it fits.** ORC-029 makes Vision a living design surface for the whole product (r11). It starts from an idea, optionally with materials the owner brings. An existing repository has no vision at all, only code, tests, docs and config. Its design lives in the code, which is exactly where the owner does not want to look.

**The outcome.**

- **The import derives an as-is vision** of what the product is today, organised by project domain (ORC-029 r9).
  - **Screen products:** the app is started in the sandbox (a container; ORC-029 pass 3), and each key screen is captured and becomes a design item. Flows come from routes and navigation, and the product's things and their relations come from schemas and types.
  - **Code products:** the public interface (exports, signatures, docs), usage examples from the README and tests, and the core algorithms summarised in plain pseudo-code.
  - **Infrastructure systems:** the topology from config (compose files, IaC, CI and deploy scripts).
  - **Rules and edge cases come from the tests.** Tests are where a project has already written down its decided cases, so each becomes a row in a table of cases and outcomes.
- **Every derived item carries its provenance and confidence,** for example "from tests, confirmed", "from code, guessed", or "conflicting: tests and docs disagree".
- **The import is a review round.** The owner confirms or corrects the guesses and conflicts first. That is the alignment loop of PRODUCT.md's core problem.
- **The owner's Lock in makes it the baseline.** After that, a change is an ordinary draft and Lock in, and the factory builds it.
- **The derivation is wide, read-only research,** so it may use subagents (ORC-031), and runs only in steps explicitly marked as research.
- **The vision stays local** (the owner, 2026-10-02: "it might best to keep vision things local"). Nothing is written into the repository.

## Scope, options and plan

Written 2026-10-03, when the milestone started. It is the last feature milestone for now (the owner).

**What exists (ORC-029 pass 4, the first slice).** For a repository that has code, the lead's first Vision round is "as it is today": the designer reproduces the key screens, the interface and core algorithms, or the topology, as artifacts marked "as is", each with the files it came from (`provenance.files`, checked against the repository at HEAD; `server/studio/existing.ts`). The owner corrects them, and later rounds revise them. What it lacks:
- the rules and edge cases the tests hold;
- a confidence per item, and conflicts between sources;
- a review that asks the owner only what the code cannot answer;
- a baseline that counts as built: today an "as is" part goes through the draft and the pre-flight like a new design, and Design and reality calls it "designed".

**The import, step by step (the lead's proposal):**
1. **Start.** On the new-project screen, "Import an existing repository": the path, the kind of product (prefilled from what the repository shows), the devices, and an import budget with the PE's estimate.
2. **Read (research steps, read-only, helpers allowed: ORC-031).** In parallel:
   - **the parts:** the designer reproduces the screens or CLI demos (the app runs in the project's environment, and evidence captures it, as in E2), the interface, the topology;
   - **the rules:** one reader turns each test into a rule in the "If …, then …" form, tagged with its test (`[it-3 R2]`), so the rule's test is already known;
   - **the words:** the product's own terms, from the README, the docs and the names in the code.
3. **Review (a round the owner answers).** Each item carries its source and a confidence: **confirmed** (a passing test or the running app shows it), **inferred** (read from the code, nothing proves it), or **conflict** (two sources disagree, for example the README and a test). The owner sees the conflicts and the inferred items that matter first; confirmed items are listed, not asked.
4. **Baseline.** The owner's Lock in makes the reviewed items the baseline. They are **in force and built**: a part whose rules' tests pass reads "built and verified", with the captured screen as its evidence. The factory has nothing to build until the owner changes something.
5. **Change.** From then on, a change is an ordinary draft, Lock in and change order.

**The choices for the owner (each with the lead's recommendation first):**

| Choice | Options |
| --- | --- |
| How much to ask | **A, ask only about conflicts and important guesses** (confirmed items are listed, not asked; recommended); B, ask about every item; C, ask nothing, and the owner corrects later |
| What the baseline is | **A, built: the import's items are in force and count as built, verified where their tests pass** (recommended); B, a draft: the items go through the pre-flight and Start the factory, as a new design does |
| Where the import starts | **A, the new-project screen: "Import an existing repository"** (recommended); B, a message to the lead in an empty project |
| What it may cost | **A, its own import budget, $3 by default, with the PE's estimate before it starts** (recommended); B, inside the building budget |

**Safety.** The import only reads: research steps, the read-only checkout, and the app run in the project's environment with no network. Nothing is written into the repository, and the vision stays on this computer.

**Proof.** A prototype of the screens with sample data first, for the owner's marks. Then the build, the QA journeys at both widths, and one import on a small sample repository: simulated, and real within the owner's trial budget if the owner allows it. The owner's own repositories are the owner's to try.
