# ORC-009: Steering by conversation

## Task identity

- ID and title: ORC-009, steering by conversation. When you give direction, the lead changes the focus, reorders work, defers work that no longer fits, and drops its own unstarted proposals. Every change is listed, attributed and undoable.
- Author and timestamps: Lead (Claude), 2026-09-29
- Status, priority, and priority rationale: Completed, P1. The user asked for this directly: "I want to be able to chat with the lead if I want to steer while it works, for example I want it to focus more on building out the apps working locally vs focus automating the deployment process." Today the lead can only reply and propose new tasks, so every redirection is manual: editing the focus, priorities and pauses by hand. That works against the user's preference for autopilot with optional human review.
- Specification revision: 1
- Project vision revision: PROJECT_SPEC.md as of 2026-09-29. The relevant lines:
  - l.17: the user steers or redirects the lead.
  - l.44: new direction becomes a recorded vision revision or task edit, linked to affected work.
  - l.98: the lead refines its plan while respecting the user's holds and latest vision.
  - l.102: no worker resumes a user-paused task.
  - l.162: explicit user selections are pinned.

## Problem and outcome

Observed. These come from a read-only trace of the code; no model runs were made.

- **The lead cannot change existing work.** Its output is only a reply plus new proposals (`completeLeadRun`, src/domain/model.ts:1517-1573). It cannot change the focus, reorder the backlog, or stop anything already on the board.
- **A message sent during planning waits and gets misanswered.** It waits for the planning run to finish, which can take up to the 20-minute run limit. That run's old-focus proposals are then applied, and its reply appears right after the user's message, as if it were the answer. The UI shows only "Lead is working…", so the queued message is invisible.
- **The lead is hard to reach.** The conversation exists only on the Overview. The board and task pages cannot reach the lead.
- **Lead changes could not be told apart from the user's or undone.** Nothing records who set a priority. Cancelling cannot be undone (`assertOpen`).
- **The obvious mechanisms would lie.** `hold` would make "pause" untruthful: a result arriving while `hold` is set is discarded (model.ts:932-936). Resume also clears every kind of hold at once.

The user's job is to redirect the whole team in one sentence while work continues, see exactly what changed, and undo any of it with one click, without reading code or approving each change.

Outcome:

- **Reach and response.** The user can tell the lead what to focus on from any page. A planning run in progress is stopped so the message is answered next. A message that has to wait says why.
- **Steering in the reply.** A lead reply to a user message can carry a steering block. The service checks each item, applies what is allowed in the same transaction that records the reply, and writes the authoritative list of changes under it. The possible changes are:
  - **Focus:** a new current focus. It is a vision revision authored by the lead, linked to the message, with the reason and a diff.
  - **Priority:** new priorities for open root tasks. Only the next free worker slot is affected; running work continues.
  - **Defer:** the current step finishes and its result is kept, and then nothing new starts on that task or its child tasks. Deferring never interrupts, and it is never shown as "Paused".
  - **Drop:** the lead may drop its own unstarted proposals. A drop can be reopened.
- **Undo and control.**
  - Each change has Undo, and the reply has Undo all.
  - A setting makes the lead apply changes to its own work only, or only suggest (Apply and Dismiss).
  - Choices the user made by hand are never overridden. The lead's change to one of them becomes a suggestion instead.
- **Later planning.** Later planning follows the new focus. Deferred work and recently dropped work are not proposed again, and the lead sees what the user undid.

## Scope

Included:

- **Domain:**
  - Steering change sets.
  - A deferral that only dispatch checks.
  - Drop and reopen for the lead's unstarted root proposals.
  - User pins for priority and for "keep running whatever the focus".
  - Stale-result protection: the vision revision is recorded on each lead run, and newer user direction turns a finished reply's changes into suggestions.
  - Planning preemption and an "answer together now" control.
  - A derived message status.
  - The steering mode.
  - Child tasks follow their root's deferral and priority tier.
  - A state format 10 migration.
- **Service:**
  - A steering section and output contract in the lead envelope, for message runs only.
  - An open-work board view listing the actions allowed on each task.
  - Focus history, and the recent steering with what the user undid or dismissed.
  - Parser and scheduler pass-through, with parse problems surfaced.
  - Simulated steering in the fake runtime, labelled as simulated.
  - ScriptedAdapter support.
- **UI:**
  - A Lead drawer from the header on every page.
  - A Steer button, a focus banner and a Deferred column on the board.
  - "Ask the lead about this task", plus deferral and priority-source banners, on task pages.
  - The change list with Undo, Undo all, Apply, Apply all and Dismiss.
  - Vision history and diff.
  - The Settings choice.
  - Notifications.
  - Updated copy.
- **Docs:**
  - This spec.
  - A note appended to ORC-005 (its executed text is not rewritten).
  - The README capability and prompt-injection note.
  - "Deferred" added to the PROJECT_SPEC state list.
- **Evidence:** a `--lead` mode in scripts/real-run-test.mjs, and one Claude-led and one Codex-led steering run on a scratch repository.

Excluded:

- **What the lead may not do:**
  - Pause or interrupt running work.
  - Release any hold (a user pause, a review gate, or a hold before start).
  - Resume tasks.
  - Cancel anything other than its own unstarted root proposals.

  These stay with the user. The change list offers "Pause now" and "Cancel instead" as the user's own one-click controls, and they use the existing truthful Pausing and Cancelling paths.
- **What the lead may not edit:**
  - the vision text
  - specs and pipelines
  - step model pins and role overrides
  - best-of choices
  - settings, autonomy, and the steering mode
- **ORC-008's area:**
  - done tasks
  - integration and delivery state
  - `autonomy.autoDeliver`
  - pull-request holds and review queues
- **Injecting a message into a lead run that is already working.** No adapter supports live steering (PROJECT_SPEC l.142, l.175). Redirecting a busy lead means stop, confirm, re-run.
- **Lead runs while the whole project is paused.** This is an open product question.
- **Planning runs changing anything other than proposing.** This bounds the prompt-injection path through worker-written summaries (README "Autopilot" note).

Superseded decision: ORC-005 excluded "The lead editing existing tasks' specs or pinned choices… The user keeps control of existing work". ORC-009 narrows that exclusion. The lead may now:

- change the focus
- change the priority and deferral of open root tasks
- drop its own unstarted proposals

It may do these only when answering the user's messages. Specs, pipelines, pins and selections stay excluded, and the user keeps every control.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | **Structured verbs.** An `actions[]` list with setFocus, setPriority (the model supplies the current value as `from`), defer, resume and cancel. The mode lives in Autonomy. Every new message stops any lead run. | Fine-grained control, with a strong safety matrix | Large (about 1,700 lines) | The model must echo current values, which is error-prone. "Resume" collides with the task Resume control. It overlaps ORC-008 in `setAutonomy` and `applyAutopilot`. Stopping every run on every message wastes cost and thrashes. | High |
| B | **Focus and ranking.** The lead lists `ranking` and `later`. A fixed service policy renumbers tasks into bands (P1–P40, P60+) and parks the lead's off-focus work. | The smallest model task, and deterministic | Large (6–8 days) | Band renumbering churns many priorities and puts ranked tasks behind untouched ones. The user's own off-focus tasks are only demoted, so on autopilot they keep taking free slots. The lead cannot remove even its own proposals. | High |
| **C (selected)** | **One optional `steer` object:** a new focus, plus per-task priority, defer or drop. One permission function drives both the envelope and the apply-time checks. The service writes the change list. Deferral is checked only by dispatch. Planning runs are preempted. The mode is a Project setting with its own command. | Direction takes effect at once, and it is visible, attributed and undoable. The lead is reachable from any page. | Large (about 5–6 days) | There is a new Deferred state to learn. The model may over-steer; this is bounded and undoable. It shares the format bump with ORC-008. | High: every change has compare-and-set Undo, and a drop can be reopened |
| D | **Status quo plus a drawer.** The lead replies and proposes; the user edits focus, priority and pauses by hand. | No new lead powers to trust | Small | Does not meet the request: steering stays manual | High |

Key sub-decisions:

| Question | Selected | Alternatives rejected |
| --- | --- | --- |
| How work that no longer fits stops | **Deferral**, a flag only dispatch checks. The running step finishes and its result is accepted. | `hold`: it discards the running result, Resume clears every hold, and the task would read "Paused by you". `holdBeforeStart`: it stalls started tasks under the false label "Queued for next step". |
| What the lead may cancel | Only its own unstarted root proposals with no open dependents, recorded so they can be reopened | Cancel anything: irreversible, and it blocks dependents. Never cancel: old-focus proposals clutter the board and the cap. |
| Responsiveness | A message stops a planning run. A reply run is not stopped automatically; "Answer together now" is offered instead. A reply that finishes after newer direction only suggests. | Stop every run: cost and thrash. Stop nothing: up to 20 minutes behind planning. |
| Which runs may steer | Runs that answer user messages (`messageIds` not empty) | Planning runs as well: they read worker-written summaries |
| Apply or suggest | **Apply by default**, following the user's autopilot preference. Settings also offers "apply to the lead's own work, suggest for mine" and "only suggest". A pinned field always becomes a suggestion. | Suggest by default: slow, against the user's preference. Follow the involvement preset: this ties the choice to Autonomy code that ORC-008 edits. |
| Child tasks | Steer roots only. Deferral and priority tier are derived from the root. | Writing children one by one: Undo would touch many fields, and a single deferred child would stall its parent's wait for its children. |
| Preconditions | Recorded by the server: the run's vision revision, the user's pins, and the current state at apply time | Values supplied by the model |

## Decision

- Agent recommendation: C
- Selected option: C, with grafted ideas:
  - **From A:**
    - a 7-day guard against re-proposing dropped work
    - at most 20 task changes per reply, and one per task
    - parse problems surfaced instead of dropped
    - "Pause now" on a running deferred task
    - Undo and applied suggestions set pins, so the lead cannot redo what the user reversed
    - race, restart and duplicate-event tests
    - a `--lead` evidence mode
    - the middle mode, "apply to the lead's own work"
  - **From B:**
    - a dependency guard
    - a separate bound on deferred proposals
    - newer direction turns a finished reply's changes into suggestions
    - an "Auto" default priority in the New task form, where choosing a number pins it
    - a deterministic change-set snapshot test
    - the user's own example as the end-to-end scenario

  B's `new:i` reference was considered and not taken. Proposals already carry their own priority, and they are created after the focus and task changes.
- Decided by: Lead
- Rationale and evidence:
  - **Smallest safe surface.** C gives the model the smallest vocabulary that meets every part of the request. That vocabulary is focus, priority, defer and drop, and the service stays the authority. A single permission function both tells the lead what it may do and enforces it against the current state.
  - **Truthful states.** Deferral is the one way to stop off-focus work that keeps states truthful. Nothing is interrupted and no result is discarded, and "Paused" still means a pause the runtime confirmed.
  - **Answers promptly without extra cost.** Preempting planning (and nothing else) removes the up-to-20-minute wait without the cost and thrash of stopping every reply.
  - **Less overlap with ORC-008.** Keeping the mode out of Autonomy avoids editing the code ORC-008 is changing.
  - **Judged best.** An independent judgment scored the three candidate designs 7, 6 and 8, with C highest. Every defect it listed as must-fix is addressed in the technical design (the table in §18).
- Uncertainty and what would change the decision:
  - Real Claude and Codex leads may follow the steering contract poorly. The real runs will show this; the response would be to simplify the contract toward option B's ranking.
  - The user may object to the lead deferring tasks they created without asking. The response would be to change the default to "apply to the lead's own work".
  - If the Deferred column confuses the user, show deferred tasks as a filter instead of a column.
- User override, if any: none yet. The user can change the steering mode in Settings at any time.

## Acceptance and validation

1. **The user's own example**, in the simulated runtime and in scripted tests. The user sends "focus more on building out the apps working locally vs automating the deployment process" from the board's Steer button, or from a task page. After one lead reply:
   - The board banner and the Overview show focus rN, set "by the lead from your message", with a diff and Undo.
   - Under the reply, the service-written change list shows every change: the focus, P a→b, "Deferred (after its current step)" and "Dropped (had not started)". Each row shows the task's live state and has Undo, and the list has Undo all.
   - Suggestions show Apply and Dismiss. Items not changed show why, for example "you set P3" or "T-012 depends on it".
   - A deployment step already running is not interrupted. It finishes and its result is accepted; the task then shows "Deferred by lead" in the Deferred column, and no next step starts.
   - Priorities the user set by hand are unchanged and appear as suggestions.
   - The next planning run proposes toward the new focus and does not propose deferred or dropped work again.
2. **Undo.**
   - Undo all restores every value that nobody has changed since.
   - A value the user changed since is left alone and reported.
   - Undoing a focus change creates a new revision authored by the user.
   - A second Undo reports "already undone".
   - An undone change cannot be redone by the lead, because Undo sets a pin; it can only be suggested again.
3. **Responsiveness.**
   - A message sent during a planning run shows "Stopping planning to answer you". The planning run's proposals are discarded. The reply run starts on the first tick after the runtime confirms the stop (about 2.5 s simulated, 15 s or less plus settle time in real mode).
   - A message sent during a reply run shows "Queued behind the current reply", with "Answer together now".
4. **Newer direction wins.** A reply applies nothing if it finishes after the user wrote again or edited the vision. Its changes appear as held suggestions, and the next reply decides.
5. **Truthful states.**
   - The lead never pauses, stops, resumes or releases anything.
   - "Paused" appears only after the runtime confirms a pause the user asked for.
   - Deferred work never appears as Paused.
   - A deferred task whose last step completes still becomes Done and is queued for integration.
6. **Safety.**
   - Planning runs cannot steer.
   - Invalid items are rejected one by one with reasons, while the valid ones apply.
   - A reply may change at most 20 tasks and the focus once.
   - Nothing touches done tasks, integration, delivery, specs, pipelines, pins or settings.
   - A drop or a deferral never leaves another open task waiting or blocked.
7. **Modes.** The "Only suggest" and "Apply to the lead's own work" modes behave as specified. The current mode is shown on the composer and set in Settings.
8. **Reach.**
   - The Lead drawer opens from every page and stays open while the user navigates the board.
   - "Ask the lead about this task" sends the task as context.
   - Keyboard use, Esc, and a 375 px width all work.
9. **Persistence and interruption.**
   - Change sets, pins and deferrals survive a restart, and Undo works after a restart.
   - A lead run lost to a restart applies nothing.
   - A duplicate completion applies once.
   - A format 9 database migrates to format 10.
10. **Checks and evidence.**
    - `npm run typecheck`, `npm test` and `npm run build` pass.
    - A browser pass covers light and dark themes and 375 px, with screenshots.
    - Mutation checks: reverting each key guard makes a test fail. The guards are the deferral placement, the message-run gate, the newer-direction downgrade, the dependency guard, the pins set by Undo, and the change-set idempotency.
    - Real Claude-led and Codex-led steering runs on a scratch repository (not SimpleApps) produce valid steering that applies and undoes, with evidence JSON.

    Support for mixed-provider steering is not claimed before these real runs pass.

## Execution plan

- **Branch and workspaces.** Branch `steering`, with each worker in an isolated worktree. Merge into `main` through a pull request after CI and an independent review. The lead is the single integration owner.
- **ORC-008 sequencing.** Whichever of ORC-008 and ORC-009 merges second renumbers its migration (10→11) and rebases its changes to types.ts, model.ts, store.ts, seed.ts and Settings.tsx. ORC-009 adds nothing to `Autonomy`, `Integration` or `project.delivery`.
- **Fixed interfaces**, published before any worker is dispatched. The authoritative definitions are in the technical design (§4 and §10):
  - the types: `SteeringChangeSet`, `SteeringChange`, `Deferral`, `Task.userSet`, `Task.deferral`, `Task.dropped`, `Project.steeringMode`, `LeadRun.visionRev`, `Message.changeSetId` and `Message.taskId`
  - the command names and arguments
  - the `parseLeadOutput` return shape
  - `steerPermission(s, t, action, mode)`
  - `messageStatus(s, m, opts)`
  - `deferredBy(s, t)`
- **Workers** (three, with disjoint files, against spec r1):
  - **W1, domain:** types.ts, model.ts, commands.ts, seed.ts, store.ts (migration), src/domain/steering.test.ts, and model.test.ts updates.
  - **W2, service:** envelope.ts, scheduler.ts, runtimes/fake.ts, testing/scripted.ts, server/steering.test.ts, and updates to teamloop.test.ts and service.test.ts. It starts against stubs of W1's exports.
  - **W3, UI:** App.tsx, a new LeadDrawer.tsx, a new SteeringChanges.tsx, Conversation.tsx, Board.tsx, TaskDetail.tsx, Overview.tsx, Settings.tsx, common.tsx, notifications.ts and styles.css.
  - **The lead** owns the docs, README, PROJECT_SPEC, the ORC-005 note, scripts/real-run-test.mjs `--lead`, integration and evidence.
- **Checks per worker:** `npm run typecheck`, `npx vitest run` on the worker's own test files, and the full suite before handing off.
- **Effort checkpoint.** Re-estimate after W1 lands with its domain tests green. If the remaining work exceeds about four days, move the vision-history UI and the "apply to the lead's own work" mode to a follow-up. The core guards and Undo stay.
- **Recovery.** A stalled or failed worker run is stopped and re-run as a new attempt, handing over its committed branch state as an artifact. A switch of provider is recorded as a new run, not as a resume of the old session.
- **Hold state.** None. This spec is published, not gated. The user may pause, edit or cancel it at any time.
