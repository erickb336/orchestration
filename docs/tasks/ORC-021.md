# ORC-021: Flows (simplify the pattern catalog)

## Task identity

- ID and title: ORC-021. Replace the "pattern catalog" with six plain **flows**, and remove the machinery that made it complicated.
- Author and timestamps: Lead (Claude), 2026-10-01
- Status, priority, and priority rationale: Done, P1. The owner found the catalog confusing and overengineered:
  - "these patterns may have been overengineered";
  - "I actually liked all the flows you originally had but this pattern confusing added unnecessary complexity";
  - asked whether we needed the pattern catalog at all ("we don't really need this pattern catalog at all then?").

  The owner then agreed the plan in this spec ("Yes let's do that"). The Compare feature (ORC-018) was scrapped the same day.
- Specification revision: 2
- Project vision revision: PROJECT_SPEC.md and PRODUCT.md as of 2026-10-01

## Problem and outcome

**What went wrong.** ORC-016 replaced the editable pipeline with a catalog of eleven JSON "patterns", and added a lot around them:

- personal pattern files with `extends` and `stepOverrides`;
- a "standard" vs "yours only" audience;
- experiments with hypotheses;
- pause variants;
- version hashes for comparison;
- a Settings → Patterns page with Reload and file errors;
- outcome records for a comparison view that will not be built.

**What the owner values instead:**

- a lead that understands the flow and its loop;
- stages isolated from each other;
- context carried between stages as artifacts that are reviewable, editable and retryable.

**Terminology.** "Pattern" was also the wrong word. For the owner, a pattern is the *shape* of a multi-agent setup, as in maker-checker, concurrent or hierarchical. The eleven files were not shapes: they were kinds of work.

**Outcome:**

- **Six flows,** each a small JSON file in the repository's `flows/` folder, changed in code: Change, Bug fix, Feature, Design, Investigation, Goal.
- **Who picks.** The lead picks a flow per task, and you can pick or change one.
- **The default.** Change is the project default.
- **Nothing else to learn.** The engine (stages, artifacts, loops, per-step provider and model, pause, edit, rerun) is unchanged.

## Scope

**Included:**

1. **Rename "pattern" to "flow" everywhere a person or an agent reads it.** That means the UI, the lead's instructions, the README, and docs written from now on. Rename the code identifiers too, so the code says what the product says: `Pattern` → `Flow`, `PatternRef` → `FlowRef`, `patternId` → `flowId`, `changePattern` → `changeFlow`, `setDefaultPattern` → `setDefaultFlow`, `defaultPatternId` → `defaultFlowId`, and so on. The folder `patterns/` becomes `flows/`.
2. **Six built-in flows.** Their steps are unchanged from today's `change`, `bugfix`, `feature`, `design`, `investigation` and `goal`. Each file keeps `name`, `description`, `whenToUse` and `steps`. The internal service flows (revert, delivery review, delivery checks) stay as they are.
3. **Removed:**
   - **Five built-ins:** `change-cross-review`, `feature-design-gate`, `goal-plan-gate`, `change-best-of-two` and `change-lean`.
     - Pausing remains available through the task's "Review every step" switch.
     - A review by the other provider remains available through role defaults (coder Codex, reviewer Claude) and per-step pins.
   - **Personal flow files** (`~/.orchestration/patterns`), `extends`, `stepOverrides`, the loader for them, Reload, `POST /api/patterns/reload`, and the file-errors list.
   - **The audience model:**
     - "standard" vs "yours only", experiments, hypotheses, and the picker's groups and chips.
     - **The rules that stay:**
       - The lead may pick any flow, and the project default can be any flow.
       - A Goal's child tasks may use any flow except Goal.
       - The service uses Change for fixes and Bug fix for a send-back fix, as today.
   - **Outcome records:** the `TaskOutcome` capture and its tests. They existed for the scrapped comparison.
   - **Exporting retired templates as pattern files** at migration (ORC-016 14 → 15). The migration still has to run correctly for older databases; templates it retired simply are not written as files any more.
4. **Settings:**
   - A "Flows" card shows the default flow (a select), plus each flow's name, "use it for" line and a read-only step list.
   - It has no Reload and no error list. A broken flow file is a test failure in the repository, never a runtime state.
5. **The New task and task page:**
   - One plain select, showing each flow's name and its "use it for" line, with a read-only step preview.
   - "Flow: Change" on the task page.
   - "Change flow" before a task starts or while it is paused, with the same rules and stale guards as today's `changePattern`.
6. **The lead's instructions:** a "## Flows" section listing the six flows, with "Pick `flowId` from these, or leave it out for the default (`change`)". Breakdown items list every flow except Goal.
7. **A state migration, 15 → 16:**
   - **Renamed persisted fields:**
     - `task.pattern` → `task.flow`;
     - `task.patternSince` → `task.flowSince`;
     - `pipelineHistory[].pattern` → `.flow`;
     - `project.defaultPatternId` → `project.defaultFlowId`;
     - `state.patterns` → `state.flows`.
   - **Dropped:** `task.outcome`, and `retiredTemplates` once the migration no longer needs it.
   - **Tasks that ran a removed flow** keep their copied steps and their recorded flow id and name. Nothing about their pipeline changes.
   - **A default that pointed at a removed flow** becomes `change`.
   - **The migration has a test** that loads a format-15 state with every removed id and field.
8. **The demo:**
   - WT-011 ("Faster trail search") ran the best-of-two experiment; it becomes a Change task.
   - Nothing else in the story changes.
   - The demo stays labelled simulated.
9. **The real-run test** (`scripts/real-run-test.mjs`) no longer writes a personal pattern file. It uses the smallest built-in flow that still exercises a Claude worker and a Codex worker at once, and pause and resume, and it says which flow it uses.
10. **The README:**
    - The "Adding or changing a pipeline pattern" section becomes a short "Flows" section: the six flows, with when to use each and their steps, and a note that changing a flow means editing `flows/<id>.json` and running `npm test`.
    - Mentions of patterns, experiments, personal files, hypotheses and the Compare page are removed.
    - The "Measuring, not guessing" section describes only what exists: usage and cost per provider and model, checks recorded by the service, and every artifact versioned.
    - The Status table gains ORC-021.
    - Screenshots that show the old picker or Settings → Patterns are retaken with `npm run capture`.
11. **A security review wherever there is a code review (r2, the owner's request).**
    - **A new role, `security_reviewer` ("Security reviewer"),** with its own role brief: review the change for security, such as injection, authorisation and access control, secrets and credentials, unsafe handling of input, files and commands, and risky dependencies, and report findings with severity and action like any review. It has its own project role default, the same as the code reviewer's unless you change it, and can be pinned per step like any role.
    - **Where it runs:** a security review step runs **in parallel with** every code review step:
      - Change S2;
      - Bug fix S3;
      - Feature S3;
      - the internal delivery review;
      - the internal revert pipeline's review.

      It reads the same inputs as the code review it sits beside.
    - **How it joins the loop.** The repair step reads both reviews' findings, and runs if either has findings (`runIf`). The final verification reads both. Both reviews run again in every repair round.
    - **The merge gate counts both.** Wherever the code review's findings gate a merge (delivery review), the security review's findings do too.
    - **Design and Investigation are unchanged,** because neither produces code.
    - **Cost:** one more review run per round. The README says so.
12. **Tests:**
    - Every built-in flow passes the pipeline graph rules.
    - Every flow that changes code has an independent code review.
    - Every flow has `whenToUse`.
    - Plus the migration test, the rename, Change flow, the lead's flow choice and its validation, and the demo still valid.

**Excluded:**

- Orchestration *shapes* (maker-checker, concurrent, hierarchical as separate concepts), a step library, and composition by the lead. These were discussed and set aside: the owner does not want abstract shapes.
- The Compare page and trace export (ORC-018, scrapped).
- Any change to how stages run, artifacts, loops, providers, delivery or checks.

## Options and tradeoffs

| Option | Approach | User benefit | Effort | Costs and risks | Reversibility |
| --- | --- | --- | --- | --- | --- |
| A | Six repository flows, the catalog machinery removed, renamed throughout (code and persisted state, with a migration) | One clear concept, the same word everywhere, much less code | Medium–large (about 1,000 renames, mostly mechanical) | A broad diff; a state migration | Medium (git history keeps everything) |
| B | Six flows and the machinery removed, renamed in the UI and docs only, code identifiers left as "pattern" | Smaller diff | Medium | Code and product say different things; the confusion persists for anyone reading the code | High |
| C | Keep the catalog and only drop the five extra files | Smallest | Small | Leaves the complexity the owner objected to | High |

## Decision

- Agent recommendation: A.
- Selected option: A.
- Decided by: the owner agreed the outcome ("Yes let's do that"); the lead chose the full rename.
- Rationale and evidence:
  - The owner's objection was to complexity and confusing terminology. Only A removes both.
  - The engine is untouched, so the risk is mechanical and caught by the test suite (about 900 tests on `main`).
- Uncertainty and what would change the decision:
  - **The diff's size.** If it threatens stability, the persisted field rename can move to a follow-up, while the UI, docs and code identifiers still change.

- **The migration:**
  - A format-15 database loads.
  - Tasks that ran removed flows keep their steps.
  - Every renamed field is moved.
  - Outcomes are dropped.
  - A default that named a removed flow becomes `change`.
- **The security review.** In Change, Bug fix and Feature, and in the internal delivery-review and revert pipelines, a `security_reviewer` step runs in parallel with each code review. Repair runs when either review has findings. The security reviewer's envelope carries the security brief. Its findings gate a pull request's merge like the code review's.
- **No "pattern" left.** `git grep -i pattern` finds no user-facing or identifier use of "pattern" for flows. Remaining hits are other meanings, such as regular-expression patterns and ORC-016's history in docs.
- **Checks:**
  - `npm run typecheck`, `npm test` and `npm run build`;
  - `node scripts/real-run-test.mjs --fake`;
  - `npm run capture`;
  - an independent review;
  - a browser pass by the lead (light and dark, desktop and 375 px).
