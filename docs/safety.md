# Safety notes

The short version is in the [README](../README.md#safety-in-brief).

- **Network:** the service binds to 127.0.0.1. It rejects foreign `Host` headers, cross-origin requests, and state changes without its client header.
- **Git:** all of the service's git commands run with hooks and fsmonitor disabled. A worktree whose git metadata was tampered with is not recorded.
- **Claude workers:** file tools are confined to their worktree, and they have no shell. There is no setting that gives them one.
- **Checks (ORC-013, and the project environment):** when you turn checks on, the service runs the repository's own code: its install scripts, its test scripts, its build, and whatever those start, including code agents wrote. Where that code runs depends on whether the project has an environment and Docker is running.
  - **In the project's environment** (with Docker). The environment is the repository's dev container (`.devcontainer/devcontainer.json`, read at the trusted base, never from the change: only its `image`, or `build.dockerfile` with `build.context` inside the repository), but only after you confirm it in Settings › Project › Environment by its digest (the file and the Dockerfile it names). A new dev container, or one that changed since you confirmed it, is not used: the checks use the image you confirmed (pinned by digest), or run on this computer, and Needs you asks you to confirm it. So a change an agent merged cannot choose the image. The lead may propose an image; only your Save sets one or confirms a dev container. The default protected paths also hold back an automatic merge of `.devcontainer/**`, `.devcontainer.json` and Dockerfiles.
    1. **Prepare** (your setup commands, for example `npm ci`, `pip install`, `go mod download`; when you set none, the checks' own prepare commands; with neither, nothing is prepared, and the run's record says so): each runs in a container on a private Docker network that has no route out and no address of the Docker host. Its only way out is an egress proxy, a small script in the official Node image (pinned by digest) that allows HTTPS through `CONNECT`, by host name, on port 443, to the registries' list (npm, PyPI and its file host, crates.io and its index and static hosts, the Go module proxy and checksum database, RubyGems, Maven Central) and the hosts you added. It refuses IP addresses, other ports, plain HTTP, and any name that resolves to a private or local address; it does not decrypt the traffic. Install code may run here. It runs as a non-root user with no capabilities and no new privileges, within limits on processes, memory and CPU, on a copy of the change without `.git`, with the project's cache folder, and with nothing else from this computer: no other folder, no Docker socket, no secrets in its environment.
    2. **Run** (the check commands): each runs in its own container with no network (`--network none`), on the prepared image and the copy. A test report the change or its prepare left in the copy is removed before the checks run.

    Before the first run, the service probes this machine's setup. A container on the private network must fail to reach the internet, this computer (through the host gateway), the Docker VM on its SSH port at each of its addresses (the gateways that `docker network inspect` lists for the private network, the proxy's network and Docker's default bridge), and an outside name. Only no route or no answer counts as unreachable: a refused connection means a host answered. The proxy must refuse a host off the list, this computer's loopback, the host gateway, and a listed name that resolves to this computer (its private-address rule, the guard for a registry name that resolves privately). A listener on this computer's loopback must see no connection. If the probe fails, or Docker is not running, or the image cannot be pulled or built, the checks run in the host sandbox below, and the run's record says why. One environment run goes at a time.

    **When Checks steps wait.** A Checks step waits until the place where it will run is ready: the project's environment when it has one and Docker passed this probe, else the host sandbox below, by its own probe. A change to the environment setting probes again. When the checks run in the environment, the host sandbox is not probed. So a run that comes to it anyway (Docker stopped, or the image could not be pulled) probes it first, and runs nothing if it is not ready.

    **The copy on this computer.** The containers write to the copy of the change (`/work`) and the project's cache folder (`/cache`), both on this computer's disk. The service measures them while a step runs; past 8 GB it stops the step's containers and says why, and a cache past 4 GB starts again empty before the next prepare. The copy is removed only after Docker no longer lists any container that mounted it, and the removal never follows a link.

    **What this does not stop.** Install code can send what it reads in the copy to an allowed registry host, in a request's address or body. A package on an allowed registry can itself be hostile, and the lockfile an agent writes chooses the packages. The image's own files are writable inside the container, and the prepared image keeps what the prepare wrote: a later commit with the same image, prepare commands, hosts and prepare inputs reuses that prepare, so a change whose install code is hostile can plant files that the project's later check runs read. The project's cache folder is shared by its prepares in the same way. A dev container's Dockerfile builds with no network for its `RUN` steps, but Docker itself fetches its `FROM` images and any `ADD` address, and pulls a dev container's image from wherever it names, as named (your confirmation covers the text, not what a tag points to later). A Dockerfile with a `# syntax=` line (a BuildKit frontend that the builder would fetch and run) or a cache mount (shared by every build on the Docker daemon) is refused. Checks can still be weakened through files they read (the test scripts, the test configuration).
  - **On this computer** (no Docker, no environment, or the environment could not start). In the Codex sandbox the code cannot write outside a throwaway copy of the change and cannot use the network. The one exception is a dependency download by npm, pnpm or yarn, which runs with every install hook off (`--ignore-scripts` or yarn's `--mode=skip-build`, `--ignore-pnpmfile` for pnpm, and yarn's own `yarnPath` and plugins never used), so no repository code runs while the network is on. Every other setup command (bun, pip, uv, poetry, bundle, gradle, mix, swift, cargo, go, make, …) runs offline, and its record says that other languages need the project's environment and Docker. Scripts a project needs run afterwards, offline, in a separate step. The sandbox does not stop that code from reading your files. The sandbox is probed before any run (writes outside the copy, connections to this machine's own loopback and to the network must all be refused), and nothing ever falls back to running unsandboxed by itself.
  - **Either way:** each command's exit status comes from the service's own wrapper process (the reaper, or `docker run`), never from anything the command can write. A cancelled CI job is re-run once through `gh api -X POST …/actions/jobs/<id>/rerun`, recorded like every other GitHub write, and only that endpoint, a pull request's comments and the read-only GraphQL query are ever sent as writes; a review bot's verdict and a skipped required check wait for you instead of starting a fix task, while a job cancelled because another job of its workflow run failed, cancelled again after its re-run, or cancelled at GitHub's job time limit is treated as a code failure.
- **Codex agents:** they run in Codex's sandbox. Writes are limited to their worktree and a private temp directory, and network access for commands is off. **They can still read files elsewhere on your machine.**
- **Connections:** MCP servers and plugins you allow run with your permissions and are not sandboxed.
- **Housekeeping (what runs leave behind):** the service looks for what Orchestrator's runs left on this computer. It looks when it starts, every six hours, and when you click Clean up now (Settings › Advanced). It acts only on what it can prove is Orchestrator's:
  - a Codex thread whose session file names Orchestrator's client as its originator. It archives the thread through Codex, where you can unarchive it.
  - a Claude session folder named for a folder that Orchestrator works in (its worktrees, its studio folders, this checkout's `evidence/`), if its transcripts ran there. It moves the folder to the macOS Trash; on other systems it only reports it.
  - a container of the recorder whose service has gone. It removes the container.
  - a container or a Docker network of the project environment, by its label (`orchestrator.environment`), whose service has gone or that is older than any step (three hours). It removes it. Then the environment's work folders under `~/.cache/orchestrator/environment` (a step's copy, the probe's, a prepare on its way to being kept) older than three hours, but only while Docker lists no container of the environment that could still use them.

  It deletes nothing of yours, follows no link, and leaves anything changed in the last hour. The one exception is a container or a network whose service has gone: nothing else will remove it, so it goes at once. A setting turns off the Codex and Claude part, and the simulated service never does it. It does not look for provider processes that outlived a service, because nothing on disk proves which process a service started.
- **GitHub:** only the service runs `gh` and `git push`. It never uses `--admin`, GitHub's own auto-merge, a forced push, a branch deletion or the merge API; the only merge is `gh pr merge --merge --match-head-commit <sha>`. A change to CI workflow files is not pushed until you allow it for that pull request, and a change to other protected files is never merged automatically. An agent environment set to "local" can reach your GitHub sign-in: automatic merging is refused for local environments unless you allow it, and it is listed as a warning in Settings → Delivery. An agent review is not a human review; the required checks, the protected paths, the daily cap and the Review list are the independent layers.
- **The vision studio (ORC-029):** designers make prototypes, terminal demos and documents, and the PE reviews them. All of it stays on this computer.
  - **Prototypes** are served from an origin of their own (`p-<artifact>-v<n>.localhost`, on the app's port + 1), in a sandboxed frame that may run scripts and nothing else. Their policy refuses network requests and form posts, and they can read only their own files.
  - **What your own browser still allows:** a prototype can still send a few bytes out through WebRTC (STUN, and TURN over TCP), `<link rel="dns-prefetch">` and `<link rel="preconnect">`. Chrome does not apply a page's policy to these. Chrome's "Preload pages" setting and its WebRTC IP policy stop all but TURN over TCP; only a proxy or a firewall stops that.
  - **Screenshots** use a headless Chrome with no way out: no UDP for WebRTC, a dead proxy, and name lookups for `*.localhost` only.
  - **Diagrams:** Mermaid runs in a hidden sandboxed frame that can reach nothing, and the app shows its drawing as an image. Every app page has a strict Content-Security-Policy: everything from the app's own origin, and frames only from the prototype origins.
  - **Terminal demos** record in a Docker container (`npm run recorder:build` builds its image): no network, a read-only root, no capabilities, a non-root user, and limits on memory, processes and CPU. Only a copy of the artifact and a fresh output folder are mounted, and only the files the tape declared are copied back. One recording runs at a time. A probe proves the container's limits before the first recording. Without Docker or the image, a demo shows its hand-written files, with the reason.
  - **Evidence of what the factory built (pass 5):** after the checks of a Feature task, the service captures the screens and CLIs that the task builds, on a copy of the change (no `.git`), one capture at a time. Nothing runs until you set the project's preview setting (the preview command and its port, the CLI entry). Where it runs depends on the project:

    **In the project's environment** (a project with an environment, and Docker; unit E2). The recorder's install never runs, and nothing falls back to it:
    1. **The prepare** is the checks' own (above): the same probe, copy, image and prepare, reused by its key.
    2. **The screens:** the built app runs in the project's image with no network (`--network none`), as the checks' run phase does. The recorder's Chromium runs in its own container that joins the app container's network namespace (`--network container:<preview>`): the two share one loopback and nothing else. So the app can connect to the browser's ports; the browser opens none (Playwright drives it through a pipe), and only its dead proxy listens there.
    3. **The CLIs:** each tape is typed into a container of the project's image with no network and a terminal. The service attaches to that terminal through the Docker daemon's API on its local socket, the same socket the docker command uses. The service holds that socket; no container gets it.

    **In the recorder's container** (a project without an environment), in two runs:
    1. **The install** is the only container with a network. It runs npm, pnpm or yarn with every install hook off, as the checks do, and with no git program, so no repository code runs. npm can still fetch from any address that the lockfile or `.npmrc` names, this computer included: Colima forwards the container's host gateway to this computer's own loopback.
    2. **The capture** has no network. It runs the preview, Chromium with the screenshot Chrome's hardening, and VHS for each tape. Chromium runs without its own sandbox; the container is the sandbox.

    Only the files that the coder's plan names come back, as regular files of their type, never through a link. On the recorder's path, the built code runs as the same user as the capture, so code that means to deceive could plant a picture; in the project's environment, the app runs in a container of its own with no output folder. The reviews and the tape show what ran.
  - **Reading your repository:** a Claude designer, lead or PE reads it through a read-only checkout, and a designer writes only to its own staging folder. A Codex agent's reads are not confined, as for every Codex run.
  - **Authority:** the lead, the designer and the PE cannot approve, overrule, lock in, choose the domains or start the factory. Only your own commands do. The lead's reply must match a fixed schema, and the service checks every part of it.
  - **Your own apps:** runs leave no thread in your Codex app and no saved session in Claude.
- **Autopilot:** the lead reads summaries that agents wrote, and on Autopilot its proposals start without review. Treat repositories and connections you do not trust accordingly. Use Check-in, or review gates, when that matters.
- **Steering by conversation (ORC-009):** when you message the lead, it may change the focus, reorder and defer open root tasks, and drop its own unstarted proposals. Only runs that answer your messages may steer, so agent-written summaries cannot steer through a planning run; a reply run still reads them. The damage is bounded: four verbs, at most 20 task changes and one focus change per reply, nothing is interrupted, nothing you created or started is cancelled, settings, specs and pins are out of reach, and every change is listed with Undo. The lead cannot steer the app's own delivery work: the review and fix tasks it creates for a pull request are rejected as not steerable and are left off the lead's board. Choices you made by hand (a priority, a pause) are never overridden. Settings can limit the lead to its own proposals or to suggestions only. Steering has been exercised only with scripted and simulated leads, not with real Claude or Codex lead runs.
